Completion Gate 错误码、盲区与推荐重构方案

这版说明记录当前已确认的 Gate 错误码设计。Gate 只处理确定性状态、证据和同步问题；语义问题交给 Agent 和后续 Review 设计。

确定性 Gate Semantic Reviewer Evidence Freshness Requirement Ledger 问题 推荐方案
核心判断

Gate 应该阻止不安全提交、过期提交、证据不新鲜提交；不应该用“有没有 ChangeSet” 粗暴判断用户需求是否完成。Reviewer 也不应该对“你好”这种低风险对话硬触发。

1. Completion Gate 错误码表

这里记录目标设计命名。语义问题不在 Gate 里用程序规则写死；Gate 只负责状态机、会话一致性、证据新鲜度和结构完整性。

错误码 校验逻辑 解释 修改方案
FINISH_MESSAGE_EMPTY 只校验 finish.message 去空白后非空。 最终交付入口必须带用户可见 message；不再根据 Markdown 形态、长度比例或“是否像完整交付物”做程序判断。 采纳。只保留非空校验，删除其他启发式校验。
FINISH_NOT_ALLOWED 调用 finishAllowed(strategy, finishPhase)：talk/ask + chat、plan + planning、execute/fulfill + executing 才允许。 只有当前 Runtime state 与策略匹配时才允许 finish。等待用户输入、检查中、提交中、已终态等阶段都不允许再次 finish。 保留。作为 Runtime 状态机保护；正常情况下模型只会在工具披露允许时看到 finish。
TOOLS_STILL_RUNNING 检查 ActiveTools != 0。 还有工具调用未结束时不允许最终交付，防止提前宣布完成。 采纳。作为工具并发硬约束。
RUN_ALREADY_CANCELED 检查 finish 时上下文是否已取消：ctx.Err() != nil 或 CompletionContext.Canceled。 用户或系统已取消 Run，禁止继续成功交付或 commit。 采纳。由 RUN_CANCELED 重命名。
RUN_FATAL_EXIST 遍历 Runtime issues，存在 SeverityFatal 即拒绝。 存在严重级别为 fatal 的内部问题。当前 Gate 只把 fatal issue 当全局硬阻塞。 采纳。后续需定义 fatal 产生边界。
RUN_SESSION_MISSING 写策略下检查 Session != nil。 写任务没有活跃 RunSession。没有会话就无法安全记录变更、baseline 和 commit。 采纳。只对真实写入/commit 路径触发。
RUN_REVISION_CONFLICT 调用 Session.ValidateBaselines()，若 baseline hash 与当前资源 hash 不一致则拒绝。 Run 开始或首次触碰资源时记录的 baseline 与 finish 时资源实际状态不一致，说明资源被其他操作改过。 采纳。保留为乐观并发/恢复场景的冲突错误。
PLAN_NOT_COMPLETE execute/planned 下检查 Plan == nil || Plan.HasBlockingSteps()。 execute/planned 下仍有 pending、in_progress 或 failed 步骤，不能交付。 采纳。计划模式必须闭环。
EVIDENCE_SCHEMA_MISSING 对发生变更的 outline、design、slide spec 执行结构化 schema/模型校验。 结构化资源变更后，必须证明当前 JSON 模型合法。 采纳。作为结构化资源证据缺失的唯一 Gate code。
EVIDENCE_HTML_MISSING 对发生变更的 HTML 执行静态校验与渲染校验。 HTML 变更后，必须证明 HTML 静态合法且实际渲染无阻塞问题；不再拆成 static/render 两个对外错误。 采纳。合并静态与渲染校验；不再使用组合 hash 作为对外概念。
ASYNC_SPEC_HTML 当目标要求 presentation/HTML 成品时，检查 Slide Spec 或 Design 变更是否已同步到对应/受影响 HTML。 Spec/Design 到 HTML 的同步问题；如果用户只要求修改设计稿/spec/design，则不应触发。 先保留。合并原 ASYNC_SPEC_HTML 与 ASYNC_DESIGN_HTML；后续再处理工作目标设计。
ASYNC_DECK_SLIDE 对 outline 和 slide specs 做完整引用合法性校验。 Deck outline 与 slide specs 不同步，或 section/subsection/slide order 引用非法。 采纳。作为 deck/slide 结构同步问题的唯一 Gate code。
COMPLETION_GATE_BLOCK Gate 拒绝后，Runtime 生成一个失败 tool observation，把 Gate issues 回灌给同一 ReAct Loop。 Gate 问题的汇总 wrapper，不是根因；根因在 issues 列表里。 采纳。只汇总 Gate 问题，不混入 Review 问题。
COMPLETION_REVIEW_BLOCK Review 拒绝后，Runtime 生成一个失败 observation，把 Review issues 回灌给同一 ReAct Loop。 Review 问题的汇总 wrapper，不是根因；根因在 Review issues 列表里。 采纳。用于和 Gate block 明确拆分。
COMPLETION_BLOCK_REPEAT 同一 rejection key 且 EvidenceLedger version 未变化，重复达到 MaxIdenticalGateRejections。 同一组 BLOCK 原因超过 3 次，终止本次 Run，防止无限 finish/reject 循环。 采纳。由 COMPLETION_REJECTED_REPEATEDLY 重命名。

1.1 Semantic Review 错误码表

Review 错误与 Gate 错误拆开。Review 负责语义判断，不应被写成固定程序规则；后续将单独重新设计 Review 的触发方式、输出分级和修复协议。

错误码 校验逻辑 解释 修改方案
SEMANTIC_REVIEW_UNAVAILABLE 按 SemanticReviewPolicy 需要 reviewer，但 reviewer store/provider 不可用，或 reviewer 输出无法解析。 当前默认 conservative，会阻塞 finish；但这不应该影响低风险普通对话。 待重设。后续和 Review 触发机制一起设计。
QUALITY_RUBRIC_FAILED Reviewer 根据 PPT completion rubric 判断存在质量问题。 涉及叙事、层级、空间、对比、可读性、一致性等语义/审美判断。 待重设。不应作为程序硬规则；需要 Review 分级。
FINAL_ANSWER_INCOMPLETE Reviewer 判断 finish.message 不包含完整用户可见交付，或与完成事实不匹配。 这是语义判断，不由 Gate 的 Markdown/长度启发式替代。 待重设。放入 Review 设计讨论。
USER_INTENT_MISMATCH Reviewer 比对 WorkSpec、上下文和最终声明，判断结果偏离用户真实意图。 这是 Review 的核心价值之一，但需要可解释、可修复。 待重设。后续确认是否返回 ask_user / repair / warning。
EVIDENCE_CONTRADICTION Reviewer 比对 final claims 与 ChangeSet/Evidence/Issues，发现声明无法被证据支持。 例如 final 声称已渲染，但没有相应 render evidence。 待重设。后续设计 claim-check 协议。
CONTEXT_INSUFFICIENT Reviewer 判断 review input 缺少做出接受判断所需的资源、证据或上下文。 不一定是失败，也可能意味着需要 read/search/ask_user。 待重设。暂列入 Review 表，后续确认是否保留。

2. Semantic Reviewer 应该怎么触发

你说“规则触发式不好”有道理，但完全交给 Agent 主动选择也不够安全。生产级产品一般是混合模式： 确定性边界必须由系统守住；需要判断力的审查可以由风险路由触发，也允许 Agent 主动请求。

A. 全规则触发

不推荐。呆板、贵、误拒绝多。尤其“你好”这种无风险输入不应被 reviewer 阻塞。

B. 全 Agent 主动选择

不够。主 Agent 有任务完成压力，可能低估风险；它不该自己决定所有审查边界。

C. 风险路由 + 主动请求

推荐。Runtime 根据风险强制少量审查；Agent 可主动调用 reviewer 工具获取第二视角。

Codex 的 Auto-review 做法是把 reviewer 放在 sandbox boundary：大部分沙箱内动作不打扰，只有越界动作交给独立 reviewer； reviewer 也不能扩大权限。Claude Code 的 hooks 设计也强调：确定性规则用 hooks，判断型规则才用 prompt/agent hooks。 Trae 的 skill 实践更偏“按任务选择专门 reviewer/skill”，而不是所有普通对话都过一个重型最终审查。

3. 推荐的最佳设计

3.1 拆开 intent 和 expected_effect

execute 只表示“允许写”。是否必须写，应该由一个独立字段表达。 

{
  "interaction": { "intent": "execute" },
  "expected_effect": "none | may_write | write_required",
  "target": { "artifact": "presentation", "level": "slide" }
}
  • none：问候、解释、状态查询，必须不写。
  • may_write：Agent 可判断是否需要写；无变更也可完成，但不能谎称已修改。
  • write_required：用户明确要求改/生成/删除，没 ChangeSet 才阻塞。

3.2 Gate 只守硬边界

  • finish contract。
  • phase / cancel / tools running / fatal issue。
  • scope / session / revision conflict。
  • 如果有实际 ChangeSet，则要求对应 evidence fresh。
  • 如果 expected_effect=write_required，则要求至少一个授权范围内的 material change。
  • 不再用粗糙 Requirement Ledger 阻塞所有 execute。

3.3 Reviewer 变成“风险审查器 + 可调用工具”

  • Runtime 强制触发：结构调整、整份 deck、多页、删除、跨 scope、用户要求高质量交付、准备 commit 公共成品。
  • Agent 主动触发：觉得需求复杂、视觉判断不确定、用户要求 review、自己做了大改。
  • Runtime 禁止触发：问候、纯说明、无资源访问的 chat、小型 no-op。

3.4 Reviewer 审查 claims，而不是审查“有没有干活”

reviewer 的输入应包含 final claims、ChangeSet、Evidence、风险等级和用户需求。它应该判断：

  • 最终回答有没有夸大。
  • 声称的修改是否有证据支持。
  • 用户明确要求是否被覆盖。
  • 是否需要人确认，而不是盲目阻塞。

4. 建议落地改动清单

优先级 改动 原因
P0 删除 IntentExecute && ChangeSet.Count()==0 这类语义硬判断 这是当前最严重误判来源，会让“你好”或 no-op 被判失败。
P0 从 runtime prompt / repair guide 删除“execute 必须有变更、ledger pending 必须完成”的硬表述 避免模型被提示词训练成“为了通过 Gate 强行改东西”。
P1 新增 expected_effect 或等价字段 把“允许写”和“必须写”拆开，消除系统性歧义。
P1 Requirement Ledger 降级为 advisory，不再硬阻塞 当前标记算法不能证明逐条需求完成。
P1 新增 request_review / review_finish 控制工具，允许 Agent 主动请求 reviewer 保留 Agent 主动判断能力，不把 reviewer 做成死规则。
P1 Runtime 增加风险路由：低风险跳过，中高风险强制 reviewer 符合生产实践：少量高风险过强审查，低风险保持流畅。
P2 Reviewer 输出分级：block / warn / ask_user / pass 不要所有 reviewer concern 都阻塞；有些应该成为最终 warning 或用户确认。
