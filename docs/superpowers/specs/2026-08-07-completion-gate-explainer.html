PPT Agent Reviewer 设计说明

Review 被设计成 review_completion 工具，由主 Agent 在 plan / execute / fulfill 中显式调用。Reviewer 只返回检查观察，不返回 action，不替主 Agent 决策下一步。

checks[] 无 action 无 decision 单次 LLM JSON 显式工具调用
设计结论

Reviewer 是 ReAct loop 中的 observation provider。它指出问题，但不规划动作；主 Agent 读取 checks 后自己思考下一步。

REVIEW 错误码介绍

表格列为：错误码、触发情况、下一步处理。这里删除 REVIEW_IMPROPER_OUTPUT，因为公开实践中 Codex/ClaudeCode 更强调边界、工具、执行与安全审查，并没有明确做“最终文案质量”专门错误。

错误码 触发情况 下一步处理
REVIEW_PASS Reviewer 未发现需要提示或修复的问题。 主 Agent 可继续执行或 finish。
REVIEW_SERVICE_UNAVAILABLE Review 服务不可用、调用失败、超时、返回非法 JSON 或 schema validation 失败。 作为提示返回给主 Agent；不默认阻塞低风险任务。
REVIEW_LACK_INFO Reviewer 缺少足够上下文做判断，例如没有 ChangeSet、没有 Gate 摘要、没有目标资源信息、用户意图不清。 主 Agent 自行判断是补充上下文、继续读资源，还是向用户提问。
REVIEW_QUALITY_POOR PPT 质量较差但不一定是执行错误，例如视觉层级弱、表达粗糙、叙事不顺、排版质量不符合高质量交付。 主 Agent 判断是否继续优化，或在最终回复中说明当前质量风险。
REVIEW_INTENT_MISMATCH 结果与用户需求有偏差或只完成一部分，例如目标页错了一部分、遗漏用户约束、执行范围不完整。 主 Agent 应继续修复或向用户澄清取舍。
REVIEW_EXECUTE_WRONG 执行结果直接错误，例如改错对象、删错内容、生成结构明显错误、违反用户明确指令。 主 Agent 不应直接 finish，应进入修复或回滚路径。

REVIEW 分析方案

Review 的核心不是“再跑一遍 Gate”，也不是“替 Agent 决策下一步”，而是提供独立观察。Reviewer 直接输出 JSON 检查数组，主 Agent 自行决定下一步。

Reviewer 输入

{
  "run_id": "run_123",
  "strategy": "plan | execute | fulfill",
  "work_spec": {
    "target": {},
    "interaction": {},
    "instruction": ""
  },
  "plan": {},
  "changes": {},
  "gate_result": {
    "accepted": true,
    "issues": []
  },
  "evidence_summary": [],
  "context_briefing": "",
  "candidate_message": ""
}

Reviewer 输出

{
  "checks": [
    {
      "code": "REVIEW_PASS",
      "summary": "未发现需要提示或修复的问题。"
    }
  ]
}
字段 约束 说明
checks 数组，建议 1-5 项。 一个 Reviewer 可以抛出多个问题；如果完全通过，返回单个 REVIEW_PASS。
code 必须在错误码枚举中。 code 本身隐含严重程度，不需要额外 severity。
summary 自然语言，必须可读。 解释 Reviewer 为什么给出该 check。主 Agent 根据 summary 自行思考下一步。
candidate_message 可选但推荐。 如果希望 Reviewer 检查最终回复质量，主 Agent 必须传入准备提交给 finish 的候选 message。

REVIEW 触发方式

Review 是显式工具，不隐藏在 finish 之后自动执行。它只在 plan / execute / fulfill 中披露，不在 talk / ask 中披露。

触发方式 什么时候触发 设计结论
Agent 主动调用 主 Agent 自认不确定、任务复杂、视觉判断主观、用户要求 Review、或计划/执行结果需要第二视角。 提供 review_completion 工具，由 Agent 显式调用。
用户显式要求 用户说“审查一下”“帮我确认”“不要直接交付”。 仍由 Agent 理解用户意图后主动调用 review_completion，不是 Runtime 写死规则触发。
Plan Review 用户要计划，或主 Agent 认为计划复杂、风险高、需要第二视角。 plan 可以使用 review_completion，因为计划本身也是交付物。
禁止触发 talk / ask。 不披露 review_completion，避免普通对话变重。 
工具披露规则：
review_completion is disclosed only when:
  strategy in ["plan", "execute", "fulfill"]

review_completion is not disclosed when:
  strategy in ["talk", "ask"]

外部实践参考

Codex Auto-review

Codex Auto-review 的公开设计更像“边界审批替代”：当主 Agent 需要越过 sandbox 或执行高风险动作时，独立 reviewer 判断是否允许。它不扩大权限，也不是每个普通回答都审查。

  • 确定性边界仍由 sandbox / policy 控制。
  • Reviewer 提供第二视角，但不替代所有规则。
  • 主要检查动作风险，而不是专门审 final message 文案。
  • 失败后主 Agent 可以寻找更安全路径继续。

ClaudeCode Hooks

ClaudeCode hooks 的设计启发是：确定性规则用程序化 hook，判断型规则才交给 prompt/agent hook。比如“是否访问 .env”适合确定性拦截；“方案是否完整、是否符合用户意图”才适合 Reviewer。

  • Gate 类规则：message 非空、工具是否运行、Run 是否取消、HTML 是否可解析。
  • Review 类判断：质量是否差、意图是否偏、执行是否明显错。
  • 公开实践没有证明必须专门做 final message 文案错误码。
  • Reviewer 结果应作为 observation 回到主 loop。

对 PPT Agent 的最终建议：review_completion 是显式工具；它做单次 LLM JSON Review，返回 checks[]；不返回 action、不返回 decision，由主 Agent 消费后继续 ReAct。
