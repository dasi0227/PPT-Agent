## 必要适配

1. **命令提交**：重命名先生成候选标题；标题、自动命名设置和命令终态在同一事务提交。取消或操作版本失效时不应用候选。压缩和交接沿用对应的事务化结果提交。
2. **重试身份**：命令创建、命令取消、Run 取消在网络结果未知时保留原请求 key、场景和实体版本。明确失败后释放该请求；跨场景不自动改写为新请求。回执仅确认操作，不跳过尚未消费的增量批次。
3. **资源草稿**：用场景、Run、交互、预期版本及原始草稿的规范化哈希识别重试。先查已提交回执，再读取当前审批和文件基线；内容未变化也保存回执。
4. **既有展示行为**：保存 `active_duration_ms` 与可空的 `active_since`，区分活动计时和等待；用户输入显式携带 `steering`，保留初始输入的回退入口；建议生成入口按“已加载、有历史、无活动任务”判断。
5. **命令权限语义**：内部执行阶段持久化与公开工具开始分开处理，保留原有策略拒绝、隔离候选执行和审批后处理的顺序。
6. **轻量 Run 查询**：从当前行提取模型路由信息，不为普通查询反序列化完整恢复检查点。
7. **协议适配**：前后端统一使用场景、实体／交互版本和当前实体响应；受影响的既有测试源码同步调整，不为旧接口保留兼容分支。

当前模型接口是同步 `Generate`，没有部分文本流。原设计 §5.9 的流式草稿机制不作为本次新增功能实施；完整响应仍先持久化再解释执行。

## MVP 故障收尾与最终验证

按后续授权，本轮仅修复命令收尾和文件／数据库提交结果不明这两处一致性缺口，完成必要的前端错误接线、针对性验证及保留数据的启动复核。三个子智能体均使用 GPT-6.1 Sol / max；没有扩大到旧失败测试修理、长期垃圾回收或全故障矩阵建设。

### 命令终态持久化失败

- 已计算出的结果最多尝试提交三次；每次失败后核对数据库中的同一命令、attempt、场景、owner 和执行代次。提交已成功但确认丢失时接受已保存的终态，不重新调用模型或 Git。
- 普通命令仍不能提交时，尝试保存 `interrupted / COMMAND_RESULT_UNCOMMITTED`，不应用业务候选。Git 命令保留活动状态与持久化 intent，由既有启动恢复核对外部提交事实，防止再次执行副作用。
- 存储持续不可写时保留工作线程的失败记录；命令 GET、会话 view／changes／SSE 及关闭服务均能显露 `PERSISTENCE_FAILED`。接受命令后的启动屏障失败、连中断状态也无法保存的路径同样处理。
- 前端对尚在观察的命令每两秒核对一次当前状态，维持单个在途请求，终态／错误／场景失效时清理。SSE 的持久化错误重新读取 view 并进入现有错误栏，避免没有增量可发布时永远等待。
- 完成回执的摘要和身份纳入内部执行围栏，命中旧回执后仍复核当前执行代次。持续存储故障不伪造数据库终态；恢复存储后重启服务，沿用现有恢复流程。

### 文件与数据库提交结果不明

- 数据库提交返回错误后，使用脱离原请求取消信号、最长五秒的查询核对原 `artifact_commit` 回执。匹配的已完成回执保留提交后文件；明确无回执才回滚；查询失败、回执未完成或哈希冲突均保留 mutation journal。
- 未决提交暂停工具执行，不发布伪失败观察、不继续下一工具。回滚、journal 更新或删除失败也保留恢复状态。
- 项目写锁内检查未决 journal，阻止新 Run 写入、人工页面修改、外观修改、附件上传和项目历史切换覆盖恢复现场；取消原 Run 不能绕过此限制。恢复器在同一文件锁内直接恢复，不受自身写入围栏阻挡。
