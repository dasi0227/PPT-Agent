# 单次模型命令的提示词与输入边界

日期：2026-09-29。以本次用户要求为准，替代旧文档中 polish 的完整项目上下文、rename 的首条需求/长历史优先和三项命令共享主路输出规则的约定。

## 问题核实

| 命令 | 改造前实际输入 | 判断 |
| --- | --- | --- |
| polish | `core.output` + 独立提示词；项目标题、内容要求、完整目录摘要、视觉要求、目标页设计稿及 HTML 摘要、相邻页、近期用户消息 | 明显过量。未直接使用执行 Agent 的全部系统提示词，但专用 AssemblePolish 仍复用了执行所需的资料；“变成 PPT 创作指令”的角色定位还会诱发扩写。 |
| commit | `core.output` + 独立提示词；项目标题、文件状态、行统计和 staged diff | 没有历史对话或执行上下文。问题是额外的主路公开表达规则、项目标题对语言/主题的干扰，以及提交格式要求不够明确。 |
| rename | `core.output` + 独立提示词；首条需求、最多 16 条近期输入、4 条最终回复、完整公开计划、已有压缩摘要 | 并非全量历史，但没有在收集时聚焦近期阶段；超预算时先删除回复和计划，反而留下首条需求，削弱进度信息。 |

三个命令本来就使用各自的旁路模型与结果工具；本次修改职责、输入投影和裁剪，不引入 Agent 工具循环，也不额外调用模型生成摘要。

## 独立提示词

三个系统消息分别仅使用 `command.polish`、`command.commit`、`command.rename` 的正文，版本为 `2026-09-29.v1`。不调用 `PublicPolicy`，不带主路 Agent 角色、执行协议或其他命令提示词。主路和其他命令的版本保持原样。

### polish

定位为文字编辑，保留用户原意与输入性质。修正错字、标点、语序、重复、指代，适度规范已经出现的前端、后端术语；不新增技术栈、事实、受众、参数或交付要求。问候、感谢、继续等短输入及已清楚的表达允许原样返回；不能回答或执行草稿。

`title` 描述编辑方向，如“统一技术术语”“明确指代与限制”；不复述任务内容。`content` 只返回完整草稿，可保留原有列表和代码，不额外套标题或模板。无需修改时正文原样返回，`changed=false`。

参考的 enhance-prompt 面向 Stitch 页面生成，其中补齐设计信息、加入设计系统等行为不适用于本次保守润色，因此未安装、调用或照搬该 skill。仅采用明确术语这一通用思路。参考来源：[enhance-prompt](https://www.skills.sh/google-labs-code/stitch-skills/enhance-prompt)。

### commit

依据实际 staged diff 生成中文 `<类型>: <概述>` 标题和 1–6 项变动。采用 standard-commit 的标题与分点原则：具体、按意图归纳、每项一句、不混杂无关变动、不凑数量。类型为 feat/fix/refactor/perf/chore/docs。

本次模型仅生成一条消息，不接收该 skill 的暂存、拆分、提交或推送操作流程。应用现有提交机制负责实际执行和持久化。已有主 Agent 的 `git_commit` 工具执行路径不属于这个旁路消息生成调用，本次保留。

模型不得从项目名或路径猜测功能，不声称测试通过或提交成功。去除非法输出时重复发送相同请求的三次循环；一次生成失败交给现有命令失败/用户重试流程。

### rename

从近期工作回顾判断当前主题与阶段，允许从结构规划演进为图表打磨等具体阶段；仍允许 keep，避免因为一次小改动或状态变化反复改名。用户最新转向优先，助手回复和计划仅提供进度证据。

标题不添加完成/失败前缀、百分比、时间戳或内部 ID。输入不足时保持现名；不再让最早的请求长期约束现阶段名称。

## 命令输入填充

三个请求均为一个 system 消息、一个 JSON user 消息和一个对应的结果工具，动态内容全部留在 user 数据中。草稿、反馈及历史摘录不会通过字符串拼接逃逸为额外指令段。

| 命令 | JSON 内容 | 不读取或不发送的内容 |
| --- | --- | --- |
| polish | `draft`、可选 `revision_feedback`、最多 120 字的项目标题、工作模式、选页类型与数量；非全页范围最多列出 6 个页码及各 80 字以内标题，显式标明省略数量 | 不读取 manifest/design/spec/HTML、历史、计划或压缩摘要。目录只用于校验范围和生成页面标签；全页范围不发送目录。 |
| commit | `file_status`、`line_statistics`、`staged_diff`、`diff_truncated` | 无项目标题、会话、Agent 规则、执行身份或临时 index 路径。保留原有 96 KiB diff 上限；截断避开 UTF-8 字符中部并明确标记，禁止推断被省略部分。 |
| rename | `current_title`、按事件顺序排列的 `recent_activity`、可选 `progress` | 无固定首条请求、压缩摘要、工具日志、完整计划正文、计划/步骤/页面 ID 和触发原因。 |

polish 读取活动 Run 的目录视图，无活动视图时读取已保存目录，不构建完整创作快照；保留项目/会话归属、模式和范围校验。没有目录的新项目仍可在全页范围润色。

rename 从同一次 journal 读取中倒序选取最近 4 次非空用户输入，保留窗口内最多 2 条最终回复，再恢复时间顺序；只采用这个窗口内最新的计划事件。旧事件不会因为预算尚有剩余而重新加入。

rename 的最新用户输入最多 800 字，其余用户输入各 400 字，回复各 360 字；过长内容保留首尾并标明省略，避免只截头丢掉结尾的用户修正。计划只含标题、状态、完成/总步数及最多 3 个简短步骤，优先当前步骤和下一步。整份请求（含系统消息及工具 schema）使用现有估算器限制为 2,000 tokens；必要时先删除较旧活动，始终保留最新用户输入，再裁减进度和长摘录。这是估算上限，不是供应商 tokenizer 的精确计数。

## 回归与人工验收

已更新或补充请求边界用例，覆盖：polish 不读取损坏的无关创作文件、不带历史和内部页面标识；草稿/反馈 JSON 分离及未修改结果；commit 只发送 staged 证据且非法响应不自动重发；rename 的近期窗口、时序、计划投影以及超长输入结尾修正保留。

按仓库约定，本次只进行代码阅读、静态调用关系核对和 Go 格式化，未运行测试、构建、浏览器自动化或真实模型评测。以下由用户手动执行：

```sh
cd backend
go test ./internal/service -run 'TestPolish|TestCommitGeneration|TestRename'
go test ./internal/httpapi -run TestPolishEndpoint
```

真实模型需重点检查：

1. 在长历史/复杂演示中润色“你好”，正文仍为“你好”，标题解释无需修改；问句保持问句。
2. 润色明确的视觉要求或 Go/PostgreSQL 技术讨论，只规范已有表达；不增加技术选型或执行步骤；修订反馈可生效。
3. commit 用同一份 staged diff 生成具体中文标题和独立要点，不受会话话题或项目名影响，不声称未验证的结果。
4. 长会话从初期规划转入连续多轮图表打磨时，命名反映近期阶段；只微调一个标签时允许 keep；手动命名关闭自动命名、取消及迟到结果保护保持既有行为。

假模型用例只验证请求组装和结果处理，不能证明真实模型一定遵守语义约束。
