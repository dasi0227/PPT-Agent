# 审查与命名工具提交可靠性开发设计

日期：2026-10-02。状态：待开发。本文记录目标行为，不代表现有实现已经支持。

## 1. 目标与范围

解决两个问题：Reviewer 未调用 `submit_review` 时立即失败；命名模型未按 `rename_thread` 协议提交时，命名任务直接失败且缺少诊断信息。

Reviewer 增加运行时指导和有限次协议纠正；命名在模型及接口支持时强制选择 `rename_thread`，并限制每条响应最多一次工具调用。两者继续严格验证最终结果，不将普通文本自动转换为成功提交。

本次覆盖独立审查循环、命名请求、LLM 请求参数及适配器、模型可见工具契约、提示词和诊断日志。编辑依赖、格式化由 [编辑依赖调度与源码一致性设计](/Users/wyw/Desktop/Projects/PPT-Agent/docs/spec/2026-10-02-编辑依赖调度与源码一致性-design.md) 单独负责。本次不调整 JEV 门控、标题语义判断、审查标准、主链路完成规则或前端视觉设计。

## 3. 已确认的行为

- Reviewer 收到纯文本后保留上下文，追加简短的 runtime 指导，再继续执行；由模型选择继续检查或提交结论，不每轮强制调用 `submit_review`。
- 命名在请求层指定 `rename_thread`，同时限制每条响应最多一个工具调用；是否修改标题仍由 `action: rename / keep` 决定。
- 工具缺失、重复提交、错误工具名、参数错误或不符合单独提交要求时，允许有限次纠正；只有最终合法结果才能被接受。
- 模型或接口不支持强制工具选择时，命名使用明确提示词和有限次纠正，记录实际采用的请求策略。
- 记录工具数量、名称、是否含正文和具体校验错误；最终失败保持原有业务错误语义。

## 4. Reviewer 的运行时纠正

### 4.1 响应处理

| 响应 | 目标处理 |
| --- | --- |
| 没有工具调用 | 保存 assistant 响应，追加 runtime 指导；有剩余额度时继续 |
| 合法检查工具调用 | 按现有白名单执行，保留结果与图片，继续审查 |
| 唯一工具调用是有效 `submit_review` | 接受 decision/reasons，结束 Reviewer；继续执行现有审查源文件一致性校验 |
| `submit_review` 参数无效 | 返回具体参数错误，允许修正后重新提交 |
| `submit_review` 与任何其他调用混用，或重复提交 | 拒绝整批，不执行其中的检查或提交；为每个调用返回对应错误，再要求单独提交 |
| 调用未披露或不允许的工具 | 拒绝整批，不执行；反馈当前允许的检查和提交工具 |

在执行一批调用前检查工具白名单和提交混用，避免先执行一部分才发现协议违规。普通检查工具自身的执行错误继续沿用现有结果处理及连续失败预算，不能把服务失败统一归类为模型提交错误。

这里的“单独提交”沿用现有 Reviewer 规则：最终响应中只有一个工具调用，且为有效 `submit_review`。普通正文不作为结论来源，不因本次开发额外增加对伴随正文的拒绝条件。命名仍保留其现有“不得附带普通正文”的独立规则。

### 4.2 指导消息与上下文

纯文本场景的指导语义：

> 本轮没有调用工具，审查结果尚未提交。如果审查已经完成，请单独调用 submit_review，提交 decision 和非空 reasons；如果仍需证据，请继续调用当前可用的检查工具。

实现时沿用现有提示词语言与 runtime 消息风格，避免重复整段审查标准。参数错误应指出具体字段或互斥条件，不只回复“协议错误”，也不能引导模型必须给出 approve。

- 复用主链路的消息来源标记方式。指导属于 runtime 控制信息，不伪装成真实用户的新要求，不写入用户消息列表。
- 保留已收到的 assistant Content、ToolCalls、检查结果、图片和适用的 ProviderContinuation，继续当前独立审查。
- 对已经产生工具调用的错误响应，先写入原始 assistant 调用，再为每个 call ID 补齐失败结果，最后按需追加指导；禁止遗留无结果调用、伪造成功或擅自执行未知工具。
- Responses 的 continuation 与消息指纹必须一致；不要把回复改写为摘要后仍重用原 continuation。Anthropic 按现有适配器正确组织工具结果，不直接复制 Responses wire 数据。
- 成功提交直接结束，没有成功后的工具往返。失败提交返回纠正反馈，不向主 Agent 提前发布最终审查失败事件。

### 4.3 预算与终止

首版每次独立审查最多发送 **2 次协议纠正反馈并继续请求**；额度累计计算，合法检查不会重置。第三次协议违规或额度耗尽时直接失败。该上限为实现常量，不新增用户设置。

现有 32 轮模型请求、128 次检查工具调用、5 分钟总超时、主 Run 预算和上下文窗口检查继续生效。纠正请求计入总轮次；被拒绝且未执行的调用不计为已执行检查，也不推进证据状态。检查工具连续失败计数与协议纠正计数分开。

取消、超时、预算耗尽、不可恢复的 provider 错误，以及审查期间源文件变化，不通过本机制无限重试。没有可安全回放的标准响应时，不凭异常字符串伪造 assistant/tool 消息。

只有有效提交且源文件校验通过，才返回审查结论。最终失败继续返回 `REVIEW_FAILED`；取消保留取消语义。不能把执行失败伪装为 revise/refuse，更不能默认 approve。现有审查持久化回执和恢复逻辑继续保证结论不重复提交。

## 5. 命名的请求约束

### 5.1 两个独立语义

“必须调用指定工具”与“最多调用一次”是两项独立约束。仅关闭并行工具调用仍允许模型返回零个工具调用，不能解决未提交问题。

统一 `GenerateRequest` 增加可选的工具选择及单次调用约束，由适配器转换为对应协议。字段应能区分未设置与显式关闭；尤其不能因 Go 的 `false` 加 `omitempty` 导致实际请求漏掉限制。不设置时保留调用方原有行为，不把命名策略应用到主 Agent、Reviewer 或其他单次命令。

命名请求的目标工具必须存在于本次 Tools；仍只披露 `rename_thread`。业务层传递协议无关语义，不自行拼接各家 wire JSON。无需为本次需求添加未使用的工具选择模式或用户配置页面。

### 5.2 协议映射

在实际模型、端点和当前设置支持时，Responses 请求片段为：

```json
{
  "tool_choice": {"type": "function", "name": "rename_thread"},
  "parallel_tool_calls": false
}
```

Anthropic 请求片段为：

```json
{
  "tool_choice": {
    "type": "tool",
    "name": "rename_thread",
    "disable_parallel_tool_use": true
  }
}
```

`tool_choice` 指定提交工具；并行限制约束调用数量。Anthropic 的 `disable_parallel_tool_use` 位于 `tool_choice` 内，不能误放到请求顶层。参数约束不替代本地对响应数量、工具名称、正文和业务字段的严格校验。

依据：[OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling#tool-choice) 和 [Anthropic Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use#disable-parallel-tool-use)。具体模型支持范围需在实现时结合实际路由确认，不能仅凭协议名称推断所有兼容网关均支持。

### 5.3 不支持时的处理

- 已有可靠证据表明实际模型或接口不支持强制选择时，直接使用自动选择工具及明确提示词；能支持单次调用限制时仍保留该限制。
- 支持情况未知时可以先尝试请求约束；只有明确指向工具选择或并行限制字段的不支持错误，才允许撤掉对应限制并重新请求。鉴权、超时、限流、普通服务错误或其他参数错误不能作为不支持的依据。
- 必要时在现有 HTTP/adapter 错误处理处保留受限的机器错误类型和字段信息，供调用方分类；不要用泛化的 HTTP 400 或自由文本包含判断吞掉其他配置错误。
- 能力决定按实际路由中的模型、协议、端点生效，不能按模型品牌猜测，也不能把现有 `ToolCalls` 或 `MultipleToolCalls` 当成支持强制选择的证据。备用模型切换后重新核对策略，不沿用不适用的 continuation 或能力判断。
- 首版只需任务内记录本次能力判定和策略变化，不新增持久化能力表、历史数据迁移或全局动态配置系统。没有明确不支持证据时，协议违规仍走纠正，不因模型未遵守一次就宣称接口不支持。

这是本需求明确允许的模型能力分支，不引入旧数据结构兼容或新旧业务协议并存。两种请求策略都必须最终提交同一 `rename_thread` 协议。

支持限制依据：[Anthropic Forcing tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools#forcing-tool-use)。

## 6. 命名的有限次纠正与写回

首次响应经过现有 `parseRenameResponse` 校验；纯文本、错误工具名、多调用、夹带正文或参数无效时，保留可安全回放的响应，反馈具体问题，再请求模型修正。

指导语义：本轮命名结果尚未提交；请仅调用一次 rename_thread。需要改名时传入 action=rename 和合法 title，保持原标题时传入 action=keep 并省略 title；不要附带普通正文。

- 一次命名任务首次请求之外，最多允许 **2 次追加 Generate 请求**；协议纠正和明确不支持参数后的重发共享额度，业务层最多 3 次 Generate。底层既有网络重试单独计数，但共同受现有 20 秒任务超时约束，不能为每次纠正重新计时。
- 继续使用该任务捕获的模型路由和同一命名上下文，不重新进行 JEV 门控，不因修正协议改变命名主题或 title/keep 规则。保留现有每轮输出预算，是否调整须有单独证据。
- 有工具调用的错误响应同样补齐对应失败结果；不实际调用未知工具，不执行部分标题写回，不把正文中的 JSON 或标题提取后直接接受。
- 最终有效提交只有两种：`{"action":"rename","title":"合法标题"}` 或 `{"action":"keep"}`。keep 仍然是成功提交，且不强迫产生新标题。
- 写回前继续检查任务取消、项目 generation、线程命名 operation version 和自动命名状态；重试期间用户手动改名或新请求取代旧任务时，旧结果不得覆盖新状态。
- 整个过程仍是一条命名 command execution。外层阶段不能因重试反复回退；内部尝试使用独立计数表达。合法结果只消费和写回一次，成功后不追加工具确认请求。
- 次数或时间耗尽后保持现有标题，命令明确失败；已取消或被取代继续使用对应生命周期语义。不得用占位标题、普通文本或静默 keep 掩盖失败，也不自动启动新的同类命名任务绕过预算。

## 7. 工具契约与提示词

同步修改实际发送给模型的定义和提示词，而非只更新说明文件：

- `submitReviewSchema`、`toolOutputSchema("submit_review")`、Reviewer Submission 段：说明成功提交结束独立审查，失败提交可收到错误反馈并在预算内修正。
- `renameThreadToolSchema` 及命名提示词：明确通过工具提交 rename/keep；将当前“不会有工具回复”的绝对表述收窄为成功后没有回复，无效提交可能收到纠正反馈。
- “一次”约束提交响应中的唯一工具调用和最终结果只被接受一次；被拒绝的调用不算有效提交，不能用“整个任务只能调用一次”禁止后续协议纠正。
- 成功提交仍使用 no-reply 契约；失败反馈使用可操作的错误描述，并同步必要的错误输出 Schema。所有模型输入参数，包括嵌套字段，都在真实 Tool Definition 中保留具体用途说明。
- 检查 `ModelToolSchemas`、Observation 投影和 Responses/Anthropic 最终序列化，确保改动真正到达模型。保留业务参数和 approve/revise/refuse 的既有含义。
- 开发时更新 [TOOL.md](/Users/wyw/Desktop/Projects/PPT-Agent/TOOL.md) 对应章节，明确成功结束与失败纠正的区别；不要把其他单次命令一并改造成纠正循环。

## 8. 日志与公开状态

每次协议违规记录一条结构化诊断，并在最终结果中关联同一审查调用或命名请求。复用现有 trace、日志和 command execution 设施，不新增前端提示文案或设置。

| 信息 | 用途 |
| --- | --- |
| 审查 run/call ID，或命名 thread/request ID | 关联当前任务及外层结果 |
| 实际模型、provider、协议及模型请求序号 | 区分真实执行路由与初始配置 |
| tool_count、tool_names、has_text | 区分未调用、多调用、错误名称和夹带正文 |
| validation_code、具体错误、字段位置 | 区分数量、名称、参数和业务校验失败 |
| 工具选择策略、参数不支持的明确原因 | 确认本轮是否使用请求约束 |
| 纠正次数、剩余额度、最终处置 | 区分已纠正成功、耗尽、取消及被取代 |

仅有完整标准响应时记录工具数量和正文存在性；provider 在解析前失败时标为未知或省略，不能写成零调用而误导分析。计数区分业务模型请求与底层 HTTP 重试，不混用现有 command attempt 含义。

诊断不默认保存完整用户材料、模型正文、工具参数或私有推理；错误字段和摘要限长并按现有机制清理。中间纠正期间公开状态保持运行，最终成功或失败后再结束原活动；不为每次内部尝试新增前端任务条目。失败审查仍无 decision/reasons，不呈现为拒绝交付。

## 9. 实施顺序与验收

建议先补请求约束及适配器映射，再实现 Reviewer 和命名的有限次纠正，最后同步真实工具契约、提示词、日志与 TOOL.md。实施过程中保留现有取消、路由、写回及审查恢复边界。

| 验收情景 | 预期 |
| --- | --- |
| Reviewer 先给纯文本，下一轮合法提交 | 出现指导并保留上下文；最终成功，不先发布失败 |
| Reviewer 纯文本后继续读取或渲染 | 允许继续检查，历史图片和结果仍可见，没有强制提前提交 |
| Reviewer 提交缺少 reasons，下一轮修正 | 返回具体字段问题；合法修正后返回结论 |
| Reviewer 混用提交与检查、重复提交或调用禁止工具 | 整批不执行，每个调用有对应错误，可在额度内纠正 |
| Reviewer 连续或间隔发生超过两次协议违规 | 总纠正额度不重置，明确失败，无伪造结论 |
| Reviewer 超时、取消、上下文超限、源文件变化 | 按原业务边界终止，不靠纠正绕过 |
| Responses 与 Anthropic 命名请求 | 分别发送正确位置的工具选择与单次调用限制；未设置约束的调用方不受影响 |
| 命名第一次违规，后续合法 rename 或 keep | 写回或保留一次，保留同一请求身份；成功后不继续请求 |
| 模型明确拒绝工具选择参数 | 有依据地撤去不支持项，重发计入同一追加额度；仍严格校验工具提交 |
| HTTP 400 原因与工具选择无关，或发生鉴权/服务错误 | 不误判为工具选择不支持，不盲目移除参数 |
| 备用模型切换，或 Responses 需要 continuation | 使用实际模型适用的约束和正确上下文；无指纹错配、缺失工具结果或私有推理泄露 |
| 命名纠正期间新请求到达、手动改名或项目被替换 | 旧结果不写回，不重复运行 JEV，不覆盖新标题 |
| 协议失败及纠正后成功 | 日志能还原数量、名称、正文存在性和具体原因，公开状态与最终结果一致 |

这些状态转换和请求序列属于容易出错的逻辑，可在现有 Reviewer、命名、LLM 适配器与路由测试中补充少量高价值用例，复用 FakeProvider 和本地 HTTP 测试设施。将旧的“首次纯文本立即失败”断言更新为预算内纠正及耗尽失败；不要只删除负例。检查模型实际收到的消息、call ID 配对和 wire 参数，不能只验证内部字段赋值。
