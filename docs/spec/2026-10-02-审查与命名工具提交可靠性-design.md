# 审查证据与命令提交可靠性设计

日期：2026-10-02；2026-10-03 按用户决定将 handoff 接入同一机制。状态：代码已实施，真实模型与界面待用户手动验收。本文以最新用户决定替代原文保留 Reviewer 检查循环、仅 rename / review 纠正的要求。

## 1. 范围与边界

Reviewer 改为后端准备证据、模型单次评判并 submit_review、仅可修复的输出协议错误有限纠正。compact、commit、rename、polish、handoff、review 使用统一提交执行器，保留各自业务输入、提示词、校验和应用边界。

不修改 JEV、共享审查标准、主 Agent 创作循环或前端视觉设计；不增加任何超时、用户设置、旧结构兼容层或历史数据迁移。保留开发启动时已有的工作区改动。

## 2. Reviewer 证据准备

实际入口：`workflow.reviewArtifacts` → `prepareReviewMaterial` → `LLMTaskReviewer.Review`。5 分钟截止时间在准备开始时设置，模型纠正不能重新计时。

| 证据 | 实现 |
| --- | --- |
| 完整需求和后续纠正 | 当前 Run 的 reviewInstructions 与 JournalTranscriptStore 的权威 run.accepted、steering.accepted、question.asked / answered；后者不受 model.edit 压缩影响，按顺序保留原始文本、引用和问答含义 |
| 主 Agent 审查要求 | 原始 demand；指定审查目标、关注点和任务标准，不能覆盖用户要求 |
| 当前资源与必要源码 | 带路径、hash、size、binary 的完整当前源文件快照；文本保持完整源文，明确列出 manifest、outline、design、spec 是否存在，读取错误失败 |
| 累计改动 | Run 起点的持久化基线与当前快照的净差异，包括新增、修改、删除、二进制哈希和未经截断的 unified diff |
| 当前任务局部 diff | task_changes 提供当前 scope 的 HTML 变动及共享资源／依赖变动的实际局部 hunks；完整累计 diff 同时保留，不以统计取代源码差异 |
| 页面目录与截图 | 当前 outline 的全部页面及 HTML 存在状态；每个现存 HTML 页面提供当前截图，标签包含页码及 slide_id，缺失／过期／损坏时复用已注册的后端 render_slide 实现 |
| 上传材料 | 原始需求、纠正及主 Agent 已读取的附件去重读取；当前产品支持图片上传，按 attachment_id 标签提供原图真实图像块，不仅发送地址或元数据 |

源码快照遵循既有项目边界，排除 `.runtime`、`.git`、`.run`、`.commit-tmp`、versions；不静默跳过其他 authored 文件。读快照持有项目读锁。单文件上限 64 MiB、全部源码 128 MiB、全部图像 128 MiB；超限直接失败。

渲染仅准备派生证据，可覆盖编辑范围外的必要页面；局部 renderer scope 不改变主 Run 的写权限。派生渲染计入原 Run 工具计数，最多 128 次，不开放模型工具循环。执行／读取失败无审查结论；成功生成图像但检测到溢出等缺陷时，将有效图像和 render_diagnostic 作为缺陷证据，不能把渲染成功等同于通过。

图像字节在准备时冻结，后续纠正复用同一快照。evidence_version 覆盖需求、demand、scope、源码与图像哈希。每轮模型调用前后和最终接受前重新检查源码、渲染依赖（包括主题 CSS）及权威用户要求；变化、取消或过期时丢弃结果。任一必要材料读取失败或上下文超限明确失败，禁止裁剪证据或默认批准。

## 3. Reviewer 模型行为

唯一披露工具为 submit_review，接口支持时指定该工具并限制一次调用。正常路径一次 Generate；合法提交立即结束，无成功后的工具确认。

- 保留 approve / revise / refuse 含义与 core.quality 标准；每个 outcome 都需要非空 reasons。
- 保留原有提交边界：唯一工具调用必须为 submit_review；普通伴随正文不额外触发拒绝，但不被提取为结论。
- read_resource、read_image、render_slide 或其他未知工具均作为错误提交拒绝，绝不执行；整批失败结果与原 call ID 配对。
- 协议纠正不改变证据、demand 或审查标准，不指导模型必须 approve。
- REVIEW_FAILED 表示证据准备／模型执行失败，不伪装为 revise / refuse；取消保持原生命周期语义。既有 pending review 持久化与回执恢复继续保留。

## 4. 六类命令的共享提交执行器

`llm.SubmissionSession` 管理请求预算、校验反馈、工具约束策略、continuation 和诊断。业务校验函数是无副作用的；执行器仅返回最终合法响应。主 Agent 常规 ReAct 请求不经过该执行器。

| 响应／错误 | 处理 |
| --- | --- |
| 合法指定工具及业务字段 | 立即返回；调用方应用一次 |
| 漏工具、错误名称、多调用、非法字段、伴随正文违反本命令规则 | 原始 assistant 响应入上下文，每个 call ID 失败结果配对，再追加具体校验问题和 runtime 指导 |
| 缺失／重复 call ID、复用已配对 call ID 或 adapter 无规范化标准响应 | 不伪造 assistant/tool 消息，不从异常或正文提取结果，直接终止 |
| 不支持约束的明确机器错误 | 只撤掉对应不支持项，重发使用同一追加请求额度 |
| 鉴权、无关参数错误、普通服务故障、业务失败 | 不当作工具约束不支持；遵守底层网络重试和既有终止边界 |
| 取消、超时、上下文／输出预算耗尽、任务被取代 | 直接终止，结果不接受、不重复应用 |

首次请求之外整个命令最多 **2 次追加请求**。协议纠正和工具约束不支持后的重发共用额度。compact 的必要输入分批每批可以有基准请求，但全命令的追加额度和累计输出预算不重置；分批不是工具循环，全命令完成前不替换原始上下文。

累计输出预算沿用原设置：compact 4000、commit 1024、rename 128、polish 1024、handoff 6000、review 4096。每轮 max output 不超过剩余预算；用 provider usage 累计，缺 usage 用统一输出估算。上下文检查包含完整输入、工具输出契约、原始 assistant 响应、全部配对失败结果及指导。超限失败，不隐藏材料。

截止时间沿用：compact 45 秒，提交信息生成 45 秒，rename 20 秒，polish 12 秒，handoff 简报生成 45 秒，review 准备和评审共 5 分钟；全部纠正与底层网络重试共用截止时间。

## 5. Provider 映射与安全回放

Responses：`tool_choice: {type: function, name: <指定工具>}` 与显式 `parallel_tool_calls: false`。Anthropic：`tool_choice: {type: tool, name: <指定工具>, disable_parallel_tool_use: true}`；并行限制位于 tool_choice 内。

依据：[OpenAI Function calling](https://developers.openai.com/api/docs/guides/function-calling#tool-choice) 和 [Anthropic Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use#disable-parallel-tool-use)。本地最终数量、工具名及业务校验仍是结果接受条件。

未知能力先尝试请求约束。只有 HTTP 400 且机器 code 为 unsupported_parameter / unsupported_value / not_supported、param 明确为实际启用的工具选择或并行字段时，学习本任务内的不支持证据；泛化 invalid_request_error 或自由文本包含不足以证明不支持。策略按实际 provider、协议、model、端点 hash 生效，备用路由不沿用无关 continuation。

Responses 续传保留原始 assistant Content、ToolCalls、私有 opaque reasoning / phase 及指纹对应关系，错误工具也有 function_call_output；Anthropic 使用规范化 tool_use / tool_result 并将提交失败标为 is_error。runtime 指导置于失败结果之后，不伪装成新的用户业务要求。

## 6. 业务应用边界

- compact：全部必要输入分批和纠正成功后才提交最终摘要；失败保留源上下文。
- commit：先沿用 StageAll 准备隔离索引和待提交证据一次，模型纠正只重生成 title/items，不重新暂存；PrepareIntent、Commit 和回执位于最终校验成功之后，纠正不执行 Git 提交。已有命令回执和未知提交结果保护继续保留。
- rename：同一捕获路由与 snapshot，不重新运行 JEV；模型调用前后检查任务是否当前，最终写回继续检查取消、operation version、project generation 和自动命名状态，keep 为合法提交。
- polish：只返回完整合法润色建议，不执行草稿或改变主 Run；阶段不会随内部纠正回退。
- handoff：保持项目锁、已有上下文组装、最近两版简报及全部反馈输入。纠正仅重生成 title / content，遵循 48 字标题、40000 字完整简报与无普通正文的原校验；最终通过校验和取消检查后才调用 AppendBriefingVersion 一次。失败或取消不保存版本；生成不创建会话、不启动 Agent，前端新建会话按钮保持原流程。
- review：准备证据后单次评判，最终严格校验及一致性检查通过才返回结论；内部纠正期间只保持原活动运行。

## 7. 工具契约、提示词与诊断

同步实际 commandresult.Schema、命名工具、submit_review、/commit 的命令输出契约及命令／Reviewer 提示词。handoff_thread 复用 commandresult.Schema 的严格字段与输出契约，通过 SubmissionSession 继承指定工具、并行限制、Responses / Anthropic 纠正回放及命令／attempt 身份诊断。输入参数的用途与严格业务规则仍在真实 Tool Definition；输出契约区分有效提交的 no-reply 与 `{code, field, reason, next_action}` 失败反馈，经 ModelToolSchemas 投影到两种 wire description。[TOOL.md](/Users/wyw/Desktop/Projects/PPT-Agent/TOOL.md) 记录实际边界。

统一 submission_id 关联 command / attempt 或 review run / call；记录 Generate 次数、真实模型 HTTP 请求次数、底层网络重试、纠正类别／字段、剩余额度、模型和工具策略、累计输出与剩余截止时间、请求耗时、终止原因。仅日志机器错误类型、code、param、request ID，不保存 provider 可能回显私有正文的 message。

HTTP started / headers_received / body_received / transport_failed 耗时定位本地准备、连接／服务器等待和响应读取；model_requests / http_requests 都按实际发送计数，包含底层重试，generate_requests 单独统计执行器调用。命名总体日志同时标明准备／决策／提交／应用阶段及总耗时；评审准备与结束日志只保留数量、哈希、结论枚举和终止阶段，不记录 reasons 正文。此前单次 Generate 耗尽 20 秒的根因仍需实际新日志确认；没有旧日志证据就不认定为模型推理慢，不增大超时。

已核对 `.run/backend.log` 中 2026-10-02 14:48:05.616 的请求 `rename_rj4wkb`：旧版 naming submission finished 记录 model_requests=1（当时表示 Generate 次数）、corrections=0、unsupported_retries=0、disposition=timed_out，后续失败为 context deadline exceeded。没有 HTTP 次数、底层重试或阶段耗时，因此只能确认一次 Generate 到截止时间仍未完成，不能确定为模型推理慢，也不能把旧版 model_requests=1 解读为只发送一次 HTTP。新日志使用 generate_requests 明确区分。

## 8. 定向检查与手动验收

高价值用例覆盖完整需求跨压缩、当前源码和实际图像、截图补齐与复用、正常单次提交、混用工具整批拒绝、Responses opaque / Anthropic 错误配对、共享追加额度和输出预算、取消／上下文／不可安全回放边界、命名被取代、评审期间源码或用户要求变化，以及 commit 校验后的唯一 intent／回执复用。

handoff 定向用例补充正常单次提交、修订上下文与全部反馈保持、多调用失败逐一配对、continuation 及累计输出预算、两次纠正额度耗尽、初次及纠正调用的取消后迟到结果丢弃，并验证仅最终合法简报保存一个版本。

仅运行改动相关的定向检查，不运行全量测试。FakeProvider、进程内 HTTP transport 和本地 httptest 不调用真实模型；不运行浏览器／Chromium 验收或使用子代理。真实模型与界面由用户手动验收：确认正常审查只请求一次且没有 read/render 循环，格式失败在两次额度内结束，取消／新输入后的旧结果不应用，命名新日志能区分 Generate 与 HTTP 耗时。
