# Jev 后端接入、会话命名、Run 工具裁剪与内容预检

日期：2026-09-29。

状态：已按本文实现首版接入，待用户手动构建、运行测试和验收。已执行用户授权的一次真实 API 连通性请求；该结果只证明端点、密钥及三类问题可用，不代表业务判断效果已验证。

## 1. 决策摘要与范围

本次确认接入三个能力：

| 场景 | Jev 类型 | 调用位置 | 产出 |
| --- | --- | --- | --- |
| 是否自动重新命名会话 | `noul` | 独立命名服务 | 是否另行发起一次生成标题的模型调用 |
| 本次 Run 的工具裁剪 | `choice` | 首次主模型调用之前 | 本次 Run 固定的工具能力清单 |
| 编辑成功后的内容预检 | `score` | 一次主模型响应的工具批次结束后 | 各修改页面最终版本的内容评分 |

共同约定：

- Jev 的问题、评判标准和输入由后端组装，不由主 Agent 生成，不新增通用 `ask_jev` 工具。
- 新增独立决策接口；首版使用 Go 标准库调用 TypeSafe HTTP API，不复用 `llm.Provider.Generate` 的生成协议。
- `backend/config.yaml` 新增顶层 `jev`，仅有 `base_url / model / key`；不放入 `llm`，不增加 `provider`，不参与主旁路模型选择。
- 自动命名与主 Agent 解耦，移除 rename 在创作时间线中的展示。生成标题仍使用现有命名旁路模型。
- 工具裁剪一次确定，不在普通工具循环中重新评估、反复开放或收回工具。
- 内容预检评价成功落盘的成果；低分或预检失败不能把已经成功的编辑改为失败。
- 本期不做资源重排、Skill/组件推荐、自动选择主模型、通用 Hook 平台或额外的强制完成门禁。
- 保留现有成果 Reviewer 的读取、渲染、视觉审查及原因说明能力。Jev 内容评分不替代视觉验收。

本文的阈值、超时和重试次数没有真实样本依据，不写入看似已验证的数值。实现时使用集中维护的内部策略，并通过定向评估确定数值；配置文件不因此增加字段。

## 3. 配置与生命周期

### 3.1 唯一配置形式

```yaml
jev:
  base_url: https://api.typesafe.ai/v1
  model: jev-1.13.0
  key: <API_KEY>
```

- `base_url` 是完整 API 前缀，客户端只追加 `/systemone`。规范化尾部斜线，拒绝重复填写完整端点、内嵌凭证、查询参数和 fragment。
- `model` 原样发送；建议固定版本，记录响应中的实际版本，避免别名升级后阈值含义悄然变化。
- `key` 仅在服务端读取，不进入公开设置、日志、工具结果、时间线或检查点。
- 三个业务场景共用一个 Jev 配置。各自的问题、阈值和时间预算由代码管理。
- 整个块省略表示未启用；块存在时三个字段必须完整且有效，空对象或部分字段不视为禁用。
- 不接受旧 `decision` 顶层配置，也不引入环境变量密钥回退或双读路径。

### 3.2 配置文件读写边界

当前解析器启用了 `KnownFields(true)`，直接在 YAML 中加入 `jev` 会失败；当前模型设置保存也可能丢弃未建模的顶层字段。因此必须一次性调整配置文件聚合结构、解析、保存和刷新流程。

建议把“整个文件配置”和“LLM 路由配置”分开建模。保存 LLM 设置时从已加载的完整文件快照更新 LLM 部分，保留 Jev 配置；继续使用现有 revision、磁盘变化检测和原子写入，不用忽略未知字段的方式绕过问题。

Jev 不出现在 LLM 卡片、聊天模型下拉或主旁路分配中。本期不新增 Jev 前端配置面板；文件刷新沿用现有明确刷新入口，不增加文件监听器。

### 3.3 快照和恢复

- 新 Run 在启动时取得 Jev 不可变配置快照；独立命名任务在实际启动时取快照。
- 运行中设置变化不改写在途调用。LLM 和 Jev 分别记录内部配置身份，避免仅修改 Jev 导致无关的 LLM 路由身份变化。
- 工具裁剪的已完成结果写入检查点；同一 Run 恢复时直接使用，不重新请求 Jev。
- 已完成预检按材料身份复用。跨进程恢复无法重建原 Jev 配置时，未完成预检标为不可用，不偷偷使用另一配置打分，不影响已经成功保存的页面。
- 不在检查点保存密钥，也不建设历史密钥快照仓库。

## 4. 决策接口与 HTTP 客户端

### 4.1 包结构与核心接口

建议新增：

```text
backend/internal/decision/
  provider.go       Provider、Request、Response、Usage
  question.go       Noul / Choice / Score 请求类型和校验
  answer.go         对应响应类型、解码和校验
  typesafe.go       TypeSafe HTTP 实现
  errors.go         决策调用错误分类
```

接口草案：

```go
type Provider interface {
    Evaluate(ctx context.Context, req Request) (Response, error)
}

type Request struct {
    State     any
    Questions map[string]Question
}

type Response struct {
    Model   string
    Answers map[string]Answer
    Usage   Usage
}
```

`Question` 和 `Answer` 分别用三个具体类型表达，避免业务代码到处对 `map[string]any` 做强制转换。State 和 Instructions 支持可序列化的结构化值；Choice 标准是选项对象，Score 标准是有序数组，Noul 标准是可选 true/false 对象。标准描述也保留官方支持的结构化形式，不仅限于字符串。

模型、地址、密钥绑定在客户端配置中。一次 Evaluate 可以混合三类问题，不能将每个问题自动拆成单独 HTTP 请求。提供按 ID 读取且校验类型的 Noul、Choice、Score 方法；缺失字段和数值零必须可区分。

首版使用 `net/http`、`encoding/json`。不为了使用 SDK 增加 Python/Node 服务或升级 Go；不提前建设通用供应商注册框架。未来替换社区 SDK 时，只替换 Provider 实现，不让第三方类型进入业务接口。

### 4.2 请求与响应合同

调用 `POST <base_url>/systemone`，Bearer 鉴权，发送 `model / state / questions`。

| 类型 | 请求 criteria | 响应 |
| --- | --- | --- |
| noul | 可选 true/false 对象 | type、noul |
| choice | 选项标识到说明的对象 | type、choice、probabilities、confidence |
| score | 2–10 个有序等级描述 | type、score、legend、probabilities、confidence |

问题 ID 仅用于对应返回，不参与模型语义判断；每个 Instructions 必须完整说明任务。所有问题共享 State，各问题彼此独立。某问题的输出不能在同一次调用中作为另一问题的输入。

客户端校验请求与返回的 ID、类型、必需字段、候选选项、等级范围及概率分布。不能把缺失答案解码为零，也不能把 HTTP 200、空 answers 或错误类型当成有效业务判断。批量业务结果按问题区分：某页材料缺失或某项答案不合法，不得伪造对应评分或让其他已完成编辑变成失败。

Score 保存原始档位分数、等级、概率分布和 confidence；若展示归一化值，应显式给出换算标准，不把它包装成测量得到的百分制质量。

### 4.3 时间预算、错误与记录

- 使用调用方 context 控制整个调用，包括排队和重试；取消后不再继续请求。
- 短暂网络错误、限流、服务过载允许有界重试，遵守 Retry-After，并受总预算约束。只有客户端负责网络重试。
- 参数、认证和协议合同错误明确返回，不通过无限重发掩盖。
- 不直接复用生成客户端默认 180 秒超时和 5 次重试。工具裁剪位于主路启动前，应有独立的较短总预算；预检和后台命名分别控制预算。
- 记录用途、请求身份、实际模型版本、问题/策略版本、耗时、用量、结果和失败类别；不记录密钥，不默认把完整 HTML 或原始会话复制到日志。
- “语义不确定”“未启用”“调用失败”“用户取消”分别表达。主 Run 被取消时立即停止，不以业务保守处理为由继续下一次模型调用。

## 5. 会话命名：独立 Noul 判断

### 5.1 流程

```text
新的有效用户输入 / 命名触发
  → 后端检查自动命名开关与任务版本
  → 组装当前标题和近期活动
  → Jev Noul 判断是否值得更新标题
  → 达到命名阈值：发起一次独立标题生成调用
  → 校验标题与任务版本后更新会话
```

Noul 问题围绕“当前标题是否已无法准确概括近期用户主题或工作阶段，值得更新”，不把一次小修改或完成百分比变化当成必然改名。

State 使用当前标题、最近用户需求与修正、少量最终回复和简短进度，不发送全量主 Agent 对话、工具日志或项目源码。复用现有命名输入投影；以近期实际任务为中心。

自动触发可以保留合并、去抖和并发控制，但原有“输入达到数量后直接请求生成模型”的路径须改为经 Jev 判断。仅有一个命名生成调用，不添加生成模型的 Agent 工具循环。

### 5.2 特殊情况和生命周期

- 默认标题的首次命名可由明确规则直接进入生成步骤；这属于已知初始状态，不必增加一次语义判断。
- 用户主动请求生成名称直接生成；用户直接提供名称直接保存，均不受自动判断拦截。
- 手动命名、关闭自动命名、较新任务或回滚使旧任务失效时，同时使在途 Jev 判断和标题生成结果失效。
- 保留现有 operation version、project generation、待办合并、取消和迟到结果保护。Jev 返回后、生成返回后都检查任务是否仍有效。
- 未启用、调用失败或概率不足时保持现名；不退回旧的定期生成路径。首次命名和主动命名仍可使用生成模型。
- Jev Noul 没有 confidence 字段，命名策略使用其 noul 值。阈值是业务内部策略，不是客户端逻辑。

### 5.3 与主 Agent、时间线的边界

主 Agent 无需知道命名判断或命名结果，不把命名调用加入主模型工具表和主执行历史。专用命名模型仍可用 `rename_thread` 作为结构化结果提交协议。

rename 不再生成创作时间线活动，包括正在命名、完成、失败或保留原名。后台命令/诊断记录可继续用于恢复、取消和问题排查；标题更新通过会话更新事件同步。用户主动操作的反馈放在对应入口。

后端公共事件投影、前端实时 reducer 与历史 hydration 必须同步调整，保证刷新前后表现一致；不通过只隐藏某个组件实现表面解耦。

## 6. Run 工具裁剪：首次主调用之前一次确定

### 6.1 候选能力与问题

当前裁剪四组能力，共五个工具：

| 能力 | 工具 | 判断重点 |
| --- | --- | --- |
| 内容要求编辑 | edit_manifest | 任务是否需要改变整份演示的目标、受众或内容要求 |
| 视觉要求编辑 | edit_design | 是否需要改变全局视觉要求，而非仅单页布局 |
| 目录编辑 | init_outline、arrange_outline | 是否需要新建、增删、重排页面或调整章节、标题 |
| 项目版本提交 | git_commit | 用户是否要求创建 Git 提交或保存项目版本，包括编辑完成后提交；普通编辑或仅保存文件不等于 Git 提交 |

`edit_spec`、`write_html`、`patch_html` 不按 edit 前缀一并裁掉。基础读取、渲染、主任务控制能力继续按当前模式和真实权限提供。

每组能力一个 Choice，在同一请求中并行判断。类别使用：

- `needed`：完成本次完整任务明确需要该能力。
- `possible`：存在合理的后续步骤可能需要，或材料不足以排除。
- `not_needed`：当前任务明确不涉及该能力。

“不可能用到”在合同中表述为“本次不需要”，避免对未知执行过程作绝对预测。判定的是完成任务所需能力，不是预测主 Agent 下一步会选哪个工具。

State 包含完整本轮任务、必要的近期修正、当前内容与视觉要求、目录状态、模式、选页范围和已确认的任务上下文。“继续”等短句必须解析到已有任务背景后再判断。

`git_commit` 使用独立问题 ID `commit`，不与内容、视觉或目录编辑绑定。保留该工具仍须遵守用户提交意图和现有执行校验，不意味着每次编辑都自动提交，也不授予远程推送能力。

### 6.2 保留和裁剪策略

只在 `choice == not_needed` 且分布与置信度达到保守裁剪要求时移除；needed、possible、不确定、缺失或失败均保留原本允许的候选能力。分类为 possible 与分布不确定是两个不同信号。

先按模式和授权生成基础工具集合，再做 Jev 裁剪。Jev 不能授予原本不存在的权限，工具参数、页面范围、读写及提交校验仍由 Runtime 执行。

按能力分组补齐依赖。目录不存在并不意味着整个 Run 都不需要 arrange_outline；允许目录编辑时，要为初始化后的调整保留必要工具，运行时检查实际前置条件。

### 6.3 固定性、快照与恢复

启动阶段执行一次 Jev 判断，在首次主模型调用之前保存：任务输入身份、Jev 实际模型、策略版本、各能力判断、最终能力/工具清单及保守处理原因。

- 同一执行合同内，模型的所有调用使用固定清单，不按工具结果或预检分数动态扩缩。
- 默认工具 registry 因项目状态刷新时，重新应用同一清单，不能重新注册后把裁掉的工具带回来。
- 模型披露与执行时校验使用同一清单；模型历史里曾出现的名称不能绕过当前清单。
- 同一 Run 暂停、恢复、继续时沿用已保存结果，不因为 Jev 配置变化重新判断。
- 所有写入仍受模式和范围约束；固定能力清单不等于冻结页面 ID，也不替代合法的页面范围扩展流程。
- 本期不增加 request_capabilities 或循环中的重新开放机制。

工具固定以同一任务、同一模式的执行合同为边界。新增要求仍能由原清单完成时继续执行；需要被裁掉的能力时，不暗中修改清单或换一条写入路径绕过，而应明确说明并以新 Run 重新判定。规划进入执行须按新的执行合同在首次执行模型调用前确定工具集合；实现时对齐现有模式转换入口，不让规划阶段获得写权限。

工具裁剪首先用于减少无关工具干扰，不宣称构成资源级安全隔离。现有 run_command 等写路径必须继续遵守既有权限；若将来要禁止某类资源修改，需要另行定义资源级策略，不能仅靠隐藏工具实现。

## 7. 内容预检：成功编辑后的批次 Hook

### 7.1 明确定义批次

批次是“一次主模型响应返回的全部工具调用”，不是整个用户请求或整个 Run。

```text
主模型返回多个编辑调用
  → 逐个执行、校验、提交
  → 收集本批真正成功落盘且内容有变化的页面
  → 同页去重，读取批次结束时的最终成果
  → 一次 Jev 请求提交多个页面/维度问题，容量不足则拆批
  → 持久化结果并组合工具观察
  → 下一次主模型调用
```

首版为 Runtime 内部专用 Hook，不增加可配置的通用 Hook 框架。主 Agent 不需要主动调用预检工具。

### 7.2 成功边界与页面收集

- 以 CommitOperation 成功后的实际变更为依据，不能只看领域工具内部的 OK。
- 本期主触发为成功修改 HTML 的 write_html、patch_html；其他已识别的页面 HTML 写入也进入相同收集逻辑，避免仅按工具名遗漏成果变更。
- 同页多个编辑只评价最终快照；失败、跳过、无实际变化的调用不制造额外评分。
- 批次后续失败不否定前面已提交的修改；仍评估成功落盘的页面最终状态。
- 仅修改 spec 而未修改 HTML 时，不把旧 HTML 自动当成本次已实现成果；其旧评估因 spec 改变而失效，等待 HTML 更新或独立审查。
- 页面删除后不评估；新页只有 spec、没有 HTML 时不产生页面实现分数。
- 全局要求、相关页职责或评判标准改变时，使受影响旧分数失效，但不在每次全局写入后自动重评整份演示。

### 7.3 材料与问题组装

State 放共享用户要求、最新纠正、内容要求、全局评判原则，以及需要的目录职责信息。每个问题的结构化 Instructions 放该页的 spec、HTML/内容投影和本题检查维度，明确所引用的字段。

HTML 是待检查材料而非指令来源。可提取标题、段落、列表、表格、必要的 SVG 文字及相关结构，减少无关 CSS、脚本和编码图片。需要的原始片段可以保留；材料缺失或超限必须明确，不静默截断后给出完整检查的结论。

以原始用户要求及后续纠正为最高依据，不能只比较可被 Agent 一起改写的 manifest、spec 和 HTML 是否相互一致。spec 用于解释页面意图，不能作为 HTML 已实现该内容的证据。

每个 Score 只评价一个维度，首版建议采用：

- 内容覆盖：实际页面内容是否完成该页在本次任务中的职责。
- 表达清晰：是否有明确结论、组织关系与可理解的表述。
- 需求一致性：实际内容是否符合当前有效要求；涉及保留内容的任务需提供修改前材料。

资料支持性只有在具备来源材料时才能评价；没有来源不返回看似通过的事实分数。图像内文字、图表渲染、溢出、遮挡和整体审美不由文本分数证明。

每个维度使用 2–10 个具有明确含义的等级；不使用只有数字或“差/中/好”而无业务定义的标准。共享原则可放 State，Score 的 criteria 仍由后端为每道问题填入实际等级数组。

问题 ID 由后端映射回页面与维度，不能仅靠 ID 告诉模型正在评哪页。跨页重复或叙事衔接需要单独提供相关页面材料和问题，不能从单页均分推出整份演示质量。

### 7.4 模型观察与业务结果

建议在该页最后一次成功编辑的模型可见结果中附加 content_precheck，早期编辑结果不附加后续版本的分数。下面为业务包装示例，数值仅用于说明字段：

```json
{
  "ok": true,
  "changed": true,
  "content_hash": "sha256:...",
  "content_precheck": {
    "status": "completed",
    "assessment_id": "assessment_...",
    "scores": {
      "coverage": {
        "score": 2.0,
        "max_score": 3,
        "confidence": 1.0,
        "probabilities": {"0": 0.0, "1": 0.0, "2": 1.0, "3": 0.0}
      }
    }
  }
}
```

建议状态为 completed、unavailable、skipped、stale，并附后端生成的状态原因；具体字段在实现时统一到模型观察、事件和存储合同中。示例中概率集中于一个等级不代表结论一定正确；实际分数也可以是档位之间的小数。

分数含义随版本化标准提供，主 Agent 据此判断是否修订。不要求 Jev 生成自由文本原因，也不把 Score 误当作布尔结论。若后续需要通过提示，可以计算合格档位的概率，但仍需保留关键维度，不能让均分掩盖明显缺陷。

预检不可用时，编辑结果仍为 OK，只标记该预检未完成。低分不触发自动回滚，不计入工具连续失败次数，不新增强制 finish 门禁，不要求主 Agent 为追分无限重写。现有预算、重复读取检测和成果审查继续生效。

### 7.5 持久化、去重与恢复

评分身份至少关联：页面 ID、最终 HTML 指纹、spec 指纹、有效用户/内容要求指纹、相关上下文、问题和标准版本、实际 Jev 模型版本。仅 HTML 相同不足以复用评分。

当前原始工具结果会在提交时持久化，而评分发生在提交后。保留不可变写入回执，另存预检记录，再按引用组合模型观察与公开结果，不能覆盖旧提交回执或事后伪装成提交前已经获得评分。

建议预检记录保存于项目内部运行数据，并在检查点引用；具体采用既有 journal payload 或专用内部文件时需选定唯一存储源，不同时保存多份权威结果。需支持：

1. 编辑提交后、请求 Jev 前记录待评页面及材料身份。
2. 请求完成后校验材料仍匹配，再保存结果并投递模型观察。
3. 恢复时复用已保存结果，不为补评分重放任何编辑。
4. 中断且没有结果时，在原配置可重建、材料未变且有预算时重新评估；否则明确 unavailable/stale。
5. 取消主 Run 后不继续评分或主模型调用，已经保存的成果保持原状。

首版等待本批预检的有界结果后再进入下一次主模型调用，保证反馈可见。编辑保存成功可以先反馈给界面，预检状态随后补充；两者不能产生重复终态或把保存中显示成尚未落盘。实时结果和历史恢复读取同一份预检记录。

## 8. 调用失败、未启用与效果边界

| 场景 | 未启用或调用失败 | 语义不确定 |
| --- | --- | --- |
| 自动命名 | 保持当前标题；首次/主动命名按明确规则处理 | 保持标题 |
| 工具裁剪 | 保存未裁剪的合法基础清单，正常启动 | 保留对应能力 |
| 内容预检 | 已成功编辑不变，预检标记 skipped/unavailable | 保存分布和置信度，不宣称质量过关 |

这是新功能的失败处理，不是旧协议兼容层；不保留重复的旧命名决策、旧 Jev 配置或双份结果协议。

Jev 判断会出错。中文指令、简短续接、局部与全局修改的区别都要用真实项目样本评估。分类置信度不是正确率承诺，分数高不是视觉或事实正确性的证明。模型或标准版本变化后重新核对阈值，不能直接继承已调出的数值。

## 10. 有价值的验证与人工验收

不以覆盖率为目标，不编写大量逐字段镜像测试。重点覆盖可观察的错误与恢复边界：

1. 混合问题正确匹配返回；缺失结果、错误类型、合法零值与非法候选可以区分；结构化 Instructions/criteria 正确传递。
2. 取消和超时覆盖重试等待；重试不乘法叠加；错误不泄露密钥；未启用与配置错误可区分。
3. 保存、刷新 LLM 设置不会丢掉 jev；在途快照不被新设置改写。
4. Jev 拦下自动命名时不调用生成模型；达到条件时只进行一次生成；手动命名后旧结果无法覆盖。
5. 工具判断在首次主模型调用前完成；普通轮次、registry 刷新、继续运行不改变清单；不确定时不会误删能力。
6. 同批同页多次写只评最终版本；部分失败仍能评成功页面；提交失败、无变化、没有 HTML 不产生虚假实现分数。
7. 预检失败保持编辑成功；结果迟到、材料变化、恢复与配置变化不会附上错误版本评分，也不会重放写入。
8. 实时与刷新后的时间线都不出现 rename 活动；编辑状态、预检状态和 Reviewer 结论互不冒充。

真实模型评估重点：自动命名误触发率、必要工具误裁剪率、内容评分与人工判断的一致程度、中文表现、首响应额外耗时、每批预检耗时和整轮成本。工具裁剪可先以同一批样本记录建议清单，确认不会频繁隐藏必要能力后启用实际过滤；这属于评估步骤，不增加永久配置字段。

实现阶段遵守 AGENTS.md：未运行构建、测试或浏览器自动化；仅执行用户明确授权的一次真实 API curl。未提交或推送 Git，应用行为由用户手动验收。

## 12. 首版实现记录与手动验收入口

实现日期：2026-09-29。未运行构建或测试，以下是代码中采用的初始策略，不是经真实业务样本校准的指标。

- `internal/decision` 提供独立 Provider、三类问题/答案和 TypeSafe HTTP 客户端；无新增第三方依赖。允许混合问题，部分无效答案按 ID 隔离；缺失值不能当成零。
- 整个 YAML 文件用 `config.FileConfig` 聚合，`JevConfig` 与 `LLMConfig` 分开。模型设置保存保留 `jev`，刷新同时发布新快照；仅变更 Jev 不改变 LLM 路由指纹。`config.example.yaml` 提供可取消注释的配置示例；真实密钥仅在本地 `backend/config.yaml`。
- 命名初始阈值为 `noul >= 0.85`，判断预算 3 秒。每个去重后的有效新输入进入判断，工作线程合并待办并取消已被新输入取代的调用；空标题首次命名与手动生成绕过判断。生成标题仍使用原命名旁路。
- 工具裁剪初始条件为 `choice == not_needed && P(not_needed) >= 0.95 && confidence >= 0.85`，预算 3 秒；内容、视觉、目录、Git 提交四个能力合并一次调用，策略版本为 `global-tools-v2`。模式转换形成新的执行合同，同一执行合同的 registry 刷新/恢复沿用检查点里的工具清单；新增裁剪项从新执行合同开始生效。
- 取消了目录文件存在性导致的动态工具列表切换；开放目录能力时同时保留 init_outline/arrange_outline，并用 `task/outline_exists` 告知当前文件状态。执行时仍拒绝重复初始化与不存在目录的编辑。
- 内容评分使用 coverage、clarity、alignment 三个独立维度，每维 4 档，原始分数范围 0–3。单个分片预算 8 秒、整个工具批次最多 15 秒；每个 HTTP 请求最多 2 次尝试，并遵守 Retry-After 和调用方取消。
- 没有官方分词器时，以保守 UTF-8 JSON 字节预算打包：state 加最长问题不超过 28,000 字节，state 加所有问题不超过 56,000 字节。它们是内部保护值，**不是官方 token 限额**；超限拆批或标记 unavailable，不静默截断。
- HTML 提取文本与结构边界，排除 script/style、显式 hidden 等内容；同时提供批次前内容和可用的 Run 初始快照，以支持保留内容的要求。CSS 布局、图片内容和事实核实仍由其它审查能力负责。
- 评分文件唯一存放于项目 `.runtime/content-prechecks/`；检查点保存批次待办、原材料身份及结果引用。原写入回执保持不变，恢复只读取回执；未获得提交回执的调用按中断处理，不重放编辑。
- 编辑终态先发出；`tool.content_prechecked` 作为补充事件携带评分或 stale/unavailable 状态，不再产生一次工具终态。前端实时 reducer 与历史 hydration 共用同一结构；后端投影通过 assessment_id 读取权威记录。全局要求、spec 或 HTML 变化后旧评分失效，不自动重评整套页面。
- 命名事件退出创作时间线。手动命名入口通过独立命令查询获取结果，标题通过原会话更新渠道同步。

已完成的 API 连通性请求：一次 curl 同时提交 noul/choice/score，返回 HTTP 200、`model=jev-1.13.0`，三类结果齐全，usage 为 input_tokens=374 / output_tokens=61。请求内容仅为简短连通性样例。

建议按以下顺序手动验收：

1. 启动后端，确认顶层 jev 可读取；在模型设置中保存一次并刷新，确认 Jev 配置仍在，且不出现在 LLM 模型列表中。
2. 新建空标题会话并输入需求，确认能命名；继续小改动与切换主题，检查是否合理保留/更新；手动命名及关闭自动命名后确认旧结果不会覆盖，刷新前后时间线均没有 rename。
3. 分别请求单页文案修改、全局设计修改、目录创建/调整、编辑后创建 Git 提交，查看 `decision.tools` trace 的四组判断；普通编辑应能裁掉 git_commit，明确要求提交应保留，含糊或失败时保守保留。检查点的 allowed_tools 在普通轮次和继续执行后保持固定，裁掉的 git_commit 不能通过旧工具名调用。
4. 一次响应编辑同页两次及多页各一次，检查每页只出现最终快照的三个维度；制造一次后续工具失败，确认之前已保存页面仍有预检结果。
5. 临时配置错误密钥并刷新，确认工具裁剪保守放行、评分 unavailable，但已经成功的编辑保持成功；恢复原配置后新 Run 使用新快照。
6. 修改 spec/内容要求而不改 HTML，确认原评分变为 stale 且不自动重评；中断批次预检后继续，确认复用持久化结果或明确不可用，不重放写入。
7. 运行新增的定向行为用例：decision 混合答案与取消重试、config/llm 配置保存快照、service 命名判断、workflow 固定工具/最终快照评分/恢复，以及前端 SSE 和历史投影相关用例。

待人工评价：中文命名误触发、必要工具误裁剪、评分与人工判断的一致性、首响应与批次评分延迟。数值策略应依据这些结果调整。
