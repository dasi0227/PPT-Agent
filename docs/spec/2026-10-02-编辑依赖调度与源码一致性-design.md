## 1. 目标与范围

解决编辑失败后的无关调用被跳过，以及保存时格式化导致 Agent 的编辑依据与实际源码不一致的问题。

本次开发覆盖批量编辑调度、调用事务隔离、源码保存与展示、版本冲突反馈、工具及系统提示词。成果审查、自动重命名、Jev 调用策略不在本次范围内。需求直接在本文维护，不新建 TODO.md；实现时同步实际工具协议到 TOOL.md。

## 2. 已确认的行为

| 场景 | 目标行为 |
| --- | --- |
| 不同页面，仅修改各自 HTML | 可并发，一页失败不阻断另一页 |
| Outline、Design、Manifest 三种资源之间的独立修改 | 可并发；不存在仅因它们是全局资源而形成的串行依赖 |
| 同一资源的连续修改 | 按调用顺序执行，前序失败则跳过依赖它的后续修改 |
| 某页 Spec 修改后再修改该页 HTML | HTML 等待 Spec 成功，其他页面仍可独立执行 |
| Manifest、Design 修改后再创作页面 | 后续依赖新要求的页面编辑等待前置修改成功 |
| Outline 新建或删除页面 | 协调受影响页面的 Spec、HTML 与稳定 ID；不得视为只写一个独立文件 |
| HTML 保存 | 后端保留提交或精确替换后得到的原文；前端只对展示副本格式化 |
| 结构化 JSON 保存 | 保留统一序列化和版本校验；按字段更新不等于没有并发冲突 |
| 版本冲突 | 拒绝覆盖，明确说明资源、原因及重新读取的方法 |

“并发执行”不要求多项磁盘事务同时提交。独立调用可以并发准备与校验，最终提交必须安全、原子、可恢复。

## 4. 批量调用的依赖与调度

### 4.1 执行前分析

在 Runtime 中根据实际工具参数、当前资源状态和原始调用顺序建立调度计划，不增加一次模型调用，也不要求 Agent 传递 `depends_on` 或哈希参数。

每个调用至少识别：原始索引、call ID、读写的逻辑资源、实际涉及的文件、必须成功的前置调用、仅需等待结束的冲突调用。

逻辑资源包括 `manifest`、`design`、`outline`、`spec/<slide_id>`、`html/<slide_id>`。物理文件范围还应包含 `.spec.json` 集合，以及 Outline 删除页面时涉及的 HTML 文件。

预检可以在内存中分析候选内容，但不得提前保存、消费正式新 ID、自动改写 Agent 参数或合并可能改变语义的编辑。预检通过不替代执行、提交时的版本和业务校验。

### 4.2 两种等待关系

- **成功依赖**：后续调用需要前置修改生效。只有前置调用完成持久化提交，才算成功并可放行；失败时递归跳过其依赖调用。
- **顺序或互斥约束**：调用共享存储或需要保持读写顺序，但没有内容上的成功依赖。等待前项结束、重新取得正确基线后继续；不得把前项失败自动传播过来。

例如，不同页面的 Spec 都写 `.spec.json`，需要协调存储，但 A 页 Spec 失败不应直接导致 B 页 Spec 被跳过。

### 4.3 依赖规则

1. 同一逻辑资源的连续编辑按原始调用顺序建立成功依赖，不凭字段不同自动并行，不自动合并调用。
2. 前序 `edit_spec(A)` 是后续 `edit_html(A)` 的成功依赖，不向 B 页传播。
3. 本次使用保守的资源粒度：同批次前序 `edit_manifest`、`edit_design` 是后续 `edit_spec`、`edit_html` 的成功依赖，不另用模型推断某个字段是否影响视觉。成功但无实际变化也视为前置成功。
4. `edit_outline`、`edit_design`、`edit_manifest` 之间不因工具名称建立相互依赖；各自已有明确参数、无需另一个调用返回值时，可以进入同一并发组。
5. Outline 的影响应从实际节点变更识别。涉及新建、删除、稳定身份或调用所需的新结构时，受影响页面调用依赖 Outline；已确认不受影响的页面不被统一阻断。
6. 无法可靠识别某项 Outline 编辑的实际影响时，相关页面操作保守串行并继续进行成员与版本检查；不得由此阻断独立的 Manifest、Design 调用。依赖新增稳定 ID 的调用必须等 Agent 收到成功返回值后，再在下一轮生成参数，不猜测 ID。
7. 普通读取可等待同资源写入结束后读取当前状态，用于诊断和恢复，不因前一次写入失败就被统一跳过。用于检查某次成功修改的渲染，应等待对应写入提交。
8. 不把新规则扩大到控制工具、审批、Git 提交等生命周期；这些操作保留既有门禁。无法准确分析的写调用不得直接进入并发池。

依赖边沿原始调用顺序建立。不得为了并发，将 Agent 已提交的旧参数重新解释为对尚未发生的新状态进行编辑；需要前置返回值才能确定的参数应留到下一轮。

### 4.4 调度与失败隔离

- 就绪的独立创作调用使用有界并发，初始上限为 3，复用现有并发执行基础，不增加用户设置。
- 在成功依赖满足后才能取得用于执行的资源视图。冲突资源依次处理；独立分支无需等待无关分支结束。
- 一次调用中多个 `edits` 仍按数组顺序应用，全部匹配、校验成功后原子保存；一项失败则该调用不保存部分结果。
- 一次调用执行或提交失败，仅回滚该调用；其依赖调用返回 `DEPENDENCY_FAILED`，说明失败的前置 call ID、工具及资源。独立成功调用不得被撤销。
- 工具结果保持原始调用顺序及 call ID 对应关系；开始、结束、跳过、重放事件与实际行为一致。未执行调用不得显示为成功写入。
- 依赖跳过不计作新增的实际编辑失败，不额外消耗修复预算。

## 5. 并发事务与版本传播

### 5.1 每次调用独立暂存

将创作工具的暂存事务改为按调用隔离。并发 worker 不得共同写入 `state.tx` 的 `artifacts`、`generationInputs`，也不得并发修改 Runtime 的上下文、工作状态、工具注册表、已知版本和汇总变更。

调度器给调用提供明确的资源与上下文视图，worker 返回暂存变更和候选结果。协调器负责提交及共享状态更新。成功结果只能在持久化提交成功后发布。

### 5.2 提交与共享集合

- 同一项目的最终提交由统一临界区协调，覆盖基线复核、持久化日志、文件写入、元数据提交及失败回滚，避免检查后到写入前被另一写入穿插。
- 审查并协调本次相关的前端管理编辑等项目写入口，不能仅保护 Agent worker 而允许另一个应用内写入口绕过相同提交保护。外部直接改盘仍由基线检测尽可能发现，不声称能够锁住任意外部程序。
- 保留单次调用原子性、稳定 call ID、持久化回执和恢复机制；重放已提交调用不得重复写入。
- 对 `.spec.json` 的读、合并、暂存、提交设置存储互斥。首版按该物理集合串行准备和提交，避免两个 worker 各自基于旧全集构造覆盖内容；无需新增按字段自动合并机制。
- Outline 删页清理与受影响 Spec、HTML 写入共同参与资源协调，相关删除作为同一调用原子提交。
- 资源无语义变化但文件排版被其他写入口改变时，结构化 JSON 操作可重新读取并验证内容哈希后建立新基线；不得把旧物理文件快照直接覆盖回去。文本操作不能采用这种语义等价替代。

### 5.3 Agent 已知版本

- 只有已返回的真实资源内容，或模型已知输入能够确定的成功写入结果，才能推进该资源的已知版本。不能因为 Runtime 内部读取了一个新版本，就声称 Agent 已经看过。
- 版本只能在成功提交后推进；失败、跳过、提交失败不能推进，也不能使无关资源失效。
- 同批次同资源的后续调用，如果其编辑基于可确定的前序成功结果，应使用该结果对应版本，不能一直复用批次开始时的旧哈希。
- 前置操作生成了后端新 ID 或其他模型无法从已知输入确定的内容，而后续参数依赖这些内容时，必须先返回结果、由 Agent 下一轮生成参数；不自动修改已有参数来让调用通过。
- HTML 的需求参考快照绑定该调用执行时真正依据的 Manifest、Design、Spec 状态，包含已成功的依赖结果。不得在提交时直接套用后来发生的无关新状态，伪造页面已适配新要求。

## 6. 保存格式、哈希与前端展示

### 6.1 资源协议

| 资源或入口 | 保存方式 | 编辑与版本依据 | 成功返回 |
| --- | --- | --- | --- |
| `edit_manifest`、`edit_design`、`edit_spec` | 对象合并后两空格缩进、末尾换行 | JSON 解析后统一序列化的内容哈希 | 实际完整对象与现有变更字段 |
| `edit_outline` | 校验、补充稳定 ID、统一序列化 | 实际保存的完整源码及原文哈希 | 实际完整源码 |
| `edit_html` | 完整输入或精确替换结果原样保存 | 实际源码及原文哈希 | 继续只返回保存摘要 |
| `run_command` 的文本编辑 | 保存命令产生的原文，不追加格式化 | 实际文件字节及文本读取依据 | 保留现有命令输出契约 |

结构化 JSON 的纯缩进、换行、对象键顺序变化不改变资源内容版本；数组顺序和字符串内容仍有意义。原始文件哈希可能变化，不能与资源内容哈希混为一谈。

通用文本编辑 JSON 是结构化工具的例外：移除现有 `sourceformat.JSON` 的隐式重排，但保留语法、Schema 和业务校验。下一次结构化工具更新时可以重新统一序列化。

`run_command` 按文本修改时，不能仅凭等价的结构化 JSON 内容哈希确认文本仍与 Agent 所见一致。必须有对应真实文本的读取依据；若只读过对象形式的 Manifest、Design，则先通过完整单文件读取取得原文。Outline、HTML 的原文读取可以复用。

### 6.2 HTML 后端改动

- 从领域 HTML 保存和命令编辑两条路径移除自动 Prettier 格式化，不额外改写缩进、换行符、引号或 CSS 排版。
- 保留 HTML 创作结构、页面身份、作用范围和业务校验；保留保存后渲染检查的要求。格式化器原先偶然提供的解析报错不能作为业务校验的替代，需审查移除后的校验边界。
- 不增加 HTML 全文回传，不通过忽略全部空白的模糊匹配掩盖旧锚点问题。
- 清理本需求导致不再使用的后端格式化实现、注入点及专用依赖；保留前端仍使用的 Prettier 能力，不开展无关清理。

### 6.3 前端展示

- 复用 `formatHTMLForDisplay`、Worker 与缓存，让源码视图、消息源码卡片使用同一展示格式化入口，不在多个组件反复排版。
- 原始源码与展示文本分开保存；源码接口、source hash、Agent 读取、实际页面渲染、源码复制及导出仍使用原文。
- 同一原文版本在缓存有效期内复用格式化结果；相同版本的并发格式化请求合并，避免 Worker 重复计算。
- 统一展示配置：HTML parser、两空格缩进、print width 100、`htmlWhitespaceSensitivity: strict`、嵌入语言格式化开启、展示换行使用 LF。这些选项只作用于展示副本。
- 格式化失败或 Worker 不可用时显示原文，不阻断查看；旧请求完成时不能覆盖已切换页面或新版本的内容。
- 保留现有只读预览及复制行为，不增加无关提示文案、开关、交互或视觉改版；遵循 DESIGN.md，但不修改 DESIGN.md。

## 7. 错误与模型指令

### 7.1 可操作的错误

沿用现有错误结构和机器错误码，通过 `reason`、`next_action`、资源及 call ID 清楚表达原因；新增或调整的模型可见字段必须同时更新真实输出 Schema，不能只写 TOOL.md。

| 情况 | 自然语言应表达的内容 |
| --- | --- |
| 当前资源尚未读取 | 尚未取得这项资源的当前内容；指出可调用的读取工具及参数 |
| 读取后版本改变 | 指出具体资源已变化；要求重新读取、基于当前内容重新生成编辑，禁止原样盲重试 |
| 文本锚点零匹配或多匹配 | 指出替换项、匹配数量及如何取得唯一锚点；不能直接宣称一定是并发冲突 |
| 前置调用失败 | 指出依赖的前置调用和资源；说明本调用未执行 |
| 页面已删除或尚未创建 | 要求读取 Outline 确认有效稳定 ID，不只要求重读不存在的 HTML |

HTML 版本冲突示例：该页 HTML 在上次读取后已更改。请调用 `read_resource`，传入 `resource: "html"` 和该页真实 `slide_id`，读取当前源码后重新编辑。实际错误必须填入可操作的资源参数，不返回省略号作为 ID。

Hash 继续由后端内部管理，不新增模型输入中的 `expected_hash`，也不要求模型抄写哈希值。

### 7.2 简短提示词约束

在 `edit_html` 的实际 Tool Definition 和相关系统提示中统一以下内容，删除“保存前自动格式化”的旧描述：

- 首次生成可读的 HTML，使用清晰换行和一致缩进，避免无必要的压缩写法。
- 局部修改沿用现有排版，只改必要内容，避免无关重排。
- 精确替换以当前已知的真实保存源码为准；刚成功原样写入且内容未变时可以继续编辑，无需重复读取。
- 尚未读取、版本已变化或当前上下文缺少所需源码时，先读取；不要凭记忆拼接旧锚点。
- 保存成功仅证明写入成功，视觉正确性仍需 `render_slide` 检查。

提示词不要求模型模拟 Prettier，也不替代版本、匹配和内容校验。同步检查 `modelToolObservation`、`ObservationParts` 和持久化恢复后的模型实际可见结果，避免只更新文档或内部结构。

## 8. 实施顺序与验收

建议顺序：调用依赖分析与事务隔离；提交及版本传播；移除后端格式化并统一前端展示；错误和提示词；实际协议文档与定向验证。每步以完整链路行为为准，不保留新旧协议双轨，不为历史开发数据增加迁移方案。

| 验收情景 | 预期 |
| --- | --- |
| A 页 HTML 替换失败，同时修改 B 页 HTML | A 失败，B 正常保存；并发和事件可观察 |
| 连续修改同页 HTML | 顺序正确；第一项失败则后续依赖项跳过；第一项成功不会因内部版本未推进导致第二项假冲突 |
| A 页 Spec 失败，同时修改 A、B 页 HTML | A 页 HTML 跳过，B 页可继续 |
| Outline、Design、Manifest 独立更新 | 可以并发；一个失败不取消另外两个 |
| 全局要求失败后仍有独立全局更新和依赖页面编辑 | 独立全局更新继续；依赖失败要求的页面编辑跳过 |
| 不同页面 Spec 更新，或 Outline 删页与 Spec 更新交错 | 不覆盖其他页面，不复活已删除数据；存储互斥不制造无关依赖失败 |
| 写入可读或紧凑 HTML 后立即精确修改 | 后端保存原文，Agent 可使用已知成功结果；前端展示格式化文本不改变保存内容 |
| 结构化 JSON 只改变排版；随后业务字段改变 | 前者资源内容哈希不变；后者产生新版本并检测旧版本编辑 |
| Outline 保存时生成 ID 或重排源码 | 返回实际完整源码，后续精确编辑基于它；不猜测尚未返回的新 ID |
| `sed` 修改 HTML 或 JSON | 没有额外格式化；文本读取、版本和业务校验继续有效 |
| 并发调用中一项提交失败、取消或恢复重放 | 回滚仅影响该调用；其他已提交结果和回执保留；不会重复执行已提交写入 |
| HTML 参考快照与同批次要求修改交错 | 快照只包含该调用真正依据的要求，不被无关后续提交污染 |
| 展示格式化延迟、失败、重复请求、页面切换 | 原文不变，按版本复用结果，过期结果不覆盖当前页面 |

调度、事务及版本传播属于复杂逻辑，可在现有 `tool_batch_test.go`、`session_test.go`、`generation_inputs_test.go`、资源工具及命令测试中补充少量高价值用例；替换原来断言全局 fail-fast 的旧期望。针对受影响测试验证，必要时对并发用例做定向 race 检查，不新增大量镜像测试，不运行全量测试或反复运行已通过的检查。

界面和真实 Run 验收交由用户手动完成，禁止 Computer Use、Browser 自动化及子代理。开发完成后报告实际修改、定向检查结果、未验证项及手动验收步骤；未经要求不提交、不推送，不修改既有无关工作区变更。
