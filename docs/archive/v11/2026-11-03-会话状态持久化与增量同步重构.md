# 会话状态持久化与增量同步重构

- 日期：2026-11-03
- 状态：详细设计稿；本次只编写文档，不修改业务代码、数据库或本地项目数据。
- 决策依据：Dasi 确认的「当前状态直接持久化、历史独立查询、事务化提交、快照与增量同步」方案。
- 适用范围：模型上下文、会话时间线、Run 与命令恢复、会话状态、项目回退及对应前后端协议。
- 与既有设计的关系：沿用 `2026-11-02-计划工具与会话计划生命周期重构.md` 的产品语义；其中“通过会话日志回放获得当前计划”的存储决定由本文替换。计划清除规则、审批语义和工具参数保持既有决定。

## 1. 目标与设计理由

### 1.1 当前问题

当前持久化把展示、模型上下文、命令结果和恢复依据集中在 `thread.jsonl`。不同读取者先加载并还原整个日志，再提取自己需要的内容：

- 刷新会话：后端全量投影公共事件，前端再次回放并重建时间线。
- 加载模型上下文：遍历全部 `model.edit`，得到当前有效消息。
- 保存模型上下文：再次读取全量日志、重建旧消息，与内存消息比较后生成 `model.edit`。
- 查询当前计划、输入前的对话、命令结果、审批应答、交接文档和压缩结果：也需要日志读取或事件序号反查。
- 实时连接：后端每次检查增量先全量读取日志，再过滤序号；前端同时存在重复初始化和全量轮询。

2026-11-03 的已有本地样本中，一个会话有 617 条事件、5,190 次内容引用，其中 5,163 次属于内部 `model.edit`；历史接口存在数十秒耗时。这是问题样本，不作为后续性能承诺或容量上限。

本次解决的是读写模型：常规操作的工作量应由当前上下文、当前页面或本次变更决定，不随全部历史版本持续累积。

### 1.2 最终设计

| 需求 | 权威数据 | 主要读取方式 |
| --- | --- | --- |
| 下一次模型调用 | 当前上下文版本及其消息记录 | 直接读取当前有序消息集合 |
| 打开、浏览会话 | 已保存的时间线条目与分组 | 分页查询，直接展示 |
| 继续任务 | Run 检查点、工具执行记录、交互记录 | 按 Run 和实体 ID 查询 |
| 当前计划、标题、建议 | 会话当前状态 | 单行查询 |
| 实时更新、断线补齐 | 已提交的会话变更批次 | 按游标范围读取 |
| 项目回退 | 项目检查点中的数据库快照和文件版本 | 恢复指定版本 |
| 问题追溯 | 诊断记录、必要的历史实体 | 显式查询或导出 |

SQLite 保存业务权威状态。进程内状态用于运行和加速；诊断日志用于追溯。普通读取不从诊断日志、增量通知记录或历史上下文版本重建当前状态。

### 1.3 范围限制

- 不改变模型选择、工具权限、输入分类、计划生命周期及一个项目的执行互斥规则。
- 不引入多进程协同写入、通用事件溯源平台、消息队列服务或多分支会话产品。
- 不修改 `DESIGN.md`；加载反馈及现有条目继续遵循全局 UI 规范。
- 前后端一次切换到新协议，不保留旧日志兼容层、双读双写或降级路径，不设计历史开发数据迁移。
- 本文的表结构、接口及指标是目标约定；所有实际验证由用户手动执行。

## 2. 核心约束与版本语义

### 2.1 必须成立的约束

1. 用户输入被确认接收前，必须已持久化；客户端是否在线不影响后端任务执行。
2. 同一次业务变化涉及的消息、上下文、运行检查点、时间线和变更通知，必须在一个 SQLite 事务内提交。
3. 前端收到的持久结果必须来自已提交状态。内存通知丢失不丢业务结果，客户端可从数据库补齐。
4. 同一工具结果只加入上下文一次；调用与结果保持原生配对，不能由 UI 文本反推模型消息。
5. 模型压缩改变有效上下文，不删除用户可见历史。
6. 加载失败不能转换为空数组成功；未加载不等于空会话。
7. 旧执行者、旧项目场景和旧实体版本的提交必须被拒绝。
8. SQLite 事务不包含模型请求、工具执行、目录遍历、渲染或文件复制。
9. 业务读取不扫描全部会话日志，恢复也不通过 SSE 历史重建运行状态。

### 2.2 标识和版本

| 字段 | 归属与含义 | 变化规则 |
| --- | --- | --- |
| `scene_revision` | 项目当前历史场景 | 回退、恢复未来等历史切换成功后递增；不能恢复成旧数值 |
| `seq` | 某会话在当前场景内的提交序号 | 每个持久会话提交分配一个；一个序号可以包含多个实体变更 |
| `context_revision` | 会话当前任务上下文版本 | 仅有效消息集合变化时递增 |
| `entity_revision` | 可更新公共实体的版本，包括条目、分组、Run、命令和交互 | 每次修改该实体递增 |
| `execution_revision` | Run／命令执行所有权代次 | 认领、恢复或撤销旧执行权时递增 |
| `checkpoint_revision` | Run 已提交恢复位置的版本 | 每次提交新的运行边界递增 |
| `request_key` | 一次用户操作或内部提交的幂等键 | 重试复用；不同内容不能复用同一键 |

传输游标包含 `(project_id, thread_id, scene_revision, seq)`，编码为不透明字符串。不同场景的序号不可直接比较。

历史切换可以恢复目标版本中的业务行及会话序号，但必须使用新的 `scene_revision`。执行所有权代次和切换操作回执不随业务快照倒退。

内部序号使用 64 位整数；通过 JSON 传输的 revision、seq、排序序号统一使用十进制字符串，前端不转为普通 `Number` 比较。时间统一使用 UTC Unix 毫秒数。

## 3. 数据结构

本节定义目标逻辑表和关键字段。所有 JSON 字段必须校验合法性，并在业务边界按明确类型校验；不能用无约束 JSON 替代状态机。项目、会话及运行归属通过外键和提交层共同校验。

所有会向前端发送 upsert 的可变实体，均需保存 `entity_revision` 和 `updated_seq`，下表未重复列出时也适用。它们只在对应场景内比较，不代替执行权或上下文版本。

### 3.1 项目历史状态与会话当前状态

`project_history_state`：每个项目一行，成为项目历史状态的唯一权威来源。

| 字段 | 类型／约束 | 说明 |
| --- | --- | --- |
| `project_id` | TEXT PK、FK | 所属项目 |
| `scene_revision` | INTEGER >= 1 | 当前场景版本 |
| `history_revision` | INTEGER >= 1 | 回退目标、未来历史及历史操作的并发校验版本 |
| `switch_state` | `ready / restoring` | 是否正处于跨文件与数据库的历史切换 |
| `switch_operation_id` | TEXT nullable | 正在处理的切换操作 |
| `last_operation_id`、`last_command` | TEXT nullable | 最近成功切换回执 |
| `checkpoints_json` | JSON array | 既有项目检查点索引及目标关系 |
| `latest_snapshot_ref`、`latest_time` | nullable | 供恢复未来使用的快照 |
| `ui_scene_json` | JSON nullable | 回退后的工作区定位信息 |

现有 `checkpoints/state.json` 的运行时权威职责转入该表。项目检查点文件仍可包含捕获时的历史元数据，但不能被常规读取当作另一个当前状态源。

`threads` 保留标题、命名设置、建议设置等现有字段；移除 `next_event_seq`、`delivered_event_seq`，增加：

| 字段 | 类型／约束 | 说明 |
| --- | --- | --- |
| `last_seq` | INTEGER >= 0 | 当前场景已提交序号，初始 0 |
| `retained_after_seq` | INTEGER >= 0 | 允许增量续读的最小游标序号 |
| `context_revision` | INTEGER >= 0 | 当前有效上下文版本，初始 0 |
| `active_run_id` | nullable FK | 尚未结束的 Run，包括暂停状态 |
| `plan_json` | JSON nullable | 最新完整步骤快照；SQL NULL 表示无计划 |
| `plan_run_id`、`plan_revision` | nullable ID、INTEGER | 计划最近执行归属及版本 |
| `next_input_suggestions_json` | JSON nullable | 当前有效建议及所属 Run／命令版本 |
| `last_context_run_id` | nullable FK | 最近承载任务上下文的 Run，不受独立闲聊覆盖 |

当前计划遵循既有三条清除路径；不得从最后一条历史计划、旧 Run 检查点或前端非空值恢复已清除计划。

### 3.2 消息记录与有效上下文

`conversation_messages` 保存已经形成的消息事实。正文和模型原生结构直接存入 SQLite，不再将长度超过 256 字节的文本逐字段外置。

| 字段 | 类型／约束 | 说明 |
| --- | --- | --- |
| `id` | TEXT PK | 稳定消息 ID |
| `thread_id`、`run_id`、`input_id` | FK／nullable FK | 会话、执行和输入归属 |
| `round_id` | TEXT | 完整对话轮次归属，便于按轮次读取 |
| `created_seq` | INTEGER | 首次提交序号，用于输入前历史截断 |
| `role` | `user / assistant / tool` | 模型原生角色 |
| `kind` | 明确枚举 | `instruction / assistant / tool_result / summary / direct_reply` |
| `native_json` | JSON object | 原生 ContentPart、工具调用、工具结果关联、Metadata、AssistantReplay 等 |
| `public_json` | JSON nullable | 经过既有公共内容处理后的可见正文和引用；内部消息为 NULL |
| `source_message_ids_json` | JSON array nullable | 摘要等消息的来源引用，不在普通加载时展开 |
| `created_at` | INTEGER | 首次形成时间 |

消息提交后内容不可变。需要修正或压缩时生成新的消息 ID，再切换上下文引用；不要原地改写已经被检查点引用的原生消息。

索引至少包括 `(thread_id, created_seq, id)`、`(thread_id, round_id, created_seq)` 和 `(run_id, id)`。模型调用完成提交使用稳定的调用 ID 生成幂等回执，避免断线重试插入重复消息。

`thread_context_versions` 保存有效消息集合的完整有序引用：

| 字段 | 类型／约束 | 说明 |
| --- | --- | --- |
| `thread_id, revision` | 联合 PK | 上下文版本 |
| `message_ids_json` | JSON array | 当前有效消息 ID 的确定顺序 |
| `created_seq`、`created_at` | INTEGER | 提交位置与时间 |
| `reason` | `append / compact / replace` | 变更原因 |

新会话初始化 revision 0、空集合。新版本先写入，再在同一事务中更新 `threads.context_revision` 和相关 Run 检查点。

这是一份直接可读的当前上下文快照；读取不需要加载前一版、执行 diff 或回放 `model.edit`。保存有序 ID 集合的成本为当前窗口消息数 O(K)，消息正文只写新增部分。这里不承诺每次保存严格 O(1)，但成本不依赖历史版本数。

批量读取消息正文，禁止对每个 ID 发起独立数据库或文件请求。ID 顺序由集合决定，缺失引用属于数据错误，不静默丢弃。

只有当前版本、可继续 Run 的检查点、未完成模型调用及项目回退检查点需要的版本必须保留。无引用旧版本可在项目维护阶段清理；不能把每一步的全部历史版本永久作为当前加载依赖。

### 3.3 任务上下文与完整对话的边界

保留现有输入分类语义：任务主模型使用任务上下文；输入识别、命名、建议等按各自规则读取最近的公开对话。

- `thread_context_versions` 只保存任务模型当前有效消息；独立闲聊、拒绝与其他直接应答不自动加入任务上下文。
- 完整对话由 `conversation_messages.public_json` 和输入归属查询，不通过模型上下文反推，也不通过 UI 渲染后的 DOM 获取。
- 摘要只针对选定任务消息生成，不把混入闲聊的摘要再通过回放拆分为任务历史。
- 系统提示词、当前计划、当前项目资料与资源在请求组装时按既有规则加入；不把每次完整组装结果反复写入任务消息集合。
- 输入决策仍使用最近完整轮次及既有 token 预算；工具选择的任务对话视图继续排除非任务输入。
- 模型原生续接信息与当前上下文版本、供应商及模型身份绑定；压缩、模型切换或历史回退后按协议失效，不能将旧续接信息套到新集合。

### 3.4 输入、追加指令与幂等

新增 `thread_inputs`，作为输入正文、接受边界和分类结果的权威记录。

| 字段 | 说明 |
| --- | --- |
| `id`、`thread_id`、`client_message_id` | 输入身份；`(thread_id, client_message_id)` 唯一 |
| `message_id`、`request_hash` | 用户消息及请求内容校验 |
| `run_id`、`source_run_id` | 当前执行归属和转交来源 |
| `accepted_seq`、`history_before_seq` | 原始接受序号及输入前历史边界 |
| `disposition`、`decision_json` | `pending` 或现有输入分类结果及必要决策数据 |
| `delivery_state` | `accepted / injected / rejected / transferred` |
| `reply_message_id` | 独立应答的消息引用，可空 |
| `reference_json`、`created_at`、`updated_at` | 附件、技能、页面及 DOM 引用的既有语义 |

读取某个输入之前的对话时，只查询 `created_seq < history_before_seq` 的公开消息。按轮次倒序选择最近窗口，再按原顺序组装；不能先读取全部消息后裁切。

追加输入转交后仍使用同一个输入和用户消息 ID，保留原始历史边界；时间线只更新执行归属，不创建第二条相同用户消息。输入转交不会把它自身或后来生成的回复带进“输入之前”的上下文。

`steering_inbox` 保留队列职责，改为引用 `thread_inputs.id`，移除依赖原始事件反查正文的 `input_event_seq/result_event_seq` 用法。接受、分类、注入、转交等阶段通过明确状态和提交序号关联。

### 3.5 Run 与检查点

`runs` 保留既有状态枚举、作用范围、执行代次、所有者和项目唯一活动 Run 约束，增加或调整：

- `scene_revision`：创建／恢复时所属项目场景。
- `input_id`、`command_json`：直接保存接受输入引用和原始 RunCommand，替换 `start_event_seq` 反查。
- `context_revision`：与当前检查点一致的上下文版本。
- `checkpoint_json`：保留执行阶段、模型路由、技能状态、未完成批次、待处理交互及必要运行计数；不再复制全部消息正文。
- `checkpoint_revision`、`execution_revision`、`owner_instance_id`：继续用于条件更新和执行权校验。
- `usage_json`、`active_duration_ms`、`terminal_json`：直接保存累计用量、运行时长及终态事实。
- `progress_json`：最新可见阶段，替换从所有进度事件推导当前阶段的方式。
- `cancel_requested_at`、`cancel_request_id`：持久取消意图和幂等身份；执行器未及时响应时也不能丢失停止请求。

检查点增加 `context_revision`、`pending_model_call`、待执行工具 ID 列表及交互 ID；同一实体的详情以工具／交互表为权威，检查点仅记录控制流和引用。

`pending_model_call` 包含调用 ID、输入上下文版本、已组装请求快照引用、供应商／模型身份和请求阶段。只保留当前未完成调用所需的请求快照；鉴权头和密钥不能进入该快照或公共接口。已完成请求的详细追踪按诊断保留策略处理，不成为恢复前置条件。

请求快照使用 `model_request_snapshots(id, thread_id, run_id, context_revision, provider, model, request_json, created_seq, created_at)` 保存不可变请求正文，以调用 ID 为主键。`pending_model_call` 直接引用该 ID；请求准备、快照和检查点同事务提交。外部图片等内容使用已经持久化的资源引用。阶段区分 `prepared / dispatched / outcome_unknown`；这些阶段不能证明供应商是否执行成功，仍按第 8.2 节核对结果。完整响应提交后清除 pending 引用，请求快照无恢复引用时可清理。

列表、标题栏、活动状态接口只选择轻量列，禁止为了显示状态读取并解析大型 `checkpoint_json`。

### 3.6 工具执行与交互

新增 `tool_executions`：

| 字段 | 说明 |
| --- | --- |
| `run_id, call_id, attempt_no` | 联合唯一身份；工具语义调用保持 `call_id`，允许安全重试增加 attempt |
| `thread_id`、`scene_revision`、`execution_revision` | 所属会话及提交时的执行围栏 |
| `tool_name`、`arguments_json`、`arguments_hash` | 调用参数与校验 |
| `status` | `prepared / executing / succeeded / failed / canceled / outcome_unknown` |
| `recovery_policy` | `read_only / idempotent / reconcile / unknown`，由工具注册代码确定 |
| `operation_id` | 文件修改、渲染、命令等外部操作的恢复标识，可空 |
| `result_json`、`result_message_id` | 结构化结果及模型结果消息，可空 |
| `error_json`、`started_at`、`finished_at` | 结果及计时 |

已持久化的成功结果不可因重复通知回退到 `executing`。当前调用状态通过 attempt 查询确定，前端显示状态由后端统一转换为既有 `completed/failed/...` 语义。

新增 `run_interactions`：

| 字段 | 说明 |
| --- | --- |
| `id`、`run_id`、`thread_id` | 交互身份和归属 |
| `kind` | `question / plan / resource / command / scope` |
| `call_id`、`request_json`、`request_revision` | 工具归属及提交给用户的完整交互快照 |
| `state` | `pending / answered / applied / canceled` |
| `answer_json`、`answer_hash` | 已接受答案及幂等校验 |
| `answered_seq`、`applied_seq` | 接受与实际应用的提交位置 |
| `created_at`、`updated_at` | 计时 |

答案接收与实际执行分为两个明确阶段。`answered` 在重启后继续应用一次；`applied` 不重复执行。相同答案重试返回原回执，不同答案覆盖已有应答必须拒绝。

审批正文、资源草稿和作用范围按既有版本规则校验，不能仅凭交互 ID 判断批准有效。计划当前步骤与计划审批正文继续分开保存。

### 3.7 命令结果、交接文档和压缩记录

`command_executions` 保留六类命令及 attempt 状态机，直接增加 `request_json`、`result_json`、`error_json`、`previous_title`、`run_id` 和必要的模型执行信息，移除 `start_event_seq/terminal_event_seq` 作为数据引用。

- `GET /commands/:id` 从命令表读取最新 attempt；最近成功结果按 `(command_id, status, attempt_no)` 查询。
- 重命名、建议、压缩等业务结果与命令终态在同一事务提交。
- 交接文档使用 `briefing_versions(briefing_id, version_no)` 联合主键，保存会话／项目归属、标题、正文、反馈及时间；按 ID 和版本直接查询。
- 压缩记录使用 `context_compactions(id)`，保存前后上下文版本、触发方式、公开摘要、token 统计、模型执行信息和时间。
- Git 提交结果直接保存 commit hash 等既有结果；外部 Git 操作的未知结果按工具同类规则核对，不盲目重新提交。
- `idempotency_records.result_json` 保存实际操作回执或稳定实体 ID，不保存只能靠日志解析的 event 引用。按场景隔离操作键，跨场景重发旧操作返回版本冲突。

### 3.8 可直接展示的时间线

新增 `timeline_groups` 与 `timeline_items`，承担持久化展示结构。后端保存语义结构，CSS、展开状态和滚动位置仍由前端负责。

`timeline_groups`：

| 字段 | 说明 |
| --- | --- |
| `id`、`thread_id`、`order_seq` | 分组身份和稳定排序键 |
| `kind` | `run / command / exchange` |
| `run_id`、`command_id`、`input_id` | 业务实体引用，按类型使用 |
| `status`、`summary_json` | 当前分组状态、终态摘要、用量／时长等轻量信息 |
| `item_count`、`entity_revision` | 条目数量与版本 |
| `created_seq`、`updated_seq` | 提交位置 |

`timeline_items`：

| 字段 | 说明 |
| --- | --- |
| `id`、`thread_id`、`group_id` | 条目身份及归属 |
| `position` | 组内稳定次序，不因更新状态重新排序 |
| `kind` | 沿用用户消息、思考、正文、工具、审批、命令、压缩、终态等现有类型 |
| `entity_revision` | 条目版本 |
| `message_id`、`tool_call_id`、`interaction_id`、`attempt_id` | 对应实体引用，可空 |
| `summary_json` | 可直接展示的公共状态、标题和摘要 |
| `body_ref`、`detail_ref` | 较长正文和详情的不可变版本引用，可空 |
| `created_seq`、`updated_seq`、`created_at` | 位置与时间 |

工具 started/completed 更新同一个条目；审批答案更新原交互条目；终态和分组摘要在同一次提交更新。用户消息通过 `client_message_id/input_id` 与乐观条目合并，不能按文本去重。

普通正文从消息记录批量读取。非消息型的长详情使用 `timeline_details(id, thread_id, public_json, created_seq)` 保存不可变公共快照；条目更新详情时换引用。HTTP 不返回 `native_json`、原始模型请求或内部恢复字段。

`body_ref/detail_ref` 是服务端生成的不透明内容引用，绑定会话、场景、条目、条目版本、来源类型及来源 ID；来源只能是该会话的消息公共正文或 `timeline_details`。详情接口按引用读取确定的不可变内容，并校验归属、场景和删除状态；不得仅按条目 ID 返回已经变化的最新详情。旧引用失效时返回明确结果，由前端刷新该条目。

列表和增量只携带必要的公共显示数据。单个条目公开 JSON 超过 32 KiB 时，正文／详情改为引用，摘要最多 2,000 个 Unicode 字符；用户消息和最终回复仍可完整打开，不能静默截断最终内容。

索引：`timeline_groups(thread_id, order_seq, id)`、`timeline_items(group_id, position, id)`、`timeline_items(thread_id, updated_seq)`，以及业务实体的唯一映射索引。

首屏按分组分页，不按原始事件分页。已完成 Run 默认返回用户消息、终态正文和分组摘要，展开后加载过程条目；进行中 Run 返回最新一页条目及完整待处理交互引用。单个超长 Run 内部继续按条目分页，不能因一个分组大而失去读取上限。

历史预览有效性、图片和工具详情按需读取；不得在首屏返回前逐条读取历史截图或重新计算评审材料指纹。当前有效性查询使用项目内容版本和对应资源身份，显示既有失效语义。

### 3.9 持久增量批次

新增 `thread_changes`：

| 字段 | 类型／约束 | 说明 |
| --- | --- | --- |
| `thread_id, scene_revision, seq` | 联合 PK | 唯一批次位置 |
| `commit_id` | TEXT UNIQUE | 内部提交身份 |
| `payload_json` | JSON object | 已提交的公共变化集合 |
| `created_at` | INTEGER | 提交时间 |

每个会话事务生成一个批次；业务内部修改没有公共变化时允许空 changes，仍推进游标。批次中按类型给出完整实体新值或显式删除，避免前端依赖缺失的旧事件推演。

```json
{
  "thread_id": "thr_example",
  "scene_revision": "4",
  "seq": "81",
  "commit_id": "commit_example",
  "changes": [
    { "type": "timeline.item.upsert", "item": { "id": "item_tool_1", "group_id": "group_run_1", "entity_revision": "2", "kind": "tool", "status": "completed", "label": "已编辑第 1 页幻灯片" } },
    { "type": "run.upsert", "run": { "id": "run_example", "status": "running", "checkpoint_revision": "12" } }
  ]
}
```

示例省略实体其他必填字段；实际公共 DTO 必须统一定义，不允许每个生产者自行选择必填字段。批准、失败、建议清除和计划清除都以显式值表达，不能靠字段缺失推断。

固定批次操作如下，接收端不得将未知操作当作成功应用：

| 操作 | 载荷与语义 |
| --- | --- |
| `thread.upsert` | 完整公共会话当前值，包括标题、计划、建议和活动 Run 引用 |
| `run.upsert`、`command.upsert`、`interaction.upsert` | 完整公共实体及 `entity_revision`；终态仍以明确 status 表达 |
| `timeline.group.upsert`、`timeline.item.upsert` | 完整分组／条目、稳定排序键和版本 |
| 对应实体的 `.remove` | 实体 ID、删除版本及必要归属；显式删除，不将终态误当删除 |
| `context_window.invalidate` | 新的统计来源版本；前端仅使统计失效，不能清空已加载时间线 |

一个批次内同一实体最多出现一次最终操作；投影器合并中间状态。每个批次的 `seq` 同时是这些实体的 `updated_seq`，删除使用高于该实体最后版本的删除版本。

批次不包含完整上下文、历史日志或未脱敏内部对象。大正文用不可变引用；一个语义提交不得拆为客户端可能半应用的多个独立批次。

变更记录同时承担数据库内的可靠通知箱，不再另行维护“SQLite outbox → JSONL → 删除 outbox”链路。

初始保留策略：保留最近 7 天的批次，并至少保留每个会话最近 10,000 批；只有同时超出两个范围的前缀可删除。清理在后台小批次事务执行，同步推进 `retained_after_seq`。容量调优可以修改策略，但普通读取不能依赖已清理批次。

## 4. 统一提交入口

### 4.1 内部提交契约

新增一个会话级提交入口，工作流、输入处理和命令服务共同调用。它是进程内业务服务，不作为前端可任意写入的 HTTP API。

输入包含：

- 项目／会话 ID、预期 `scene_revision`、稳定 `request_key` 及请求摘要。
- 涉及 Run 时的 owner、`execution_revision`、预期 `checkpoint_revision`。
- 涉及上下文时的预期 `context_revision` 与明确的追加／替换操作。
- 已计算好的消息、工具结果、交互应答、命令结果及对应状态变化。
- 必须更新的会话字段和公开语义事实。

返回已提交的场景、序号、实体版本及幂等回执。业务方法应使用具体操作类型，例如 `AcceptInput`、`CommitAssistantResponse`、`CommitToolResult`、`AcceptInteractionAnswer`、`CommitCompaction`，不要暴露任意表 patch。

### 4.2 提交步骤

1. 在事务外完成耗时准备和候选结果校验；涉及文件的操作遵循第 8 节的恢复协议。
2. 进入会话提交队列。沿用项目执行／历史切换锁，统一锁顺序为项目 gate → 会话队列 → SQLite 写事务。
3. 校验项目未删除、未切换，场景和执行权有效；重复幂等键返回同场景原回执，内容不一致则拒绝。
4. 只读取本次变化必要的当前行，校验实体与上下文版本。
5. 分配 `last_seq + 1`；写消息、上下文版本、工具／交互／命令和 Run 检查点。
6. 由公共投影器同步更新受影响的时间线条目、分组和会话当前状态；投影失败则整个事务回滚。
7. 写入 `thread_changes`、操作回执并更新 `threads.last_seq`，提交事务。
8. 提交成功后更新进程内已提交状态，唤醒 SSE 订阅者及运行队列。

公共投影器只处理本次业务变化，并读取必要当前实体，不能扫描历史重建全部时间线。模型内部事件与公共展示事件不再共享一份原始 payload 类型。

进程内广播是唤醒信号，不是可靠数据源。广播失败不回滚已成功事务；订阅者通过持久序号补齐。内存状态采用提交后发布，失败候选不能继续用于下一次模型调用。

### 4.3 并发和数据库配置

- 保留单工作目录写入所有者，不引入第二个独立后端写同一数据库。
- 单一写事务队列串行化落库；模型调用、工具计算可以按现有规则在队列外进行。
- SQLite 沿用 WAL、外键和 `synchronous=FULL`。增加独立只读连接池，初始上限 4；写连接维持 1，所有连接统一设置必要 pragma。
- 只读事务用于获取一致快照，批量取完数据后立即结束；HTTP 输出、文件读取和 SSE 等待不得占用数据库事务。
- 同一事务内的 Store 方法必须复用传入事务，不能重新获取写连接；消除 `eventInTransaction` 的整日志文件读取。
- Context 压缩、命令取消和工作线程结果提交必须使用实体版本校验，不能用“最后写入覆盖”解决冲突。

## 5. 写入流程

### 5.1 新会话与输入接受

1. 创建会话时，同一事务写 `threads`、revision 0 的上下文和空状态。成功响应可直接建立前端 `ready` 空会话。
2. 新输入以 `client_message_id` 幂等接受，保存用户消息、引用、`thread_inputs`、时间线条目及既有流程需要创建的 Run。
3. 接受事务保存 `history_before_seq`；响应成功后才允许客户端将乐观条目标为已接受。
4. 输入分类在事务外执行，读取固定边界前的最近公开对话和当前项目资料。
5. 分类结果提交到输入记录。task 按既有规则清除已完成计划、进入任务上下文；其他输入保存独立应答及终态，不污染任务上下文。

HTTP 响应丢失时重发相同输入 ID，返回同一接受回执；不能创建新消息或新 Run。

### 5.2 模型调用

1. 从内存中的已提交上下文组装请求；冷启动只加载当前上下文版本及其消息。
2. 把待发模型调用 ID、上下文版本、必要请求快照与执行位置提交到 Run 检查点。
3. 持久化失败则不发送模型请求；发送与等待响应在事务外进行。
4. 流式内容按第 5.9 节处理。完整响应形成后，按调用 ID 幂等保存原生 assistant 消息及公开正文。
5. 有工具调用时，同一事务写 `prepared` 工具记录、更新上下文、检查点和时间线；没有工具时提交对应正文或终态。
6. 提交成功后才能执行工具或发起下一次模型请求。

不得为了保存 `state.messages` 调用全量历史 Load，也不得通过重建所有旧消息来计算变化。Runtime 持有当前上下文版本和新产生的消息 ID，明确提交新增内容。

### 5.3 工具调用

1. assistant 工具调用及 `prepared` 记录先持久化。
2. 通过条件提交将本次 attempt 置为 `executing`，记录操作标识，然后进入工具主体。
3. 工具完成后，一个事务保存结构化结果、模型 tool-result 消息、有效上下文、剩余批次、工具状态和时间线。
4. 并行工具可以分别完成，但同一会话提交串行化；结果按原始调用身份和既有协议顺序组装，不能让先完成者覆盖另一结果。
5. 工具失败同样保存完整失败结果和后续控制流。运行中 UI 所需的公共状态从工具当前行获取。

一个工具批次的所有必要调用形成已持久结果并完成原生配对前，不允许发起下一次依赖该批次的模型请求。存在 `outcome_unknown` 时先解决恢复状态，不能编造成功结果或把未配对上下文发给模型。

由工具注册声明恢复方式。模型参数不能把具有副作用的操作伪装为只读或幂等。

### 5.4 交互与审批

创建交互时，一次提交保存请求快照、`pending` 状态、Run waiting 检查点和时间线。通知完成后才能等待用户。

用户应答先校验场景、交互归属、请求版本和状态，再持久化 `answered` 及答案回执。随后执行者认领并在应用事务中更新上下文、审批结果、scope／mode、交互 `applied`、检查点和公开条目。

需要额外计算时在事务外准备；准备期间 request_revision 或执行权变化则拒绝旧结果。相同答案的重复请求返回原回执，已经 applied 的答案不会再次唤起执行。

### 5.5 追加输入、直接应答与转交

- 追加输入接受时独立保存，用户能够刷新后看到 accepted 状态。
- 分类、注入、拒绝与转交直接更新 `thread_inputs` 和 inbox；实际进入上下文与标记 injected 必须同事务。
- 独立应答只写公开对话及对应时间线，不改变运行中的任务上下文版本。
- 转交到下一 Run 复用输入 ID 和消息 ID，保留原始历史截断点，事务内更新新旧 Run 与队列归属。
- 不再使用 `model.edit` 的相邻位置、watermark 或 `taskSource` 推测哪些消息属于直接应答。

### 5.6 上下文压缩

1. 固定 `scene_revision`、`context_revision` 和来源消息 ID 集合。
2. 在事务外计算摘要及保留消息，校验 token 预算和工具调用配对。
3. 提交时要求来源上下文版本仍然一致。若已变化，丢弃候选或重新按新版本计算，不覆盖新消息。
4. 同一事务写摘要消息、新上下文集合、当前引用、Run 检查点（如有）、压缩结果、命令终态及时间线。
5. 更新窗口统计版本，使旧模型续接缓存失效；原公开消息和工具历史保留。

手动压缩继续遵守当前项目锁和无冲突任务规则。内部自动压缩由当前执行者提交，不另建与 Runtime 竞争的上下文写入者。

### 5.7 计划与命令

- 计划工具写入最新 `threads.plan_json`，同事务提交计划版本及相关工具结果；读取当前计划为单行查询。
- 手动清除计划直接校验 Run 状态并写 NULL；不先读取所有事件再比较日志长度。
- 六类命令统一直接保存 request/result/error。执行副作用与结果提交采用对应恢复协议。
- 建议、标题、交接文档等在结果提交时校验原始会话／输入／命令版本，过期自动结果不覆盖新值。
- 命令 retry 复用逻辑 command_id、增加 attempt；UI 展示最新 attempt，同时能按需要读取最近成功结果。

### 5.8 停止、失败与完成

终态提交必须统一保存最终正文、Run 状态、累计用量／时长、当前检查点、相关工具／交互状态、时间线和项目执行锁释放条件。

停止请求先持久化取消意图，再通知执行器。取消不等于工具回滚；已经提交的工具结果保持成功，无法判断副作用的调用进入 `outcome_unknown`。

HTTP 失败、SSE 断线和前端卸载不能单独证明 Run 失败。前端只展示已收到的后端状态，不能自行追加持久失败事件或重建“权威终态”。

### 5.9 流式文本与高频进度

流式 token 和重复阶段提示不逐条写成永久会话变化。

- 进行中正文使用有 ID、有版本的 draft 条目，最多每 250 ms 合并一次持久更新；完整消息、工具调用、等待交互和终态必须立即提交。
- 内存可推送独立 `thread.transient` 帧提高跟手性，携带 Run 执行代次、draft ID 和 offset；这类帧没有持久 SSE id，不推进恢复游标。
- 持久 draft 更新包含完整已保存文本或其引用；它覆盖对应瞬时显示，而非再次拼接。
- 瞬时帧断线后允许丢失；重连显示已持久 draft，不能把未完成 draft 加入模型上下文。
- 重启时，未完成 draft 标记为中断状态并保留已保存片段；正文最终完成后再生成不可变模型消息。

## 6. 读取与 HTTP 协议

### 6.1 会话首屏

新增 `GET /api/v1/threads/:id/view?group_limit=20`，上限 50。响应包含：

```json
{
  "project_id": "pro_example",
  "thread_id": "thr_example",
  "scene_revision": "4",
  "seq": "80",
  "cursor": "opaque_cursor",
  "thread": { "id": "thr_example", "title": "演示文稿", "plan": null, "plan_revision": "3" },
  "active_run": null,
  "active_commands": [],
  "pending_interactions": [],
  "timeline": { "groups": [], "items": [], "older_cursor": null, "has_more": false, "is_empty": true },
  "context_window": null
}
```

其他 Thread/Run 字段使用统一公共 DTO；示例仅展示响应层次。`active_run`、`plan` 等通过显式 null 表达不存在。

实现要求：

1. 在一个短只读事务内检查项目场景与删除状态，读取 `last_seq`、会话状态、当前 Run、活动命令、待处理交互和最近分组／条目。
2. 这些数据与 cursor 必须属于同一个数据库快照。不能查询完消息后另取一个更晚的 cursor。
3. `is_empty` 依据是否存在公开时间线分组和当前活动实体判定，不等于当前页数组长度。
4. 正在运行或等待交互的实体必须出现在独立状态字段中，不因时间线分页而漏掉。
5. 单个组首屏条目默认 50、上限 100；全文或工具详情按引用加载，不在首屏读取图片字节。
6. 首屏不等待上下文 token 重新估算、模型恢复计算或历史评审有效性重算。

### 6.2 历史与详情分页

| 接口 | 用途 |
| --- | --- |
| `GET /threads/:id/timeline?before=<cursor>&limit=20` | 更早的时间线分组 |
| `GET /threads/:id/timeline/groups/:groupId/items?before=<cursor>&limit=50` | 组内更早过程条目；首次无 before 返回最新一页 |
| `GET /threads/:id/timeline/items/:itemId/detail?ref=<content_ref>` | 指定不可变引用的公开正文／详情 |
| `GET /threads/:id/changes?cursor=<cursor>&limit=100` | HTTP 增量补齐，上限 500 批 |
| `GET /threads/:id/events?cursor=<cursor>` | SSE 持续同步 |

表中路径均位于 `/api/v1`。分页使用稳定排序键和 ID 的 keyset 游标，不使用 offset 扫描。更早页面按正常时间顺序返回，前端前插并维持滚动锚点。

分页游标必须包含项目场景；跨场景请求返回 `SCENE_CHANGED`。同场景页面允许反映查询时的最新实体值，响应带 `read_seq` 和每个实体版本；前端合并时低版本不能覆盖已收到的新版本，分页响应也不能推进实时恢复游标。

首屏和所有分页均由已保存条目生成。折叠、筛选失败工具和 Markdown 渲染仍在前端完成，但不再由原始 Run 事件计算工具最终状态。

旧 `GET /threads/:id/history` 移除。`active-run` 和 `GET /runs/:id` 可继续供显式运行操作使用，但常规会话首屏不再单独依赖它们。

### 6.3 写请求与错误契约

涉及本方案的输入、停止、交互应答、命令和历史操作写请求必须携带 `scene_revision` 及稳定操作 ID；沿用已有 client_message_id／command_id 等幂等身份，不另造重复身份。修改已有实体时还需提交对应版本。服务端不能在收到过期请求后自动替换为最新场景继续执行。

成功回执返回实体身份、提交 cursor 和对应版本。HTTP 回执只有包含完整变更批次且补齐前序批次时才能推进前端 appliedSeq；仅收到某次操作成功不能跳过尚未收到的其他变化。

| HTTP 状态／错误码 | 处理规则 |
| --- | --- |
| `409 SCENE_CHANGED` | 当前缓存和旧操作失效，重新加载场景；不自动重发写操作 |
| `409 CURSOR_RESET_REQUIRED` | 游标超出保留范围或高于当前水位，重新读取 view |
| `409 VERSION_CONFLICT` | 实体、上下文或执行权变化，重新读取相关状态；不覆盖新值 |
| `409 IDEMPOTENCY_CONFLICT` | 相同操作 ID 携带不同内容，拒绝执行 |
| `404 NOT_FOUND` | 目标不存在或当前不可访问，沿用删除／导航处理 |
| `410 CONTENT_REF_EXPIRED` | 历史详情引用已不可用，刷新对应条目 |
| `503 PROJECT_RESTORING` | 项目处于文件与数据库切换阶段，保持旧内容冻结并等待重新加载 |

错误响应保留统一公共错误结构和请求 ID，不把失败转换为成功空列表。SSE 无法修改已发送 HTTP 状态时，使用 `thread.reset` 携带同类 reset 原因后关闭。

### 6.4 模型与辅助命令读取

| 读取者 | 目标路径 |
| --- | --- |
| 新 task／Runtime 冷加载 | 当前上下文版本 → 批量消息 → 组装当前项目资料 |
| Run 恢复 | Run 检查点指定上下文版本及待处理实体 |
| 输入识别／命名／建议 | 输入边界前或当前最近公开轮次，按原预算裁切 |
| 工具选择 | 最近任务公开轮次，按输入分类过滤 |
| 当前计划 | `threads.plan_json` |
| 命令详情 | `command_executions` 的对应 attempt |
| 审批应答 | `run_interactions` |
| 交接文档与压缩结果 | `briefing_versions`、`context_compactions` |

上下文窗口统计作为可重建的派生数据，以上下文版本、当前计划版本、项目内容指纹、模型配置和提示词版本为校验键。首屏可返回匹配的已有统计，否则返回 null；面板按需触发计算，不阻塞历史显示。生成器仅使用当前有效上下文，完成后仍需校验来源版本，过期结果不得覆盖新统计。

## 7. 增量同步与前端状态

### 7.1 服务端传输

SSE 的持久事件名统一为 `thread.change`，id 为提交后游标，data 为第 3.9 节的完整变更批次。

连接流程：

1. 校验 cursor 的项目、会话、场景和保留边界。
2. 先登记该会话的进程内唤醒订阅，再读取数据库中 `seq > cursor.seq` 的批次。
3. 按顺序发送积压批次，更新连接自身游标；继续查询直到追上。
4. 等待提交唤醒后再查询新范围。心跳只保持连接；每 15 秒附带一次轻量水位核对，补偿丢失的进程内唤醒。
5. 发送过程中不持有数据库事务或会话写锁；慢客户端使用有界发送缓冲，积压超限断开并由游标补齐。

普通空闲连接不读历史正文、不遍历文件。每次 range 查询使用 `(thread_id, scene_revision, seq)` 索引，不能先查全表再过滤。

游标早于 `retained_after_seq`、超出当前水位或属于旧场景时，HTTP 增量返回明确 reset 错误；SSE 发送无持久 id 的 `thread.reset` 后关闭。前端重新获取首屏快照，不尝试拼接跨场景数据。

重连位置以客户端已经应用的 cursor 为准：显式 query cursor 优先，未提供时才接受 `Last-Event-ID`，两者均需校验归属和版本。前端在断线、解析失败或应用失败后关闭旧连接，以 Store 中已应用的 cursor 创建新连接；不能让浏览器提前记录的事件 ID 跳过尚未应用的批次。错误不能悄悄退回从序号 0 回放。

### 7.2 前端唯一会话入口

新增共享会话加载／同步模块，由 Store 管理，每个会话在同一页面内只有一个 in-flight 首屏请求和一条共享订阅。

```ts
type ThreadViewState = {
  loadStatus: 'unloaded' | 'loading' | 'ready' | 'error';
  streamStatus: 'closed' | 'connecting' | 'open' | 'reconnecting';
  generation: number;
  sceneRevision: string | null;
  appliedSeq: string | null;
  cursor: string | null;
  thread: ThreadView | null;
  activeRun: RunView | null;
  groupsById: Record<string, TimelineGroup>;
  itemsById: Record<string, TimelineItem>;
  orderedGroupIds: string[];
  olderCursor: string | null;
  error: PublicError | null;
};
```

类型展示必要职责，命令、交互和乐观输入等字段按对应公共 DTO 补齐。`loadStatus` 与 Run 的运行状态分开，禁止用 `idle/recovering` 代替历史加载状态。

初始化顺序为请求 view → 一次性写入 Store → 从返回 cursor 订阅 SSE。快照与建立连接之间的变化由数据库增量补齐。

组件只选择所需状态；`useActiveSession` 改为纯 selector，不再在每次调用时附带恢复副作用。重新挂载组件复用同会话请求，不能额外发起 history 或 active-run 请求。

### 7.3 应用变更与分页竞态

- 一次提交批次中的所有变化通过一次 Store 更新应用，之后才推进 appliedSeq/cursor。
- 已应用序号直接忽略；收到更大的不连续序号先补齐缺口，不跳过中间批次。
- 同一批次校验失败或应用失败不推进游标，进入重同步流程；禁止吞错后显示空会话。
- 按 ID 和 entity_revision upsert，显式 remove 记录删除版本，防止迟到分页把已删除条目重新插入。
- 未加载历史分组的条目更新只进入稀疏缓存或标记分组需刷新，不立即把旧工具行插进最新列表。待用户翻页时合并最新版。
- HTTP 操作回执和 SSE 都可能携带同一次提交，按 commit_id/seq 去重。
- reset、项目回退和删除递增 generation，取消旧请求；旧响应的场景或 generation 不符时丢弃。
- 普通切换会话可复用内存视图；关闭视图只释放订阅引用，不取消后端执行。重新进入使用已有游标补齐，游标失效才重新读取首屏。
- 窗口 focus/visibility 恢复时检查连接和游标即可；取消每 4 秒遍历所有会话拉取完整历史的逻辑。

### 7.4 UI 状态规则

| 条件 | 表现 |
| --- | --- |
| 还在解析项目／会话或首次 loading | 复用全局色彩和间距的轻量骨架，不展示 init |
| ready，服务端确认无可见历史和活动实体 | 展示既有 init 态 |
| ready，有内容 | 展示直接读取的时间线 |
| 首次加载失败 | 使用既有错误反馈与重试操作，不能伪装为成功空会话 |
| 已有内容时断线 | 保留内容并重连，不清空为 init |
| 切换历史场景 | 冻结旧场景交互，重新载入目标场景；不混合旧新状态 |

不新增解释段落、提示标语或英文翻译。保留既有折叠样式、Markdown 语义、最新输入定位及滚动行为。首次恢复历史不逐条播放入场动画；实时新增内容才使用既有动效。

## 8. 崩溃恢复与项目回退

### 8.1 服务启动

1. 取得工作目录写入所有权，打开新结构数据库。
2. 先恢复未完成的项目历史切换和项目文件修改事务；未恢复完成的项目保持隔离，不接受新任务。
3. 使旧进程的执行所有权失效，按索引查询未结束 Run 和命令，不扫描所有会话历史。
4. 从 Run 检查点引用加载有效上下文、未完成工具、交互及队列。恢复 Bus 的去重／状态约束时直接读取这些当前实体，不回放全部公共事件。
5. 通过统一提交入口发布恢复后的状态，再开放执行和客户端同步。

需要恢复的上下文、消息或结果缺失时进入可见恢复错误，禁止用空上下文继续模型调用。检查点与当前上下文的不同必须有明确来源：既有暂停／历史版本读取其固定引用，新 task 读取线程当前版本。

### 8.2 中断点处理

| 中断位置 | 重启后的处理 |
| --- | --- |
| 输入事务未提交 | 服务端未确认接收；同 ID 重试可重新接受 |
| 输入已提交、HTTP 回执未到 | 返回原回执，不创建重复消息 |
| 模型调用准备已提交、响应未保存 | 保留调用身份，标记中断；支持供应商查询时核对，否则按既有恢复策略重新请求，可能产生重复推理计费，但不能据此重做已提交工具 |
| 完整响应已提交、工具尚未派发 | 从 prepared 调用继续，不重新生成已经保存的响应 |
| 工具 executing、没有持久结果 | 进入 outcome_unknown，按工具恢复策略判断，不能认定“未执行” |
| 工具结果与检查点事务已提交 | 直接使用已保存结果，跳过该次调用 |
| 交互 answered、尚未 applied | 重新认领后应用一次 |
| 交互已经 applied | 返回已处理状态，不重复推进 |
| 压缩候选计算完成、事务未提交 | 当前上下文不变；候选可以丢弃 |
| 终态事务已提交、通知未送达 | 首屏或增量查询获得终态，不恢复执行 |

`read_only` 可安全重试；`idempotent` 必须复用真实有效的外部幂等标识；`reconcile` 查询操作日志、目标文件哈希、渲染产物或 Git 状态；`unknown` 暂停为可见恢复错误，保留结果未知的事实，由用户决定后续处理，不能自动重放。数据库事务无法保证外部副作用恰好执行一次，不作此承诺。

### 8.3 文件修改与数据库的一致性

继续使用项目文件修改协议保存操作意图、前镜像／后镜像和 operation_id。文件完成后，再在会话事务中提交工具结果。

文件已改但结果未提交时，恢复器根据 operation_id 和实际文件状态完成核对并补交结果；无法证明目标状态时标记未知，不能靠重复运行命令尝试“修复”。

新图片、截图等不可变资产先持久化成功，再提交数据库引用；事务失败留下的未引用资产可稍后清理。不能提交尚未落盘的资产引用。

### 8.4 项目检查点与回退

项目检查点与 Run 检查点职责不同：前者恢复项目历史版本，后者恢复一次任务的执行位置。

项目检查点必须捕获以下一致内容：

- 项目资料、页面文件、品牌与必要资产版本。
- 会话当前状态、输入／消息、所需上下文版本和时间线。
- Run、工具执行、交互、队列、命令、交接文档、压缩结果及业务幂等回执。
- 捕获时的项目历史元数据和 UI 定位信息。

不捕获进程内订阅、瞬时流式片段、可重建统计缓存或历史 `thread_changes`。恢复后客户端重新获取快照，无需恢复旧通知缓冲。

捕获仍使用既有项目 gate 和快照保护，保证文件与数据库来自同一静止业务边界；本次不引入新的文件版本控制系统。

回退流程：

1. 校验项目无冲突执行、目标检查点和 history_revision。
2. 在改变活动文件前，持久化当前完整 preimage 和切换恢复记录；将 `project_history_state` 置为 restoring。
3. 关闭旧场景订阅、冻结项目操作，准备并恢复目标文件。此期间不能提供混合场景的业务读取。
4. 在一个 SQLite 事务内恢复目标业务数据，过滤当前已删除对象，清除该项目旧变更批次，将 scene_revision 设为切换前值加一，并更新执行围栏。
5. 在同一事务内将每个恢复会话的 `retained_after_seq` 设为其 last_seq，写入成功操作回执并置为 ready，再提交。旧场景游标全部失效，新首屏游标可从恢复水位继续。
6. 事务成功后发布新场景，发出 reset／项目刷新通知，再清理切换恢复记录；此步不再修改决定恢复成功与否的业务状态。

文件与 SQLite 不能靠一次 SQL 事务原子修改。恢复记录必须先于文件修改持久化：若成功回执尚未提交，重启恢复切换前 preimage；若成功回执已提交，完成目标场景收尾。切换执行权代次及恢复后的场景版本不得因回滚 preimage 而重新授予旧工作线程。

`project_history_state` 的实时 scene_revision、switch_state 和操作回执由切换控制器管理，不能被快照中的旧行直接覆盖。失败恢复完成后也必须结束旧订阅并使旧异步请求失效。

### 8.5 删除、保留与数据清理

沿用限时撤销删除语义及删除围栏。新表纳入项目／会话归属查询；最终物理删除时按外键和既有清理流程统一删除，限时撤销期间不能提前清除恢复所需消息和资产。

垃圾回收根包括当前上下文、可继续 Run、待处理调用和交互、公开时间线、命令／文档结果、保留的项目检查点和删除撤销快照。清理未引用上下文版本或资产时必须考虑这些根。

诊断日志可以独立轮转。删除诊断日志或清理过期变更批次不能影响普通打开会话、下一次模型调用、审批或运行恢复。

## 11. 性能目标与观测

### 11.1 结构性目标

| 路径 | 允许的工作量 |
| --- | --- |
| 首屏 | 索引查询最近分组和有限条目，不随旧会话总长度线性增长 |
| 有效上下文冷读 | 当前 K 条消息及当前项目资料，不读取历史上下文版本 |
| 保存上下文 | 新增正文及当前有序 ID 集合，不回放日志 |
| 空闲 SSE | 心跳、低频轻量水位查询，不扫描或还原正文 |
| 断线补齐 | 缺失的 Δ 个变更批次，超出保留范围时重取有限快照 |
| 命令／交互详情 | 按业务 ID 查询，禁止全会话或全项目遍历 |
| Run 恢复 | 当前检查点、有效上下文和未完成实体 |
| 项目回退 | 允许与所选项目快照体积相关，属于显式操作 |

### 11.2 时间指标

以下为同一开发机器、本地前后端、模型与外部工具耗时不计入的验收目标，实施后由用户测量，不是当前已达成结果：

- view 接口 P95 ≤ 300 ms；应用脚本可执行后的会话首屏内容 P95 ≤ 1 s。
- 普通消息／工具结果提交的数据库持锁 P95 ≤ 50 ms；大结果和文件阶段单独记录字节数与耗时。
- 在当前上下文和首屏内容相同的情况下，历史规模扩大 10 倍不应造成首屏与普通保存耗时近似线性增长。
- 新用户输入和首屏失败均不能因统一 15 秒超时策略被误报为空会话；不通过延长超时掩盖读取问题。

记录首屏查询、数据库等待、正文序列化、返回字节数、前端应用批次、首次显示、恢复阶段、上下文消息数、待补批次数和重复初始化请求数。常规日志不输出消息正文、模型请求或敏感附件。

性能数据不足时先定位数据库排队、序列化或渲染阶段，再决定是否需要额外虚拟列表、缓存或索引；不以全量缓存掩盖常规读取依赖全部历史的问题。

## 12. 实施顺序、切换和手动验收

### 12.1 实施顺序

1. 固定公共 DTO、实体状态、提交边界和新 Schema。
2. 完成会话事务入口、直接状态存储、上下文与运行检查点联动。
3. 一并切换工具、审批、输入、六类命令、计划和辅助对话读取。
4. 完成项目快照、场景恢复、删除与资源引用生命周期适配。
5. 提供 view／分页／changes／SSE，前端切换共享同步 Store 和直接展示。
6. 删除旧业务日志路径、重复恢复与全量轮询，完成手动验收交付。

步骤可以在开发分支逐项完成，但新旧前后端协议不能并行作为正式运行方案；不能把未切换读取者留在旧日志上作为降级。

现有开发数据库格式直接失效，通过新格式工作目录或明确范围的开发数据重建启用新结构。不得编写旧日志导入、历史数据迁移或自动静默删库。任何实际重置操作都不属于本次文档任务。

### 12.2 手动验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 新建空会话 | 创建成功后直接 ready，可显示既有 init |
| 刷新有历史会话 | 加载中不闪 init；首屏只请求一次 view，时间线随后显示 |
| 多个组件同时挂载／栏目隐藏再显示 | 同会话共享请求和订阅，不重复拉历史 |
| 首屏超时、网络错误 | 明确错误状态，可重试，不变成空会话 |
| 空闲会话保持打开 | 无 250 ms 全量扫描，无 4 秒全历史请求 |
| 翻阅旧分组、展开超长 Run | 有界分页，完整正文可访问，滚动位置稳定 |
| 分页请求中到来工具更新／删除 | 新版本不被旧页覆盖，旧工具不跳进最新位置 |
| 初始快照返回后、SSE 建连前产生消息 | 增量完整补齐，无漏消息、无重复 |
| 断线、重复事件、乱序、保留边界过期 | 按游标补齐或 reset；整个批次原子应用 |
| 模型压缩与历史查看 | 模型使用新摘要，公开旧消息仍完整存在 |
| 压缩计算期间新增任务消息 | 旧候选被拒绝，不覆盖新增上下文 |
| 闲聊、拒绝、任务和追加输入混合 | 完整对话可见，任务上下文归属正确 |
| 输入回执丢失、重复提交、转交下一 Run | 用户消息和上下文均不重复，自身不进入输入前历史 |
| 回答审批后立即关闭页面／重启服务 | 答案保留且只应用一次，权限和版本校验有效 |
| 工具准备后／执行中／结果提交后分别重启 | 分别继续、核对未知结果、复用已提交结果 |
| 手动停止与工具结果同时到达 | 取消不覆盖真实结果，不误判外部副作用已撤销 |
| 命令成功、失败、重试与最近成功结果 | 从实体记录直接恢复，attempt 及结果一致 |
| 计划更新、清除、闲聊及下一 task | 遵守既有生命周期，刷新和恢复不复活旧计划 |
| 服务重启后首次打开很长会话 | 不扫描全部日志，不等待所有历史 Run 恢复 |
| 项目回退／恢复未来／切换中崩溃 | 文件、上下文、时间线一致；旧游标和旧执行者失效 |
| 删除、撤销删除、最终清理 | 新状态、引用和资产与既有删除语义一致 |
| 清理诊断日志或过期变更批次 | 当前业务状态可读，普通执行及恢复不依赖它们 |
| 相同首屏与上下文，增加大量旧历史 | 查询与保存成本不随全量历史线性扩大 |

文档阶段不运行自动化验证。后续实施也遵守项目的手动验证约束，不调用 Browser、Computer Use 或子代理执行验证。
