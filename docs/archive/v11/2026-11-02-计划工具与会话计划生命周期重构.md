# 计划工具与会话计划生命周期重构

- 日期：2026-11-02
- 状态：开发前确认稿；本次仅编写文档，确认后实施。
- 决策依据：当前会话中 Dasi 最终确认的工具定义、全量覆盖方式和清除条件。

## 1. 目标与设计理由

将计划审批与执行清单分开：plan 模式产出可审批的方案，create 模式自主安排并推进执行步骤。当前计划归属于会话，跨单次 Run 保留。

执行清单采用完整快照覆盖。Agent 提交的内容即最新清单，不通过计划或步骤 ID 匹配旧数据。该方式参考本地 DeepSeek Harness 的 `todo_write`；清除时机使用本项目已确认的三条规则。

当前问题来自工具、状态与生命周期共同耦合：`create_plan` 同时在 plan/create 模式暴露，`update_plan` 要求已有已批准计划；步骤 ID 参与审批签名、事件校验和里程碑，新 Run 与历史回放又会清空计划。因此实施需同步后端、前端、协议和提示词。

## 2. 工具协议

### 2.1 create_plan

仅在 plan 模式提供，参数为两个必填字段：

```json
{
  "content": "完整 Markdown 方案正文",
  "steps": ["规划目录", "编写幻灯片", "渲染检查"]
}
```

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `content` | 非空字符串 | 沿用现有需求复述、实施方案、执行步骤、预期结果与验收标准的正文组织方式 |
| `steps` | 非空字符串数组 | 本次方案的完整执行步骤，每项为非空名称 |

处理流程：保存方案提交记录，将步骤初始化为 `pending`，展示审批；批准后沿用现有切换到 create 并继续执行的流程，拒绝后留在 plan 模式接受调整与重新提交。

移除独立的计划 `title` 参数。方案正文直接用于阅读、复制和历史展示，计划进度弹窗沿用现有「执行计划」标题。

### 2.2 update_plan

仅在 create 模式提供，只有一个必填字段 `steps`。无清单时建立清单，已有清单时完整覆盖，写入后直接执行，不触发计划审批。

```json
{
  "steps": [
    { "title": "规划目录", "status": "completed" },
    { "title": "编写幻灯片", "status": "processing" },
    { "title": "渲染检查", "status": "pending" }
  ]
}
```

```json
{ "steps": null }
```

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `steps` | 非空步骤数组或 `null` | 数组完整覆盖当前清单；`null` 清除整个当前计划 |
| `steps[].title` | 非空字符串 | 步骤名称 |
| `steps[].status` | 枚举 | `pending`、`processing`、`completed`、`failed` |

每次快照独立校验字段、状态和最多一个 `processing`；空数组作为无效参数处理，清除使用明确的 `null`。

名称、数量、顺序和状态全部以最新数组为准。去掉旧步骤匹配、已完成步骤不得回退、已完成步骤不得消失等跨快照校验。无计划、计划执行中或计划全部完成时，create 模式均能调用此工具。

工具参数、模型上下文、前后端计划数据和事件中统一移除 `plan_id`、`step_id`。保留既有 Run、工具调用、审批交互的标识，各自继续负责执行、调用和应答关联。

## 3. 方案审批与当前清单

两类数据各自承担明确职责：

| 数据 | 内容 | 生命周期 |
| --- | --- | --- |
| 方案提交记录 | `content` 与提交时的完整步骤 | 随审批及历史保存，后续执行更新不改写已提交正文 |
| 当前执行清单 | 最新 `steps` 快照 | 会话级持续保存，由工具写入、手动清除或下一 task 清除事件更新 |

`create_plan` 提交时初始化当前步骤；批准后 create 模式承接这些步骤。直接进入 create 模式时，Agent 可通过 `update_plan` 自主建立清单，不需要虚构正文、审批状态或计划标题。

取消将当前执行步骤与已批准方案正文进行哈希一致性比较的机制。方案审批仍校验有效的 `interaction_id`、待处理状态和应答归属；方案内容在对应审批记录中保持为提交时的版本。

当前清单可以由 Agent 重新组织，实际执行仍遵循用户目标、授权范围和现有工具权限。计划更新或清除不改变这些执行条件。

## 4. 会话状态与清除规则

### 4.1 保存与恢复

使用既有会话日志保存完整计划快照与清除事实，作为当前清单的权威来源。前端实时更新、历史回放、会话切换、刷新与服务重启读取同一有序事件结果。

Run 创建、`user_turn`、`run.started`、Run 结束和模式切换都不直接清空当前计划。清单不再依赖最新 Run 是否曾调用过计划工具。

新 task 读取会话保留的清单，作为模型上下文中的 `<current_plan>`。输入「继续」时能够基于现有清单和实际项目内容承接未完成工作。现有 Run 断点恢复也读取会话最新清单，旧断点中的计划数据不再覆盖会话状态。

### 4.2 三条清除路径

| 触发条件 | 执行时机与结果 |
| --- | --- |
| Agent 调用 `update_plan({ steps: null })` | 写入明确的会话清除事件，当前计划变为 `null` |
| 当前清单全部完成，下一 task 开始 | 上一任务结束后，新输入被判定为 `task` 且获准进入任务处理时，先持久化清除，再组装该任务上下文 |
| 用户点击计划弹窗的「清除计划」 | 后端检查会话当前执行状态后写入同样的清除事实 |

全部完成按当前非空清单中所有步骤均为 `completed` 判断。`chat`、输入拒绝、识别失败、刷新、重试请求和既有任务中的追加输入，不构成下一 task 开始。

未完成清单跨后续 task 保留，由 Agent 决定继续推进或显式清除。创建新 Run 本身不能代替 task 判断。

清除只移除当前计划，方案历史、旧快照及已生成项目内容继续保留。步骤和计划不再具有稳定身份，覆盖前后的历史通过事件顺序追溯。

### 4.3 手动清除

在现有计划弹窗提供「清除计划」操作，复用公共按钮及交互样式。有计划时展示该操作。

`creating`、`running`、`waiting`、`recovering`、`canceling` 期间按钮禁用；停止、暂停或结束后可清除。后端复核相同状态，避免按钮状态滞后导致执行中的清单被手动移除。

清除不产生一条用户聊天消息，不创建空 Run。提供会话级 `DELETE /api/v1/threads/:id/plan`，写入既有会话事件通道，返回清除后的状态。执行重复清除按幂等处理。

## 5. 事件、上下文与完成检查

### 5.1 事件适配

- `plan.updated` 表达会话级的完整步骤快照或 `null`。工具写入可携带原有执行归属，手动清除可作为无 Run 的会话事件；不伪造 Run 或工具调用。
- 审批请求保留 `interaction_id` 和方案提交快照；审批应答移除 `plan_id`，沿用交互归属和幂等规则。
- 移除工具事件中的 `plan_step_id`、里程碑中的 `completed_step_ids` 及对应校验和 reducer 字段。
- 移除根据旧、新步骤身份自动生成完成里程碑的逻辑。保留独立的正常执行消息，不对完整快照进行步骤 diff 或匹配。
- 清除作为显式事件保存；实时与回放均能处理 `null`，不能用旧值兜底重新填回已清除的清单。

共享协议一次切换到新结构，前端类型、解析器、后端公共事件校验、历史与推送同步适配。

### 5.2 模型上下文

`<current_plan>` 提供会话最新步骤快照或 `null`。方案审批正文按其原有提交记录供需要的上下文读取，进度更新无需重新发送正文。

同步移除上下文中的步骤 ID、当前步骤与批准哈希绑定等旧结构，调整上下文投影、压缩与恢复路径。停止或失败保留清单；界面的执行反馈依据承接该计划的 task 状态，独立闲聊不改变计划执行归属。

### 5.3 完成判断

当前清单存在且含未完成步骤时，完成检查提示 Agent 按新协议提交完整步骤进度，使用可读步骤名称表达问题。

已有内容、渲染、范围与成果验收继续判断实际任务是否完成。`steps: null` 或清单全部勾选不替代实际验收。

## 6. 提示词的必要调整

沿用现有英文、简短段落和职责描述风格。工具协议的精确定义由工具描述及参数 schema 承担，模式提示词仅说明使用目的与模式差异。

| 文件 | 最小必要修改 |
| --- | --- |
| `backend/prompts/tool/create_plan.md` | 明确仅用于 plan 模式方案审批；删除自动分配步骤 ID 的说明，保留现有正文组织与审批反馈流程 |
| `backend/prompts/tool/create_plan.json` | 移除 `title` 参数描述，保留 `content`、`steps` 的简洁定义 |
| `backend/prompts/tool/update_plan.md` | 改为 create 模式完整清单写入：首次建立、后续覆盖、`null` 清除；简述及时更新进度 |
| `backend/prompts/tool/update_plan.json` | 使用 `steps`、步骤名称与四种状态描述，删除 `updates.step_id` 等旧参数 |
| `backend/prompts/mode/create.md` | 将最后一条计划指引改为按需使用 `update_plan` 安排、推进多步骤工作，移除通过新方案审批才能计划的暗示 |
| `backend/prompts/mode/plan.md` | 保留现有正文结构和 `create_plan` 审批流程，仅修正与新参数或工具可见性直接有关的内容 |
| `backend/prompts/core/agent.md` | 仅在通用 Planning 句子与新模式职责冲突时作一句级别调整 |

不新增独立的冗长计划策略章节，不将后端校验、异常分支和所有禁用行为逐条写入提示词。工具返回和 `PLAN_NOT_COMPLETE` 的模型指引同步换成新参数格式。

## 8. 实施顺序与验收

建议按协议和模型、后端状态与审批、前端状态与交互、提示词与相关引用的顺序完成一体化修改，再交付用户手动验证。

| 手动验证场景 | 预期结果 |
| --- | --- |
| create 模式直接提交多步骤工作 | 无需计划正文与审批，首次 `update_plan` 即显示清单 |
| plan 模式提交方案并批准 | 读取完整正文审批，批准后 create 模式承接步骤 |
| plan 模式拒绝后调整方案 | 继续规划、重新提交，历史正文与审批记录正确 |
| create 模式改写清单名称、数量、顺序、状态 | 最新数组直接覆盖，不产生 ID 或匹配错误 |
| 工具提交 `steps: null` | 当前计划移除，刷新及重启后仍为清除状态 |
| 未完成清单经历超时、失败、停止、闲聊或后续 task | 清单保持，后续模型上下文可读取并接续 |
| 全部完成后先闲聊，再开始下一 task | 闲聊保留；下一 task 接受后清除 |
| 已有任务中的追加输入、拒绝输入和识别失败 | 不触发下一 task 自动清除 |
| 手动清除及执行期间点击 | 停止后可清除；执行、等待、恢复和停止过程中按钮禁用，后端同时限制 |
| 切换会话、刷新、恢复执行、查看历史 | 会话当前清单与历史提交正确，不被最新闲聊 Run 或旧恢复快照覆盖 |
| 完成检查与里程碑、工具记录 | 无旧 ID 字段依赖，实际成果验收仍生效 |

按项目约定，验证由用户手动执行。本次文档阶段不运行自动验证，不修改业务代码或全局设计规范。

结构直接切换到新协议，不保留兼容层、双读双写或旧协议降级，不为历史开发数据增加迁移方案。确需处理本地开发数据时另行明确范围，不在本次文档阶段操作。
