# 项目资源按需创建与 Agent 编辑审批

日期：2026-10-08。状态：前后端已实施，待用户手动验收交互与视觉。

## 1. 目标与已确认决策

新项目不自动生成 `.manifest.json`（内容要求）和 `.design.json`（视觉要求）。左侧目录仍显示这两个入口；打开缺失资源时，画布中间显示「暂无文件」和「新建」。用户点击「新建」后立即写入当前默认内容，并在同一画布展示可编辑文件。内容要求的标题取项目标题，其余必填文本为「待明确」、列表为空；视觉要求使用现有 `defaultDesign()` 的默认内容。缺失不等于已有空文件，不得在读取、预览、导出或 Agent 上下文中暗中落盘。

Agent 新建或修改内容要求、视觉要求、目录结构时，每次实际写入前必须请求用户审批。审批操作只有「通过」「编辑」「拒绝」；「编辑」跳转对应画布，以 Agent 提议稿为起点，允许增删改任意内容，最终「保存并通过」。用户在非 Agent 审批场景下直接新建或编辑这些资源，照常保存，无需审批。目录结构继续沿用当前“尚未初始化”的项目状态，不新增空 `.outline.json`。

Timeline 中，等待审批的编辑工具行使用黄色铅笔与「编辑内容要求／视觉要求／目录结构」，紧邻标题右侧放黄色背景「待审批」标签；下方沿用当前 diff 样式，操作按钮按语义分别为绿色「通过」、黄色「编辑」、红色「拒绝」。编辑草稿期间保持黄色待审批状态。无论直接通过还是编辑后通过，最终都变为现有绿色铅笔「已编辑…」工具行，默认折叠，展开显示**实际提交内容相对审批前版本**的 diff。审批不另占一条 Timeline 记录，也不显示「已批准」作为完成摘要。拒绝不写入项目，工具行显示未应用的结果。

本需求仅覆盖上述三种项目资源；页面设计稿、HTML、主题等沿用现行规则。已审定提示词保持不变。

## 2. 实施前状态与影响范围

- `backend/internal/service/project.go` 的 `initWorkDir` 原本同时创建 Manifest、Design 和空 `.spec.json`；移除前两项，保留 `.spec.json` 及项目初始化所需的目录和 Git 初始提交。
- `backend/internal/service/ppt_mutation.go` 的项目快照目前强制读取 Manifest、Design；`backend/internal/spec/types.go` 与 `frontend/src/api/types.ts` 的快照也把它们声明为必有。前后端一次性改为明确的缺失状态，不保留旧协议兼容分支。
- `backend/internal/pptmutation/mutation.go` 的手动 Manifest patch 依赖文件已存在；需增加只允许缺失时使用的创建操作，并保证创建与既有文件冲突时不覆盖。Design 同样应有明确的创建语义，不能靠普通写入覆盖竞争中新出现的文件。
- `backend/internal/pptmutation/resource_edit.go` 的 Agent 结构化编辑要求 Manifest、Design 已存在；需支持首次创建，同时保持完整 Schema 校验、默认值和版本检查。`edit_outline` 已有缺失资源的 `init` 路径。
- `backend/internal/workflow/runtime.go` 在工具执行成功后调用 `CommitOperation` 持久化；审批门禁应放在候选内容校验、暂存之后，正式提交之前。`RunSession` 的操作快照、持久化回执和 Runtime checkpoint 是恢复的基础。
- `backend/internal/contextengine/assembler.go`、`backend/internal/workflow/project_state.go` 已部分容忍资源缺失，但仍可能向模型或渲染路径传入零值对象；其中 `loadSpec` 对缺失 Outline 仍会报错。需让新项目的三种资源缺失状态都能被正确表达，同时区分“缺失”和“已有文件”，让 Agent 无需为了确认缺失而再读一次无内容资源。
- `frontend/src/features/deck/DeckNavigator.tsx` 已显示资源入口；`ProjectDocumentView.tsx`、`ManagementEditor.tsx`、`runtimeFrame.ts` 以及后端 `export/snapshot.go` 等仍假设资源存在。目录结构当前主要在左侧编辑，审批草稿的画布编辑需补齐对应的中间画布交互。
- `frontend/src/features/agent/ActivityRows.tsx`、`ChangeDiffCard.tsx`、`eventReducer.ts`、`historyHydrator.ts`、`timelineGrouping.ts` 已有编辑工具行、diff 和历史重放；审批应并入同一个 `call_id` 对应的工具项。

## 3. 资源状态与默认内容

### 3.1 单一存在性来源

项目快照协议将 `manifest`、`design` 改为对象或 `null`；`null` 只表示对应源文件不存在。`hashes` 只包含真实存在的资源版本，不给缺失资源生成虚构哈希。Outline 维持现有空 `sections` 展示方式，但其真实存在性继续由项目状态／源文件判断，不能把空结构误当已初始化文件。文件存在但 JSON 无效仍报错，不能降级成 `null`。

渲染、缩略图、导出等内部消费者使用统一的**有效展示值**：缺失 Manifest 时仅以项目标题作为 Deck title，缺失 Design 时使用现有默认 Decorations；这些值只参与运行和导出计算，不回写项目资源、不出现在快照中作为“已创建文件”。相关摘要／缓存哈希必须区分“源文件缺失”和“源文件存在且值碰巧与默认值相同”，避免陈旧缓存。导出快照按真实源文件存在性复制；需要运行框架字段时使用同一有效展示值。若没有任何页面，仍按现有“尚无页面”规则阻止导出；不能因为 Manifest／Design 缺失而额外报资源无效。

Agent 的 `project_state` 明确报告 Manifest／Design 的 `exists` 或 `missing`。模型上下文中缺失资源不得伪装成空的 Manifest／Design，也不要自动发起无意义的 `read_resource`；实际读取缺失资源时返回明确的未创建状态和下一步可用编辑工具，而不是泛化的文件读取异常。修改模型可见的工具定义和运行时上下文即可说明首次创建及审批行为；不得修改受保护的 `backend/prompts/core/agent.md`、`output.md`、`reference.md`。

### 3.2 用户点击「新建」

仅在目标文件确实缺失时展示中间画布空态及「新建」。点击即通过正常项目变更 API 原子创建，不先打开空白表单，也不要求审批：

| 资源 | 创建内容 | 并发条件 |
| --- | --- | --- |
| 内容要求 | 项目标题；`goal`、`audience`、`language`、`pages` 为「待明确」；`requirements`、`prohibitions` 为空数组 | `manifest.create` 仅在文件不存在时成功 |
| 视觉要求 | 现有 `defaultDesign()`：空需求及默认 Decorations | `design.create` 仅在文件不存在时成功 |

把默认对象的构造收敛到手动创建、Agent 首次编辑和内部有效展示值都能复用的位置，避免三处出现不同的默认字段；内部有效展示值仍不代表源文件已经创建。

创建成功后刷新快照并直接显示现有管理编辑界面；重复点击、跨窗口竞争或资源已被 Agent／其他窗口创建时，不覆盖已有内容，刷新为当前文件。请求失败保留空态和重试能力。运行期间普通用户资源变更继续受现有 Run 锁保护；这与审批中的候选稿编辑是两个不同通道。

## 4. Agent 编辑审批生命周期

### 4.1 候选稿与门禁

`edit_manifest`、`edit_design`、`edit_outline` 生成并校验候选结果后，若与当前项目实际内容相比有变更（包括从“文件不存在”变为“文件存在”），保存持久化的待审批记录，暂停该工具调用及依赖它的调用，将 Run 置为 `waiting`。待审批记录至少包含 `run_id`、`call_id`、`interaction_id`、资源类型、资源原始存在性、审批前版本／原文哈希、Agent 原始提议、当前用户草稿、草稿修订号、候选 diff、Outline 关联的受影响页面和衍生文件范围。草稿单独存储在运行数据中，**不得写入项目源文件或公开为已提交结果**。

缺失 Manifest／Design 的首次 Agent 编辑应基于同一资源默认结构补全未传字段，形成满足现有 Schema 的完整候选对象；工具定义明确告知首次创建、字段用途、默认补全和审批。已有资源继续按现有“省略保留、数组整体替换、Decorations 按键合并”语义处理。Outline 首次创建继续使用 `init`，后续保持稳定 ID 及删页清理规则。候选稿新增节点在隔离的事务暂存区生成稳定 ID，只有最终批准后才发布到项目；现有节点的 ID 始终保留。已有文件上的无实际变化调用直接按现有无变更结果完成，不生成空审批。

门禁只拦 Agent 的这三种资源写入，不能被其他 Agent 写入口绕过。`run_command` 的 `sed -i` 若目标是 `.manifest.json`、`.design.json` 或 `.outline.json`，在写入前拒绝并引导使用对应结构化编辑工具；同时审计其他 Agent 文件写入路径。用户手动编辑由项目管理 API 直接提交，不经过 Agent 审批。

### 4.2 用户操作

| 操作 | 行为 |
| --- | --- |
| 通过 | 对当前候选版本执行最终基线检查与原子提交；发布实际工具成功结果和最终 diff；Run 恢复。 |
| 编辑 | 跳转目标画布并加载持久化候选稿。内容／视觉要求复用现有字段编辑模式，但字段保存只更新审批草稿；目录结构画布提供章节、小节、页面的添加、修改、移动、删除，复用现有目录操作与视觉模式，所有操作只更新审批草稿。 |
| 保存并通过 | 先保存画布中尚未提交到草稿的输入，校验完整资源，再以最终草稿提交。原始 Agent 候选与用户最终稿不同也仍属于原 `call_id` 的同一次编辑。 |
| 拒绝 | 丢弃候选及草稿，项目文件和衍生文件均不变；返回明确的用户拒绝工具结果，Run 可继续处理独立工作，但不得在同一 Run 自动反复提交该资源的同一被拒绝意图。 |

进入「编辑」本身不等于审批，不改项目文件。离开画布或刷新后，Run 仍等待；再次打开可恢复已保存草稿。取消编辑只返回待审批工具行，不擅自当作拒绝。审批按钮提交期间禁用重复操作。Outline 草稿删页时，审批 diff 必须可见被移除的页面；其 Spec／HTML 清理只随最终批准的同一事务执行。最终草稿如果与基线完全一致，作为无变更结果结束，不生成虚假的增删 diff。

### 4.3 事务、依赖与恢复

审批前只允许候选暂存和读取，不能调用 `CommitOperation`，不能发布 `tool.completed` 成功事件，不能更新 Agent 已知资源版本或页面生成依据。批准后针对**最终草稿**重新运行统一领域校验、受影响资源计算与生成依据计算，再以原 `call_id` 通过现有提交日志／回执原子提交；`tool.completed` 的结果、`ChangedTargets`、Outline 新 ID 和 diff 都取真实提交结果。

同批次调度保持现有成功依赖和顺序约束：依赖待审批修改的页面、渲染及同资源编辑必须等待其批准并提交；拒绝则按依赖失败规则跳过。独立分支可按现有调度执行，但不能把未批准内容当作已提交上下文。为避免多个交错审批造成草稿和基线混淆，首版同一 Run 同时最多挂起一个资源编辑审批；需要多个时按工具依赖与原始调用顺序依次提出，不合并不同 `call_id`。

Run checkpoint 与审批记录必须支持进程重启后恢复同一个待审批请求、草稿、修订号和对应工具调用。历史事件重放不得生成第二条审批，也不得重复提交。重复批准请求凭 `interaction_id`、草稿修订号和原 `call_id` 幂等返回既有结果；批准前再校验文件存在性、内容版本与项目锁。基线已变化时拒绝覆盖，保留可理解的冲突状态，让 Runtime 重新获取当前资源并产生新候选，旧批准不能套用到新内容。Run 取消／失败时清理未提交草稿，不能遗留源文件写入。

## 5. 接口与事件契约

在现有 `/api/v1` 路由下增加下列能力；具体 handler 命名遵循项目约定，但请求／响应语义应一致：

| 接口 | 用途与核心字段 |
| --- | --- |
| `POST /projects/:id/mutations` | 扩展 `manifest.create`、`design.create`，创建默认资源；仍支持 `expected_scene_revision`，创建条件由服务端真实文件存在性判定。 |
| `GET /runs/:id/resource-edit-approvals/:interaction_id` | 返回待审批 `call_id`、目标资源、基线存在性和版本、Agent 提议稿、当前草稿、草稿修订号、结构化 diff、受影响页面；只允许所属项目的授权用户读取。 |
| `PUT /runs/:id/resource-edit-approvals/:interaction_id/draft` | 使用预期草稿修订号提交完整候选对象；Outline 新节点携带隔离暂存区生成的稳定 ID。服务端校验并返回新修订号及新 diff；不得写项目资源。修订冲突返回 409。 |
| `POST /runs/:id/resource-edit-approvals/:interaction_id/decision` | `decision: approve | reject`，批准时必须带精确草稿修订号；服务端先核实交互仍待处理，再触发 Runtime 原子提交／拒绝。重试幂等。 |

新增公共事件 `resource.edit_approval_requested`、`resource.edit_approval_updated`、`resource.edit_approval_answered`，均包含 `run_id`、`call_id`、`interaction_id` 和资源标识；请求／更新事件带可重放的草稿修订号及 diff 摘要，回答事件带决定，最终提交状态由原工具的 `tool.completed` 给出。Event reducer 以 `run_id + call_id` 更新原工具项，不创建独立的 approval Timeline item；历史水合与实时 SSE 使用同一还原逻辑。项目快照在成功提交后刷新。审批结果及最后显示的 diff 必须来自真正保存的最终内容，不能沿用 Agent 原提议的预览数据。

## 6. 前端呈现与交互

空态放在打开内容要求／视觉要求后的**中间画布**，保留左侧目录入口。仅显示「暂无文件」与「新建」，点击后直接进入现有编辑视图。正常已有文件的编辑交互不变；空态和按钮复用 `DocumentCanvas`、公共按钮、Lucide 图标与 `docs/design/DESIGN.md` 的间距及状态色，不增加额外解释文案。

审批中的 Timeline 使用现有编辑工具行和 `ChangeDiffCard` 的文件名、字段／目录节点与 `+/-` 差异样式。黄色铅笔、标题及「待审批」标签紧靠排列；按钮放在 diff 下方。点「编辑」打开相应资源的候选稿画布，并保持 Timeline 待审批状态。画布字段编辑不能调用普通 `projectStore.mutateProject`；须使用审批草稿 API。Outline 候选稿画布需可完整增删改，不能只显示当前 `ProjectDocumentView` 的只读目录。用户在草稿画布进行增删后，Timeline diff 跟随草稿修订更新。完成后恢复现有绿色铅笔「已编辑…」，默认折叠；展开仍是现行 diff 组件。若当前工具分组规则适用，批准后可按现行分组；待审批项始终独立可操作。

Run `waiting` 时，普通项目编辑仍按现有锁被阻止，只有当前审批的草稿编辑通道可用。画布切换、刷新和历史重放后状态一致。按钮提供键盘可达性和可辨识文字；黄色只表示待处理／编辑，绿色只表示批准成功，红色只表示拒绝。颜色从现有语义 token 获取，不在业务组件中硬编码。

## 7. 验收与实施边界

1. 新建项目后，真实工作目录没有 `.manifest.json`、`.design.json`；目录有入口，打开分别显示「暂无文件」「新建」；仅点击新建才产生对应默认文件，并立即显示可编辑内容。
2. Agent 在资源不存在和已存在两种状态下编辑任一受控资源，都先生成有效候选并停在审批；审批前项目源文件、页面身份和导出源快照不变。命令文本编辑不能绕过审批。
3. 直接通过、编辑并通过、拒绝各自得到正确的原子结果。编辑后可以完整添加／删除字段或目录节点；完成行始终是「已编辑…」，展开为最终实际 diff。拒绝和取消 Run 不写入候选。
4. 审批期间刷新页面或重启后端，可恢复同一候选与草稿；重复提交、过期修订、源文件冲突都不重复写入或覆盖别人的新内容；依赖调用只在批准提交后执行。
5. 缺失资源不导致项目快照、Agent 上下文、画布预览、运行框架或导出误报错误；已有但无效的文件仍按现行校验报错。缺失与真实默认文件在版本／缓存中可区分。
6. 只对审批状态机、持久化恢复、冲突／幂等和关键前后端契约补充有价值的定向测试；不为小型视觉改动增加测试，不运行全量测试。遵守项目规定，界面交互与视觉验收由用户手动完成，不使用 Computer Use 或 Browser 自动化验证。

实施时保留当前未提交的用户改动；不修改 `docs/design/DESIGN.md`、`docs/archieve/` 和三份受保护核心提示词；不为旧开发数据增加兼容或迁移。完成代码改动后报告改动范围、定向检查结果和仍需用户手动验收的交互。

## 8. 实施落点

- 项目初始化、快照、默认值与手动创建分别落在 `backend/internal/service/project.go`、`ppt_mutation.go`、`backend/internal/spec/types.go`、`backend/internal/pptmutation/mutation.go`；前端空态及创建入口在 `frontend/src/features/viewer/ProjectDocumentView.tsx`。
- Agent 编辑候选稿由 `backend/internal/workflow/runtime.go` 在正式提交前拦截；持久化草稿、基线校验、修订与最终重算位于 `resource_approval.go`、`backend/internal/pptmutation/approved_resource.go`。`backend/internal/run/` 负责等待、答案持久化与重启恢复；HTTP 接口由 `backend/internal/service/run.go` 和 `backend/internal/httpapi/run_handler.go` 提供。Run 终结时清理候选草稿，保留已回答审批的幂等回执。
