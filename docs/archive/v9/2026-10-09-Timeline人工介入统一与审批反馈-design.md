# Timeline 人工介入统一与审批反馈

日期：2026-10-09  
状态：代码已实施，定向逻辑与类型检查已通过；界面和实际运行等待用户手动验收。

## 1. 目标与依据

统一 Timeline 中等待用户决策的展示结构、选择顺序及提交方式，并让拒绝理由完整到达 Agent。计划拒绝改为继续修订方案，资源手动编辑改为保存草稿后回 Timeline 最终审批。

视觉参考：[临时交互 demo](../../tmp/2026-10-09-timeline-hitl-cards.html)。demo 已反映选项、文案和外层结构；demo 中的资源画布「恢复／保存」及二次继续流程仅记录于底部决策要点。生产实现以本文状态机及代码为准。demo 的 mock、假 API 和构建入口不能作为生产实现直接移植。

实施遵循 [UI 设计规范](../design/DESIGN.md)。本文取代 [项目资源按需创建与编辑审批](2026-10-08-项目资源按需创建与编辑审批-design.md) 中的旧按钮文案、直接审批和「保存并通过」交互；该文档的候选隔离、修订校验、原子提交、依赖调度和恢复约束继续有效。无需改写旧文档或全局设计规范。

实施前现状依据当时前后端代码、最新设计文档及近期提交：`d2c9b0d3`、`47b9d2e0`、`0de2b5cd`、`c4a6bdb6`。下文的目标行为与当前已实现行为分别说明，不能把 demo 当作运行时验收结果。

## 2. 已确认的交互规则

| 类型 | 外层结构 | 决策选项，从左到右 | 提交方式 |
| --- | --- | --- | --- |
| 资源编辑 | 工具行＋默认展开卡片 | 批准／手动编辑／拒绝 | 先选择，再继续；手动编辑另有草稿阶段 |
| 计划审批 | 工具行＋默认展开卡片 | 批准／拒绝 | 先选择，再继续 |
| 命令授权 | 工具行＋默认展开卡片 | 批准／拒绝 | 先选择，再继续 |
| 范围扩圈 | 工具行＋默认展开卡片 | 批准／允许全部页（若有）／拒绝 | 先选择，再继续 |
| 用户问答 | 工具行＋默认展开卡片 | 沿用现有回答选项、自由输入和跳过 | 沿用现有内部交互 |
| 人工继续 | 沿用现有失败／停止后的继续入口 | 沿用现状 | 沿用现状 |

四类审批选择统一按绿色、黄色（若有）、红色的语义顺序排列，选项等宽占满内容区。未选中时保持中性色，仅选中项使用对应的浅色背景、语义色文字和边框。蓝色「继续」置于底部右侧，去掉其左侧的箭头图标。人工继续现有的播放图标保持。

资源选项精确使用「批准／手动编辑／拒绝」，计划与命令精确使用「批准／拒绝」。范围扩圈保留「允许全部页」；提案本身已覆盖全部页时不重复提供该选项。

选择本身不提交业务决定，不执行命令、不改变授权、不写入资源、不恢复 Agent。未选择时不能提交。提交期间禁用重复操作；失败保留选择和输入，成功以服务端确认及事件还原结果，避免提前呈现成功。

## 3. 统一外层与状态展示

### 3.1 工具行承担状态，卡片承担决策

资源编辑、计划、命令、范围扩圈、用户问答统一呈现紧凑的图标、操作／对象摘要、状态标签和展开控件。等待处理时统一黄色「待人工介入」，替换这些交互入口的「待审批」「待人工审批」等旧标签。

等待人工介入时自动展开，用户可以手动收起；收起后标签仍可见。刷新或恢复待处理记录时默认展开。同一次等待期间的重绘、草稿更新和重复事件不得反复覆盖用户手动收起的选择。

正文去掉与工具行重复的操作标题及等待状态，保留必要的决策证据：文档本身的标题、文件名、diff、完整命令、扩圈范围、申请原因及问题原文。复用现有长内容展开和 diff，操作区不参与正文截断。

折叠不能销毁交互状态：选项、各选项的文本草稿、当前问题位置、问答输入及已保存资源草稿都须保留。可保持正文挂载并隐藏，或将状态提到稳定容器／store；不能依靠卸载后重新初始化表单。

### 3.2 同一记录贯穿生命周期

同一个交互的等待和已提交状态更新同一条 Timeline 记录。资源审批继续合并到原 `run_id + call_id` 的工具项；其他交互保留现有 `run_id + interaction_id` 身份，复用为工具行外观，不为展示结构再插入一条重复卡片。

真正提交决定后默认收起，移除待处理标签，工具行显示实际结果；再次展开仍可查看该次提案、决定和已提交反馈。进入资源画布、保存／恢复草稿都不属于最终提交，保持待人工介入状态。

资源批准后的成功摘要继续表达真实「已编辑…」，最终 diff 来自实际提交内容。拒绝显示未应用的结果。不同审批轮次分别保留各自提案与反馈，后来重提的计划不能覆盖上一轮被拒绝的历史证据。

问答同步外层结构，不改成批准／拒绝。保留单选、自定义回答、自由输入、跳过、问题翻页及继续。结果行按真实回答与跳过数量展示，跳过不能计作已回答，也不能在模型侧当成用户选中了推荐项。人工继续不纳入待人工介入标签统一。

## 4. 拒绝反馈

四类审批选择拒绝后，在选项下方展开多行输入框；可填写拒绝理由或修改建议，然后点击「继续」随决定提交。反馈为可选，不因空白文本阻止拒绝。

按选项分别保存本次输入。切换到批准或手动编辑时隐藏拒绝输入框，最终请求只携带当前决定对应的文本，不误提交以前的拒绝草稿；切回拒绝可继续编辑原草稿。折叠、请求失败和普通重绘不清空输入。

统一字段名 `feedback`，可选字符串，含义是用户随当前审批决定提供的原文理由／建议。非空内容保留原文与换行，不经摘要、改写或翻译；空值可以省略。仅含空白视为未提供反馈，不据此推断批准或停止。

反馈必须贯通：

`前端请求 → API 校验 → Answer → 交互队列 → 持久化／checkpoint → Runtime → 原工具调用的模型 Observation → 回答事件／历史展示`。

反馈影响后续方案选择，不改变决定的授权含义：资源拒绝仍不写入，命令拒绝仍不执行，范围拒绝仍保持原范围。Agent 可以依据建议改用已授权方案；不得仅因建议提及某操作就把它当作授权，也不得不作调整地反复申请同一被拒绝操作。计划拒绝单独采用下一节明确的重提语义。

## 5. 资源手动编辑与最终审批

### 5.1 三个阶段

1. 在 Timeline 选择「手动编辑」，第一次点击「继续」打开对应画布，以当前审批草稿为起点；首次草稿来自 Agent 提案。此时不提交审批答案。
2. 画布仅提供「恢复」「保存」两个中性按钮，不再提供「保存并通过」。保存完成后可回 Timeline 核对当前草稿相对审批前基线的 diff。
3. 回到原审批项再次点击「继续」，对已保存的当前草稿提交最终批准。保留「手动编辑」选择，无需强迫用户再选择「批准」。

需有与当前 `interaction_id`、草稿修订关联的明确编辑／待确认状态，区分第一次继续打开画布与保存后的继续提交批准，避免一直重新打开画布。该状态是 UI 流程状态，最终资源决定仍只有 `approve | reject`，不得新增后端 `edit` 审批决定。

不能仅凭 `draft != proposal` 判断是否已完成保存：用户可能保存未改动的提案，也可能恢复后确认原提案。刷新后至少恢复持久化的当前草稿及修订，允许用户审阅并批准该版本；不得以刷新丢失本地状态为由自动批准或丢弃草稿。

### 5.2 保存、恢复和离开

- 「恢复」回到本次 Agent 最初提案 `proposal`，而不是审批前项目基线；清理未保存输入，并通过草稿通道恢复当前草稿。
- 「保存」校验并保存画布尚未保存的输入，只更新隔离审批草稿和修订号，不写正式项目、不提交批准、不恢复 Run。
- 保存成功后更新 Timeline diff 与待确认状态；保存失败保留输入和原修订，不能放行最终批准。
- 画布有未保存内容或保存请求进行中时，Timeline 不能假装批准了这些内容；先完成显式保存，再以已保存修订确认。不能在 Timeline 的继续中悄悄补做原「保存并通过」。
- 离开画布、取消局部编辑或切换文档不等于拒绝；再次打开沿用已保存草稿。未保存输入沿用当前编辑器的离开策略，不把它公开为持久化草稿。

「批准」直接确认当前持久化草稿；「拒绝」提交 `reject` 与可选 feedback，不写项目。无论直接批准还是编辑后批准，最终提交前仍必须检查最新修订、项目基线与锁，重做领域校验、受影响资源计算，并执行既有原子提交。

保留资源审批的幂等、过期修订拒绝、基线冲突、Outline 稳定 ID／衍生文件清理、依赖成功门禁与取消回滚。草稿更新事件不能变成工具成功事件；只有最终真实提交后刷新项目快照并恢复依赖调用。

## 6. 计划拒绝改为修订后重提

### 6.1 实施前代码行为

实施前 `awaitPlanApproval` 支持 `approve | revise | refuse`：`revise` 保留未批准状态；`refuse` 将计划设为 `PlanCanceled`。两者都回 planning 并恢复同一 Run，但 canceled 状态使 `controlSchemas` 不再开放 `create_plan`，反而开放 `finish_task`，`completion.go` 还有拒绝计划的收尾豁免。`mode.plan` 也明确禁止拒绝后自动重提。

因此旧行为的拒绝并非直接终结 Run，而是让模型失去重提入口并可以收尾。这与用户仍想获得可执行计划的意图冲突。

### 6.2 新状态机

计划审批只保留 `approve | refuse`，删除计划专用 `revise` 决定及其分支，不保留旧协议兼容层。

| 决定 | 计划与 Run 状态 | 原 `create_plan` 返回 | 后续行为 |
| --- | --- | --- | --- |
| approve | 按既有原子转换冻结批准内容，进入执行阶段 | `decision=approve` 与批准摘要 | 按批准计划执行 |
| refuse | 计划保持未批准／`awaiting_approval`，回 planning，恢复同一 Run | `decision=refuse`、明确需修订重提的摘要及可选 feedback 原文 | 保持 `create_plan` 可用，修订完整计划并再次等待审批 |

拒绝采用原 `revise` 的运行逻辑；明确拒绝当前候选但规划任务继续。不得根据文本是否像修改建议来暗中切换取消与修订行为。

有反馈时依据反馈及原需求修订完整计划；没有反馈时重新审视已有需求和方案，作出合理改进后重提。只在确实缺少阻塞信息时问答澄清，不因空反馈自动结束，也不把同一未调整提案无限重发。

原审批答案与工具 Observation 只完成一次；重提调用形成新的候选和审批身份，重新暂停等待。未获新批准前不能执行写操作，`update_plan` 仍仅用于已批准计划的状态更新。

同步删除因「拒绝计划」而开放 `finish_task`、跳过步骤／完成策略检查的专用捷径。明确停止／取消仍使用现有 Run 停止流程，不删除真正的运行取消能力，不把反馈当作停止按钮。

## 7. 前后端协议

沿用现有路由和身份校验，只直接切换相关枚举并补齐反馈字段：

| 接口 | 决定枚举 | 反馈与身份 |
| --- | --- | --- |
| `POST /runs/:id/plan-approval` | `approve | refuse` | 已有 `feedback`；保留 `interaction_id`、`plan_id`、`idempotency_key` |
| `POST /runs/:id/command-permission` | `allow_once | deny` | 新增 `feedback`；保留 `interaction_id`、`call_id`、`command_hash` |
| `POST /runs/:id/scope-expansion` | `approve | revise | refuse` | 新增 `feedback`；保留 `interaction_id`、`call_id`、`base_revision` |
| `POST /runs/:id/resource-edit-approvals/:interaction_id/decision` | `approve | reject` | 新增 `feedback`；保留 `interaction_id`、`call_id`、`revision` |
| `PUT /runs/:id/resource-edit-approvals/:interaction_id/draft` | 不提交决定 | 继续保存 `revision + draft`，返回更新后的草稿与修订 |
| `GET /runs/:id/resource-edit-approvals/:interaction_id` | 读取审批记录 | `answer` 包含可选 feedback，供重开和恢复展示 |

前端统一文案不要求后端不同业务的枚举同名。范围的 `revise` 继续表示立即授权全部页，含本 Run 创建的页，不是要求 Agent 重新提交申请；Reviewer 等其他业务中的 `revise` 也不在计划枚举删除范围内。

将新字段同步加入请求类型、对应 Answer、answered 公共事件、资源审批记录及前端 Timeline answer；命令和资源当前只有决定字符串的展示状态需扩为可携带反馈的结构。历史水合与实时 reducer 读取同一目标结构。

API 和 Runtime 均按目标枚举校验，计划不再接受 `revise`。保持交互归属、调用身份、哈希／基线修订的匹配检查。答案持久化后才能继续；相同身份与相同答案的重复请求幂等，改变决定或 feedback 的重复请求不能覆盖已提交答案。

checkpoint、交互队列持久化、重放与资源记录应保持决定和原文一致；恢复不得漏反馈、重复工具回复或重复写入。不为历史开发数据新增迁移、双读双写或旧拒绝行为降级。

## 8. 工具 Observation、定义与提示词

### 8.1 模型必须实际收到反馈

计划和范围审批通过原 `create_plan`／`request_privilege` 返回业务决定。计划输出枚举改成二选一；计划与范围的输出契约都描述可选 `feedback` 的用途及决定后的可用行为。范围拒绝摘要说明原范围保持，有反馈时另外保留原文。

命令拒绝与资源拒绝当前使用失败／阻止结果。`modelToolObservation` 对 `!OK` 通过 `toolResultError(...).ModelObservation()` 输出错误；最新代码会把 Data 中不覆盖错误身份的业务细节复制到错误投影。应利用这条真实链路保留独立的原文 feedback，更新已生成的 Observation，并同步错误契约及持久化／重放，不能只检查内部 Data 就认定模型已经收到反馈。

保留真实错误 code、授权边界和依赖失败语义。不能为了传反馈把拒绝改成虚假的工具成功，也不能污染一般参数错误、执行失败或其他无用户反馈的错误。成功资源编辑仍返回实际已保存资源，成功命令仍返回真实执行结果，不强制给所有成功工具虚构审批结构。

审批决定沿用已有用户来源的 Observation 元数据模式，包括没有反馈的决定；有反馈时保留原文，避免被当作 Agent 自己的提案或摘要。原工具回复、恢复重放及上下文压缩后仍须保留决定、反馈和权限含义，不披露内部草稿存储路径等运行元数据。

### 8.2 修改真正发送给模型的契约

检查工具注册、运行时披露、输出投影和 Provider 入口，更新实际 `ToolSchema`／`OutputSchema` 及 `ModelToolSchemas` 生成的模型可见说明。每个新增业务字段必须解释内容和用途；不以参考文档替代实际发送的契约，也不新增无用途的反馈输入参数给 Agent。当前工作区没有 `TOOL.md`，无需为本需求创建替代的全局工具文档。

涉及 `create_plan`、`request_privilege`、`run_command` 和受控资源编辑工具的审批结果、错误结果及描述。资源拒绝不得误写为内容已保存；命令拒绝不得误写为命令已执行。拆开当前计划／范围共用输出构造中不同的决定枚举，避免误删范围 `revise`。

同步 `backend/prompts/mode/plan.md`：删除「refuse 禁止重提并允许收尾」，写明拒绝当前方案后根据反馈修订、重新调用 `create_plan`、批准前只读。其他有关审批的模式提示词只在确有冲突时作相关调整，工具参考文档按真实实现更新。

以下文件保持完全不变：

- `backend/prompts/core/agent.md`
- `backend/prompts/core/output.md`
- `backend/prompts/core/reference.md`

如实施发现无法在工具定义、输出契约和模式提示词中解决的冲突，记录具体冲突交用户点名授权；不把本需求视作这些文件的修改授权。

## 10. 实施顺序与验收

建议依次完成：协议与持久化字段；计划状态机及工具披露／完成门禁；真实模型反馈投影及契约／模式提示词；草稿保存与最终批准拆分；Timeline 公共结构及各类选项；定向逻辑检查及用户手动验收清单。前后端以同一目标协议一次切换，不交付只改按钮、后端仍沿用旧语义的结果。

### 10.1 可由开发检查的关键逻辑

- 计划拒绝在有／无反馈时均保持未批准、恢复 planning、开放新提案；旧调用只返回一次，新提案等待新的批准；未经批准的写操作与拒绝后的直接收尾被门禁阻止。
- 命令、范围、资源拒绝的反馈经过答案存储、事件、checkpoint、恢复和真正的模型 Observation 后仍保留；命令不执行、范围不改变、资源不写入。
- 草稿保存／恢复不批准也不恢复 Run；最终批准使用最新已保存修订和真实 diff，重复答案幂等，过期修订与基线冲突不能覆盖项目。
- 前端目标类型与 SSE／历史还原一致；问题跳过不会计作回答；真实 Provider 工具描述包含更新后的输出字段和枚举。

只对上述状态机、恢复、幂等和反馈投影补充必要的定向测试；优先复用现有测试。小型视觉改动不新增测试，不运行全量测试。类型／编译检查和逻辑用例通过不能表述为 UI 或端到端验收通过。

### 10.2 用户手动界面与运行验收

1. 四类审批及用户问答均是工具行＋默认展开卡片，标签统一「待人工介入」；手动收起仍可定位待办，展开后选择、输入及问题位置不丢失。
2. 审批选项等宽、顺序正确，默认中性，只有选中项呈语义色；选择不会直接提交，继续没有箭头。范围的全部页选项仅在需要时出现。
3. 四类拒绝均能展开多行输入、带理由或空理由提交；切换选项不串反馈，请求失败可继续编辑；提交后可重开查看原文。
4. 资源手动编辑第一次继续进入画布，只有中性恢复／保存；保存后 Run 仍 waiting，正式项目无变化；回 Timeline 审阅最新 diff 再继续才写入并恢复执行。
5. 计划拒绝后 Agent 修订重提；新计划等待批准，旧提案与反馈保留。没有反馈也不会仅因拒绝自动结束，明确停止仍正常取消。
6. 问答内部操作和人工继续保持现状；长内容、窄栏、键盘操作、重复点击、刷新与后端重启恢复按真实使用检查。

遵守项目规定：不使用 Browser／Computer Use 自动化验证，不使用子代理；界面与实际运行验收由用户手动完成。实施交付应分别报告代码完成、定向检查结果、用户待验收项及真实阻塞，不宣称未执行的验收已通过。
