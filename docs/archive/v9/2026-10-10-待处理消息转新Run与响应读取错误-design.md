# 待处理消息转新 Run 与响应读取错误

## 已确认行为

原 Run 收到完成结果时正常结束。已经接受但尚未注入的消息不再因收尾被拒绝，而是按接受顺序进入一个新 Run。已经注入原 Run 的消息不重复执行。

- 第一条待处理消息成为新 Run 的主输入，其余消息进入新 Run 的 steering inbox，沿用正常的消费路径。
- 新 Run 使用原 Run 选择的模型、当前模式与资源配置；消息分别保留附件、DOM 引用和引用顺序。
- 所有转入消息属于新执行的初始输入：使用最新已接受范围，范围版本从 1 开始。
- 取消、失败和暂停不自动开启新 Run，保持对应停止语义。

## 收尾和持久化

先提交原 Run 的完成状态并释放项目执行锁，再创建新 Run。原活动句柄保留到转移结束，阻止普通新请求抢占该窗口。

新 Run 接受事件、幂等回执和消息转移在同一个数据库事务中提交。主消息标为已注入新 Run，其他消息的 inbox 引用转到新 Run；事务失败不消费原消息。`run.accepted` 记录来源 Run 和消息 ID，历史重放据此移除旧位置，再展示新 Run 的主输入和后续消息，避免重复。

启动时扫描已完成 Run 的待处理 inbox，补上完成与创建之间的进程中断窗口。新 Run 已接受后，重复扫描不会再次执行。单个启动失败会记录错误并保留消息，不阻止用户进入设置。

## 模型响应错误

读取响应体失败与 JSON 解码失败分别处理：

- 读取失败记录 `body_read_failed`，保留真实 cause、HTTP 状态、request ID、已读取字节数和摘要。
- 完成读取后才记录 `body_received`；JSON 格式、类型或大小错误记录 `body_decode_failed`。
- 诊断只公开固定错误类别，不输出 cause 的原始文本、URL、密钥或响应正文；`errors.Is/As` 仍可追踪真实原因。
- 读取阶段取消立即终止，包括最后一次尝试。非暂时性 HTTP 4xx 仍不重试，即使读取其错误正文失败。

## 保持现有重试时间

默认单次 HTTP 超时 180 秒。暂时性连接/读取错误、408、429、5xx 和无效 2xx 响应最多重试 1 次；重试前等待 200 毫秒。每个逻辑模型请求总预算为 6 分钟，包含重试、退避和一次备用模型切换，切换不重置截止时间。取消和预算耗尽停止后续尝试；下一逻辑请求或手动继续会获得新预算。

本次补充针对性的消息转移、事务回滚、历史展示和响应读取失败测试。按项目约定不执行自动测试、构建或浏览器验证，运行验收由用户手动完成。
