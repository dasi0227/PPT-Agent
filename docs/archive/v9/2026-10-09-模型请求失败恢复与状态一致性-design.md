# 模型请求失败恢复与状态一致性

日期：2026-10-09  
状态：已实施，定向逻辑测试、前端类型和相关文件 lint 检查已通过；实际界面及模型运行等待用户手动验收。

## 问题与依据

最新 RUN 在第 18 轮模型请求失败后终止，但错误卡片仍显示「正在尝试恢复」。原因是 `PROVIDER_UNAVAILABLE` 的固定错误文案描述了进行中的动作，而 Runtime 已发出终止事件。

同一错误原先归入 `run.error`，Runtime 和持久化层都会清除继续资格，前端也跳过异常状态的资格查询。因此已完成的页面保留了，用户却无法继续原任务。

依据当前前后端实现、最新的 [Timeline 人工介入设计](2026-10-09-Timeline人工介入统一与审批反馈-design.md) 和近期提交 `2b63f7f8`、`d2c9b0d3`、`47b9d2e0`。沿用现有卡片与继续流程，遵循 [UI 设计规范](../design/DESIGN.md)。

## 状态与展示

| 实际状态 | 事件与表现 |
| --- | --- |
| 自动重试已安排，正在等待或发送请求 | `run.progress` 的 `run.retrying` 显示重试进度 |
| 模型请求最终失败 | `run.failed`，正文「模型服务请求失败。」；清除进行中的进度 |
| 断点具备继续资格 | 查询服务端 `can_continue`，显示已有「继续执行」按钮 |
| 用户请求继续 | 禁止重复提交；服务端接受后恢复同一 RUN，并通过已有恢复事件展示运行状态 |
| 真正的内部异常 | 仍使用 `run.error`，保留错误原因；无有效恢复断点时不开放继续 |

`retryable` 表达错误的可重试性质，不表示正在重试，也不直接授权恢复 RUN。前端所有终止类型的按钮资格都以服务端 `can_continue` 为准。

错误注册表的公共文案只描述请求失败，不承诺正在恢复。终止卡片按 `PROVIDER_UNAVAILABLE` 错误代码使用同一终止文案，历史事件重放也不显示正在进行的恢复动作。

## 断点继续

`PROVIDER_UNAVAILABLE` 发生在获取模型响应时，该次响应中的工具尚未执行。将其归入可恢复的任务失败，保存最后可执行阶段的终止断点。

沿用现有恢复机制：

- 保留同一 RUN、Loop、批准计划、权限范围、已完成变更、证据和持久化工具观察。
- 从保存的执行阶段重新请求模型，重建当前上下文，不自动重放已完成工具。
- 继续前核对断点执行修订、最新项目运行记录、项目锁、模型路由配置及文件状态；冲突拒绝继续。
- 原子领取继续资格，防止重复恢复；新运行会使旧运行失去继续资格。
- 未保存可靠断点、请求格式错误、失效图片引用和内部异常不因 `retryable` 字段获得继续资格。

现有 SQLite 规则仅对 `run.error` 和被替代的停止事件强制清除继续资格。模型请求失败改发 `run.failed`，无需放宽这些保护规则。

不修改历史运行或设计迁移。此前已保存为不可继续的 RUN 仍不自动开放继续资格；新失败按新规则保存。

## 自动请求限制

- 所有 HTTP 暂时失败共用初次请求加一次重试的策略，包括传输异常、408、429、5xx 和无法解码的成功状态响应。
- 保留单次 HTTP 请求默认 180 秒超时；一轮逻辑模型请求总上限为 6 分钟，退避和主／备用模型请求共享该截止时间。调用方更短的截止时间优先。
- 配置了备用模型时，继续沿用既有的一次切换；每个模型最多两次 HTTP 尝试，切换不重置总时间。Runtime 重建备用模型请求时保留原请求截止时间。
- 成功取得响应后结束该请求预算，下一轮模型请求使用新预算。手动继续是用户发起的新请求预算，不自动无限恢复。
- 取消或预算耗尽后不继续发送重试请求，取消仍呈现为用户停止，超时呈现为模型请求失败。

补齐 `OnProviderRequest` 到真实 Provider 的连接，在内部 trace 记录 HTTP 尝试序号、阶段、状态码和耗时。诊断不记录请求地址、密钥或原始请求／响应体。

## 验证

定向检查覆盖：

- 不同暂时错误的重试上限、共享截止时间、退避期间取消和异常响应诊断。
- 备用模型重建请求时截止时间不重置。
- 请求失败的终止事件、公共错误文案、继续断点及用户取消的分类。
- 保留批准计划和已完成工具观察，继续时不重放已完成写入。
- SQLite 终止持久化、同一 RUN 继续、重复领取、新运行、内部异常和文件冲突的保护。
- 卡片文案、服务端按钮资格、重复点击与继续被拒绝，以及终止后清除重试进度。

未执行浏览器、Computer Use 或真实模型运行验证。用户重启服务后手动检查失败卡片和继续执行效果。
