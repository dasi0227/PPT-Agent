THE CENTRAL IDEA

这不是“让 LLM 直接写 PPT HTML”，而是单一 ReAct Agent 在受控工具面、证据账本和完成闸门内完成 PPT 变更。

最新 Runtime 将旧的多节点 PEV 编排收敛为一个由 RunIntent 约束的 ReAct loop：Agent 自主判断是否维护计划；模型提交 finish 后，系统用证据、范围、可选计划和版本基线决定能否真正 commit。

01 · 项目全景

项目有两条主线：前端是运行时间线与 PPT 预览消费者；后端把项目资料、模型工具调用、浏览器渲染和文件产物组织成一个可恢复、可验证的执行循环。学习时优先沿后端主线理解。

React 前端创建项目 / Thread / Run；订阅 SSE；预览 HTML 幻灯片。
→
HTTP API把 REST 请求转换为 Service 调用；提供 SSE / HITL / Cancel。
→
Run + Context建立 Run，装配本次任务可见的 ContextPack。
→
Intent-Bounded Runtime按 RunIntent 建立权限边界，并驱动单一 agent loop。
→
产物、证据与事件Blueprint / Design / HTML、render evidence、SQLite 事件与公开 SSE。
后端的边界：模型并不直接操作任意文件。它每一轮只能看到当前 phase 公开的工具；写入先进入 .staging/<runID>。系统不仅校验文件和版本冲突，还要求“修改后的最新内容”拥有对应的 schema / static / render / reference 证据，才允许提交。

02 · 先记住的六个概念

Task Contract

WorkSpec

一次 Run 的权威任务描述：用户指令、目标产物/层级、交互意图与选项。它先被校验，后续各层都以它为依据。

Bounded Context

ContextPack

不是“把仓库全塞给模型”。它按任务 profile 和 token 预算挑选 deck、目标页、设计、相关页、HTML 摘要、资产与记忆。

Authorization Boundary

RunIntent

talk、ask、plan 是只读授权，execute 是唯一写授权；Runtime 不再用关键词推导额外 Strategy。

Agent-Controlled Plan

Plan

execute Run 始终可调用 update_plan，由 Agent 判断是否需要。计划有版本、不可回退的 completed step 和最多一个 in-progress step；一旦创建就必须在完成前闭环。

Controlled Agency

Tool Disclosure

工具按 phase、interaction、风险与 target scope 动态公开。业务表面被收敛为 5 个 PPT 工具，另有 4 个 runtime control 工具。

Evidence-Gated Finish

Evidence Ledger + Completion Gate

工具产出带 source hash 的证据；后续写入会让证据失效。finish 是候选提交，只有证据新鲜、计划完成、范围合法才会被接受。

03 · 一次用户请求的端到端旅程

以“修改某一页 PPT HTML”为例。这里是理解全项目最重要的一张流程图。

  1. 前端创建 Run：POST /threads/{id}/runs 传入 instruction、target、interaction。
  2. RunService 规范任务：加载 Thread 和 Project，校验 WorkSpec 与 slide 归属，并创建当前 Run。
  3. ContextAssembler 生成 ContextPack：读取 Blueprint、Design、目标 HTML 摘要、资产和 Thread memory；记录 manifest 与预算。
  4. run.Engine 建立外壳：先持久化 Run 和 ContextManifest，再异步执行；同一 project 的 Run 通过锁串行。
  5. Runtime 建立授权边界：只读 Intent 进入 chat/planning phase；execute 进入唯一写能力 Harness Loop。
  6. 单一 ReAct loop：模型每轮获得当前上下文、可选计划、变更与证据，再调用一个已公开的业务或控制工具；是否创建计划由 Agent 自主决定。
  7. finish 不是直接成功：Completion Gate 检查 staged changes、scope、plan、版本基线与新鲜证据；通过才 commit，否则把可行动问题作为 observation 交还模型。
  8. 事件驱动 UI：runtime 只投影经过清洗的公共事件；Bus 做 schema、时序和因果校验，再持久化到 SQLite 并经 SSE 续传给前端。

05 · Intent-Bounded Runtime：一个 Loop，Agent 自主规划

workflow.Runtime.Run 是新总入口。它不再把“计划、执行、验证、修复”拆成 Go 编排节点，而是在一条 ReAct loop 内维护 phase、plan、staging changes、evidence、messages 和预算。

ContextPack + WorkSpec
interaction intent 与目标范围
→
talk / ask只读协作：进入 chat phase，只公开读取与沟通工具。
plan只读规划：进入 planning phase，输出可供后续 Run 执行的完整方案。
execute进入写能力 Harness Loop：既可直接执行，也可由 Agent 随时调用 update_plan 管理复杂工作。
05AAgent 自主编排流程workflow/runtime.go
RunIntent确定只读或写权限
→
Disclose按 intent + phase + scope 公开工具
→
Agent 判断直接行动或调用 update_plan
→
同一 Loop 执行计划可随进展创建和更新
→
Completion Gate有计划则必须完成，无计划也可安全结束
重要细节：计划是 Agent 的工作清单，不是权限令牌。创建计划不会扩大 target scope；需要越界资源时必须由用户提交新的授权范围。

06 · Context Engine：模型看到的是“任务相关的受预算上下文”

ContextAssembler.Assemble 是运行前的准备阶段。它把文件、数据库和历史记录整理为可追溯的 ContextPack，并生成 ContextManifest 作为审计凭据。

06A上下文装配流程contextengine/assembler.go
ValidateWorkSpec、Project ID、budget
→
Resolve Profile按 blueprint / presentation、deck / slide 决定装配策略
→
Load Canonical DataDeck、all slides、DesignSpec；先验证蓝图一致性
→
Add Relevant Data目标页、相邻页、HTML summary/ref、assets、memory、recent turns
→
Budget + Manifest按优先级丢弃可选段，计算 token / hash / refs

为什么需要 ContextManifest？

它记录每段上下文来自哪里、版本、hash、token 估算、选择理由、是否被丢弃。这使一次模型执行可以复盘：模型“当时到底看到了什么”。

为什么有 ContextRef？

大 HTML 不一定直接进入 prompt。PPT 工具 read_ppt 会按剩余预算返回完整 HTML，或退化为摘要与 manifest reference；search_refs 只在已授权的 context / memory / history / project 内检索。

07 · ReAct 主循环：真正的 Agent Harness

新 Runtime 的可靠性来自“模型可自主选择下一步，但系统拥有状态、工具面、预算与完成权”。核心只有一个循环：workflow.Runtime.Run。

07ARuntime phase 与状态拥有者workflow/runtime.go + domain.go
Initialize从 RunIntent 建立 phase、loop ID、scope、ledger、budget
→
Agent Choiceexecute 可直接行动，也可用 update_plan 创建清单
→
Executing每轮：补入 steering、可选 compact、公开 schemas、调用 agent
→
Control / Domain处理 update_plan、ask_user、review_completion、finish，或执行 PPT domain tool
→
Completion Checkfinish 被 gate 接受则 commit → terminal；否则 observation 回灌并继续

Runtime 持有什么？

loop ID、phase、scope、可选 plan、Transaction、EvidenceLedger、issues、messages、turn / tool / token 计数和 progress 去重状态。

模型拥有什么？

每轮只拿 ContextPack、当前计划、ChangeSet、Evidence 快照、对话 observation 与当轮公开工具 schema；它不能访问 runtime 内部路径或数据库。

预算与退出

默认上限为 128 turns、1 小时、5 次连续失败、3 次同状态 gate rejection；任何一个上限都会以结构化 outcome 结束。

07B每一轮 ReAct 的精确流程workflow/runtime.go
Checkpoint检查 cancel / turn / tool / duration budget；合并用户 steering
→
Disclose按 phase + interaction 计算本轮工具 schema
→
Agent.Next编译 system prompt + ContextPack + runtime snapshot，拿到文本或一个 tool call
→
Executecontrol call 由 Runtime 处理；domain call 交 ToolRegistry 执行
→
Observe记录 trace / evidence / invalidation / issues；将 tool result 作为 assistant + tool messages 回灌下一轮
关键变化：不再有旧的 Go Engine → StepExecutor → Verifier → Repair 线性流水线。验证被拆进 domain tool 产生的证据，以及 CompletionGate.Check 的最终一致性判断；模型被拒绝后可以据 issue 自行继续修复。

08 · PPT Tool Surface 与 Transaction：把模型的能力压缩为稳定协议

最新重构移除了 artifact-oriented 的旧工具集合，模型只认识统一的 PPT 领域表面。ToolRegistry.Disclose 决定本轮哪些 schema 可以看见，ToolRegistry.Execute 逐项重复执行授权检查。

08A工具公开与执行流程workflow/default_tools.go + tools.go
Register5 个 domain tools + runtime control schemas
→
Disclosephase / interaction 过滤；chat 和 planning 只有 read-only
→
Agent Call模型只能调用已公开 name
→
Execute Guard再次检查 disclosure、phase、intent、risk、session 和 declared target
→
Domain Result返回 domain-shaped data、changed targets、issues、evidence 与 invalidations

五个模型可见的业务工具

read_ppt 读取授权的全局模型或稳定 slide；write_ppt 完整创建/替换；edit_ppt 锚定编辑；search_refs 仅检索授权上下文；render_slide 以隔离 Chromium 进行视觉诊断。

四个 Runtime 控制工具

execute 中始终可选 update_plan；ask_user 发起结构化问题并 checkpoint 等待；review_completion 由 Agent 主动请求语义复核；finish 只提交“完成候选”，不会绕过 gate。

08B事务提交流程workflow/transaction.go
NewRunSessionexecute intent 创建受控写 Session
→
Write记录 before / after hash 与 tool source
→
Evidence写入使旧证据失效；schema / static / render / reference 工具为当前 hash 写入新证据
→

这层现在多了一层语义安全：Transaction 负责文件原子性；Evidence Ledger + Completion Gate 负责确认“这份暂存内容已经按其最新版本被检查”。例如 HTML/CSS 变更后，必须重新 render 每个受影响 slide 才能完成。

09 · Run Engine 与事件流：让一次 Agent 执行可控、可看、可恢复

run.Engine 是 workflow 的运行时外壳；它不承载业务推理，而是处理并发、生命周期、HITL、取消与广播。

09ARun 生命周期run/engine.go
StartWithContext创建 pending Run + 保存 ContextManifest
→
Public StartBus 先发并校验 run.started，再启动后台 goroutine
→
Project Lock + Runtime同项目串行；调用 workflow.Execution；可 cancel、steering、ask_user
→
Finish FallbackRuntime 正常投影 run.finished；外壳仅兜底补齐终态
→
Close关闭 Bus、移除 active handle

为什么按 Project 加锁？

文件产物属于 project 工作目录。同一 project 并行 Run 可能抢写同一 HTML；因此同项目串行、跨项目并行。

新的 HITL 在哪里？

ask_user 生成带 option schema 的 question.asked；InputQueue 只接受匹配 reply_to 且结构正确的 JSON answer，恢复时发 question.answered。

09B事件持久化与 SSE 续传run/bus.go + httpapi/run_handler.go
Runtime Projectreasoning / plan / milestone / tool / question / final 被转换为 public payload
→
Validate SchemaValidatePublicEvent 拒绝路径、HTML、raw reasoning 等敏感字段
→
Validate Sequencerun.started first；plan revision 单调；tool start/complete 配对；question 单 pending；completed 必有 final
→
Persist FirstSQLite event store；产品事件写 history.jsonl
→

观察性设计：这次重构的关键是将“内部 trace”和“用户可见 timeline”分开。trace.go 可记录内部诊断；SSE 只能承载版本化 public event contract，且会清洗 HTML、文件路径、系统提示词和推理链泄露。

10 · 存储与产物：SQLite 管“索引和运行态”，文件系统管“PPT 内容”

Canonical Project Files

文件系统工作目录

保存 deck / slide blueprints、design spec、物化后的 HTML slide、thread memory 和 staging。Blueprint 是结构化的规范层；HTML 是可预览的 presentation 层。

Operational Metadata

SQLite

保存 project、thread、run、event、slide metadata、asset index 和 workflow commit 元数据。它使列表、状态查询、SSE 回放和版本追踪可用。

→
Slide Blueprint每页内容语义与结构
→

→

11 · 建议的源码阅读顺序

不要一上来读所有工具实现。先追一条真实调用链，建立“谁调用谁、谁拥有状态、谁能写文件”的心智模型。

1
从 HTTP 到 Run：backend/internal/httpapi/run_handler.go → backend/internal/service/run.go → backend/internal/run/engine.go。确认一个 Run 怎样获得 ContextManifest、后台执行和项目锁。
2
理解输入和上下文：backend/internal/model/work_spec.go → backend/internal/contextengine/assembler.go。重点问：哪些信息会进入模型上下文，哪些仅以 ref 或 summary 形式存在？
3
从 Intent 进入 loop：backend/internal/workflow/runtime.go → prompt_modules.go。对照 talk / ask / plan / execute 四种 Intent，确认权限、phase 与可选计划如何组合。
4
读 ReAct loop 的两类工具：runtime.go 的 executeControl → tools.go。重点区分 agent 可调用的 control（计划/问人/复核/结束）和 domain（读写编辑渲染）。
5
读完成条件：completion.go → evidence.go → transaction.go。重点验证“先写后 render”为什么会产生新鲜证据，而改写后为什么旧证据必须失效。
6
读 PPT 与浏览器边界：ppt_tools.go → render_tool.go → backend/render-worker/worker.mjs。确认 HTML 如何进入受控写 Session、如何隔离渲染、如何回传截图与诊断。
7
最后读公共 timeline：model/public_event.go → workflow/public_events.go → run/bus.go → frontend/src/features/agent/eventReducer.ts。把后端公共事件与 UI 时间线逐项对照。
