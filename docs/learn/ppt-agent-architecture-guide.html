THE CENTRAL IDEA

这不是“让 LLM 直接写 PPT HTML”，而是让 LLM 在受控工作流里完成可验证的产物变更。

系统把一次用户指令收敛为明确目标与约束，组装上下文，选择执行强度；对复杂变更采用 Plan → Execute → Verify → Repair → Commit 的闭环，并把整个过程持久化、可续传地投影给前端。

01 · 项目全景

项目有两条主线：前端是工作台与事件消费者；后端负责把项目资料、模型推理和文件产物组织成一个可靠的运行时。学习时优先沿后端主线理解。

→
HTTP API把 REST 请求转换为 Service 调用；提供 SSE / HITL / Cancel。
→
Run + Context建立 Run，装配本次任务可见的 ContextPack。
→
Adaptive Runtime选择轻量回答、局部变更或完整 PEV Workflow。
→

后端的边界：模型并不直接操作任意文件。它只能看到当前 step 获准的工具；写入先进入 .staging/<runID>，验证和冲突检查通过后才提交到项目工作目录。

02 · 先记住的六个概念

Task Contract

WorkSpec

一次 Run 的权威任务描述：用户指令、目标产物/层级、交互意图与选项。它先被校验，后续各层都以它为依据。

Bounded Context

ContextPack

不是“把仓库全塞给模型”。它按任务 profile 和 token 预算挑选 deck、目标页、设计、相关页、HTML 摘要、资产与记忆。

Routing Decision

Strategy

根据只读/修改、范围、关键词、物化状态等信号，在 respond、direct action、compact workflow、full PEV 之间选择。

Executable Contract

WorkflowPlan

将任务变成带目标、依赖、能力、验证器和预算的步骤集合；有确定性 fallback，LLM 规划失败不致使系统失控。

Controlled Agency

Tool Selection

每个步骤只暴露“这个 stage + strategy + capability + target scope”共同允许的工具，工具结果再反馈给模型。

Safe Write Boundary

Transaction

一组产物在 staging 区写入、校验和记录 hash；commit 前再次检查源文件没有变化，失败会恢复已写入文件。

03 · 一次用户请求的端到端旅程

以“修改某一页 PPT HTML”为例。这里是理解全项目最重要的一张流程图。

  1. 前端创建 Run：POST /threads/{id}/runs 传入 instruction、target、interaction。
  2. RunService 规范任务：加载 Thread 和 Project，补默认交互策略，校验 WorkSpec 与 slide 归属。
  3. ContextAssembler 生成 ContextPack：读取 Blueprint、Design、目标 HTML 摘要、资产和 Thread memory；记录 manifest 与预算。
  4. run.Engine 建立外壳：先持久化 Run 和 ContextManifest，再异步执行；同一 project 的 Run 通过锁串行。
  5. AdaptiveRuntime 路由：只读任务直接答复；简单局部变更走 direct action；更复杂的任务进入 Workflow Engine。
  6. Workflow 执行：计划、逐 step 受限 ReAct tool loop、校验、必要时 repair，最终提交 staging 中的变更。
  7. 事件驱动 UI：每个阶段、工具调用、验证和产物提交都会进入 Bus → SQLite → SSE；断线时用 Last-Event-ID 补发。

05 · Adaptive Runtime：先决定要不要启动完整 Harness

workflow.AdaptiveRuntime 是总入口。它不是无条件执行长链路，而是先通过 ExecutionStrategyRouter 做成本/风险/复杂度权衡。

ContextPack + WorkSpec

→
respond咨询 / 只读：给模型只读上下文和分析 step，不生成正式 WorkflowPlan。
direct_action明确、低风险的单页局部修改：单 step + staging + 必要校验。若发现范围扩大或未产生变更，会升级。

full_pev整套、多页、全局、重排等高影响任务：跨产物计划、执行和验证。

06 · Context Engine：模型看到的是“任务相关的受预算上下文”

ContextAssembler.Assemble 是运行前的准备阶段。它把文件、数据库和历史记录整理为可追溯的 ContextPack，并生成 ContextManifest 作为审计凭据。

06A上下文装配流程contextengine/assembler.go
ValidateWorkSpec、Project ID、budget
→
Resolve Profile按 blueprint / presentation、deck / slide 决定装配策略
→
Load Canonical DataDeck、all slides、DesignSpec；先验证蓝图一致性
→
Add Relevant Data目标页、相邻页、HTML summary/ref、assets、memory、recent turns
→
Budget + Manifest按优先级丢弃可选段，计算 token / hash / refs

为什么需要 ContextManifest？

它记录每段上下文来自哪里、版本、hash、token 估算、选择理由、是否被丢弃。这使一次模型执行可以复盘：模型“当时到底看到了什么”。

为什么有 ContextRef？

大 HTML 不一定直接进入 prompt。它可被降级为摘要和不透明引用，模型需要细节时才通过 read_context_ref 在剩余预算内读取。

07 · PEV 主循环：真正的 Agent Harness

完整 Runtime 的可靠性来自一个显式状态机，而不是依赖模型“记得下一步应该做什么”。核心在 workflow.Engine.Run。

Plan

PlaybookFor 根据 WorkSpec 选择 playbook，生成 fallback plan；可选 LLM planner 的产物必须通过 ValidatePlan，否则回退。

Execute

按依赖顺序运行 steps。每一步带 targets、capabilities、verifiers、budget；每一步都发 started/completed/failed 事件。

Verify / Repair

Issue 的 error 与 fatal 会阻止提交。系统最多修复两轮，并且要求阻塞问题数确实下降，否则停止而不是盲目循环。

→

Harness 的关键约束：单个 step 的模型循环有 MaxStepTurns（默认 12）和 MaxToolFailures（默认 3）。工具失败、上下文取消和预算超限都有明确退出路径。

08 · Tools 与 Transaction：把模型的“能做什么”变成可检查的边界

工具不是全局常驻菜单。ToolSelector.Select 会对 ToolRegistry 做多重筛选，只有满足所有条件的工具才会连同 schema 一起交给模型。

典型读取能力

典型写入能力

09 · Run Engine 与事件流：让一次 Agent 执行可控、可看、可恢复

run.Engine 是 workflow 的运行时外壳；它不承载业务推理，而是处理并发、生命周期、HITL、取消与广播。

09ARun 生命周期run/engine.go
StartWithContext创建 pending Run + 保存 ContextManifest
→
Async Execute后台 goroutine 取得 project lock
→
Running调用 workflow.Execution；可取消、可 NeedsInput
→
Finish按 outcome 写 done / failed / canceled
→
Close关闭 Bus、移除 active handle

为什么按 Project 加锁？

文件产物属于 project 工作目录。同一 project 并行 Run 可能抢写同一 HTML；因此同项目串行、跨项目并行。

HITL 在哪里？

NeedsInput 会把 Run 置于等待语义，前端通过 POST /runs/{id}/input 回答；适用于 before-apply 或运行中阻塞。

Workflow Emitstage / step / tool / artifact / terminal
→
Bus分配连续 seq；终态只能出现一次
→
Persist First写 SQLite events；白名单写 history.jsonl
→

→
SSELast-Event-ID 先回放历史，再接实时流
观察性设计：history 只保存白名单事件，明确避免持久化隐藏的模型推理。前端仍可回放用户目标、策略、计划、工具、产物和最终结果。

10 · 存储与产物：SQLite 管“索引和运行态”，文件系统管“PPT 内容”

Canonical Project Files

文件系统工作目录

保存 deck / slide blueprints、design spec、物化后的 HTML slide、thread memory 和 staging。Blueprint 是结构化的规范层；HTML 是可预览的 presentation 层。

Operational Metadata

SQLite

保存 project、thread、run、event、slide metadata、asset index 和 workflow commit 元数据。它使列表、状态查询、SSE 回放和版本追踪可用。

10A从 Blueprint 到 HTML 的关系blueprint + service/workflow_commit.go
Deck Blueprint页序、主题、全局结构
→
Slide Blueprint每页内容语义与结构
→
Design Spec设计 token / layout 约束
→
Materialize / Revise生成或修改 HTML
→
Materialization State根据各 revision 判断 fresh / stale / unknown
理解方式：Blueprint / Design 是更接近“源代码”的 canonical inputs；HTML 是由它们物化而来的可交付表现层。上下文装配与策略路由会利用 materialization state 决定能否局部 patch 或必须 rebuild。

11 · 建议的源码阅读顺序

不要一上来读所有工具实现。先追一条真实调用链，建立“谁调用谁、谁拥有状态、谁能写文件”的心智模型。

1
从 HTTP 到 Run：backend/internal/httpapi/run_handler.go → backend/internal/service/run.go。先确认一个 Run 是怎样被创建的。
2
理解输入和上下文：backend/internal/model/work_spec.go → backend/internal/contextengine/assembler.go。重点问：哪些信息会进入模型上下文，哪些不会？
3
理解策略路由：backend/internal/workflow/strategy.go → adaptive.go。用不同用户指令手动模拟它会选哪一条路径。
4
读完整 PEV：backend/internal/workflow/engine.go → plan.go → playbooks.go → verifiers.go。重点追 Stage 和 fail/repair 分支。
5
读模型执行边界：executor.go → tools.go → builtin_tools.go → transaction.go。重点确认每个写操作如何被 scoped 与 staged。
6
最后读运行与前端投影：backend/internal/run/engine.go → bus.go → frontend/src/features/agent/eventReducer.ts。把后端 event 与 UI 时间线一一对照。
