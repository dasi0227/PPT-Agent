# 重复读取无进展终止规则与渲染图片循环分析

> 后续实施：已根据用户决定落实 [Run 内已读图片保留](2026-09-29-run-image-retention-design.md)。下面的单轮图片生命周期描述属于故障发生时的历史实现；工作账本、计划推进和 timeline 的分析建议尚未实施。

## 事件结论

2026-09-29 的 Run `d4948721-a19b-4b09-9f4f-0d4bfb623231` 在 01:58:25 因 `RUNTIME_BUDGET_EXCEEDED` 停止，执行了 128 轮。

- 110 次读图都成功，重复阶段没有新写入、重新渲染、计划更新、完成检查或 `finish`，也没有模型输出的文字视觉结论。
- 重复阶段 106 次模型请求的输入估算合计为 7,582,301 token，单次估算从 54,274 增至 86,185。整个 Run 的 128 次请求估算合计为 8,282,194。它们是日志中的输入估算累加，不是实际账单，也没有扣除供应商缓存计费差异。
- 已成功写入的页面保留在项目中；终止仅回滚当前未提交操作。

证据来源为 `.run/backend.log`、该项目线程的 `thread.jsonl` / payload、渲染索引与 PNG 文件、SQLite 中的 Run 模型记录。

## 最近图片改动的影响

`e618a24a`（2026-09-29，附件扁平存储）将上传附件从 `attachments/<id>/original.*` / `thumbnail.webp` 改为 `attachments/<id>.png|jpg|webp`，同步了附件服务、导出快照、附件测试与 HTML 嵌入提示词。

渲染图继续使用 `.runtime/renders/<run_id>/<screenshot_id>.png` 和 `.runtime/render-index/`。`read_image(image_path)` 进入 `renderimage` 分支；`runImageResolver` 先处理 `project:<id>/render:...`，再处理上传附件。此次四页 HTML 未引用上传附件，因此附件布局变动没有参与此次截图生成与读取。依赖旧附件路径的历史 HTML 仍可能受附件路径切换影响，但不是本次循环。

限制截图只对下一次成功模型响应可见的机制来自 `b1ce3d1c`（2026-09-22），不是最新附件提交。代码在 `Agent.Next` 成功返回之后才移除图片；Anthropic 适配器将图片以 base64 image block 放入 tool_result，不是仅传文件路径。这个生命周期要求 Agent 在看完后保留文字结论，本次模型没有做到。

本次模型记录为 MiMo Flash / `mimo-v2.6-flash`，当前配置使用 Anthropic 协议。该适配器不返回 provider continuation，每次发送完整 messages，故 `render_images_released` 中清除 continuation 不构成本次异常的直接原因。先前将 continuation 清除列为可能诱因的判断在这里修正。

可以确定的原因是成功读图循环没有产生任务进展，且 Runtime 只有总轮次、时长、连续工具失败、重复完成检查拒绝等上限，无法提前识别这种成功调用循环。单轮图片生命周期与没有文字观察共同形成重复读取的条件。现有记录没有供应商原始多模态处理记录，不能进一步断言模型为何选择重读，也不能将其认定为服务端未收到或忽略图片。

## 后续深挖：为什么停在读图，为什么 Plan 不再更新

本节以线程持久化的 `model.edit`、工具响应、`plan.updated` 为依据重建模型对话。仅统计后端 `tool.called` 不足以判断是否调用计划工具，因为 Runtime 控制动作不走普通业务工具的同一追踪路径。排查期间后端被重新启动，`.run/backend.log` 已轮换；以下事件仍可从该线程 `thread.jsonl` 及其 payload 复核。

### Plan 实际更新过两次，之后停留在封面步骤

以下时间均为 2026-09-29 UTC+8：

| 时间 | 模型动作与结果 |
| --- | --- |
| 01:47:29 | 把 `update_plan` 和 `edit_manifest` 放在同一响应，触发 `INVALID_CONTROL_CALL`，该批未执行。 |
| 01:47:32 | 单独重试 `update_plan` 成功，初始化步骤变为 `in_progress`。 |
| 01:48:12 | 四页 `edit_spec` 完成，Runtime 向模型发布四页均为 `done` 的工作账本；此时尚未写入 HTML。 |
| 01:49:11 | 把 `update_plan` 和四次 `write_html` 放在同一响应，再次整批被拒绝。 |
| 01:49:12 | 单独重试 `update_plan` 成功，初始化变为 `completed`，封面变为 `in_progress`。 |
| 随后 | 逐页完成四次 HTML 写入、渲染和首次读图，未再更新 Plan。 |
| 01:50:21 起 | 在前两页间交替重读 106 次，未产生视觉结论、页面修改或 Plan 更新。 |

因此，准确描述是“模型在开始写页面后没有继续维护计划”，不是“计划接口一直失败”。两次调用格式错误均被模型修复。最终状态仍为初始化完成、封面进行中、另外三页及目检待开始；持久化后端状态本身如此，不是前端漏刷新。

执行期 `update_plan` 一直可用，修改步骤状态不需要再次授权。执行计划只允许改变状态、不允许改变已批准的结构，也不妨碍此次应做的完成标记。

### 确定的状态问题：一次写操作成功被表示为整页 done

`runtime.go` 对所有非只读业务工具提取页面 ID，先调用 `WorkLedger.MarkRunning`，再根据工具成功与否调用 `WorkLedger.Complete`。`work_ledger.go` 中 `Complete(..., true, ...)` 直接将页面状态设为 `done`。这包含 `edit_spec`，没有判断该页 HTML、渲染或用户承诺是否完成。

本次对话 `msg_ttj4hy` 明确包含四页 `status: done`，出现在四页规格写入之后、首次 HTML 写入之前。这不是单纯的日志命名：它作为 `task/work_ledger` 送给了模型，而执行提示词要求模型继续待办页面、只在新增需求或缺陷等情况下重访完成页面。

新建项目在计划阶段尚无页面 ID，六个计划步骤均没有 `target_slide_ids`。后续页面工作项也没有 `plan_step_id`，不能把页面操作映射回对应计划步骤。由此形成三套未闭合的状态：Plan 仍在封面、工作账本四页完成、渲染证据逐页增加。账本的 `done` 实际代表最近一次写操作成功，却以任务进度的形式呈现，具有误导性；应与真实页面交付状态区分。

### 与循环高度吻合的机制：图片信息没有转化为可持续的检查结果

图片在 `Agent.Next` 成功返回后被 `WithoutRenderImages` 移除；路径、源码哈希和 `stale` 等文字仍保留。此 Anthropic 接入每次重发 messages，没有 continuation 保存之前图片的视觉信息。

本次每轮只读一张图，且读图后的模型响应没有任何文字视觉结论。因此当模型读 B 时，下一次请求只含 B 的像素，A 只剩路径；再读 A 时又失去 B 的像素。对需要跨页判断风格一致性的任务，这提供了 A→B→A→B 振荡的条件。实际调用序列正好如此，但记录不能证明模型主观上确实是在做跨页比较。

`read_image` 成功只返回图片及引用信息，不记录“已检查、检查结论、剩余问题”。`latest_rendered_images` 是资源索引，也不表达视觉检查完成。历史提示词已经要求读图后记录文字发现，模型没有遵守；当时 Runtime 也没有检查这项缺失或推进视觉检查状态。不能把“读图成功”自动当成“视觉质量通过”。

### 为什么没有被拉回 Plan

- Plan 状态不会随着 `write_html`、`render_slide` 或 `read_image` 自动推进，依赖模型主动调用 `update_plan`。
- `prepareAgentRequest` 对内容未变化的上下文不重复追加。最后一次计划状态位于重建对话的索引 66，进入循环后不断被新工具消息推远；未被截断，但也没有在阶段切换时得到新的进度提醒。
- `CompletionGate.Check` 只有在模型调用 `finish` 后才用 `PLAN_NOT_COMPLETE` 要求补齐步骤。这次模型从未调用 `finish`，该反馈无法介入读图循环。
- 两次错误混用控制工具和写入工具增加了无效历史，第二次还包含四页完整 HTML；模型修复调用后继续写页面，但没有恢复逐步更新计划的行为。这是已观察到的协议遵循问题，不能证明模型从此不敢调用计划工具。

综上，可确定的是状态表达失真、视觉结论缺失，以及计划维护和完成反馈缺少运行中的衔接；单轮像素生命周期与这些问题一起，为本次重复读图提供了持续条件。无法从现有记录确定模型选择重复动作的内部推理，也没有依据归因于最新附件存储改动、截图过期、计划工具被隐藏或供应商必然不支持图片。

### 后续修复方向（本节为分析，尚未实施）

1. 修正工作账本语义：页面规格、HTML 写入、渲染和真实任务完成应按实际需求表达，不能任意成功写入就表示整页完成；为新建页面建立与任务步骤的运行期关联。
2. 用户后续决定让整个 Run 的已读图片持续可见，已经实施，见文首链接。视觉检查结论和页面任务完成的关联仍属后续工作。
3. 在阶段变化或已有证据与 Plan 明显脱节时提供简短、具体的推进反馈，引导模型更新状态或说明未完成原因，不能仅在 `finish` 时检查；也不能仅凭写入或渲染成功自动宣告语义任务完成。
4. 保留已增加的重复读取终止规则作为费用上限保护。该规则负责止损，以上修复负责减少进入循环的机会。

## 新增终止规则

新增错误码 `REPEATED_READ_NO_PROGRESS`：连续 6 个工具响应轮次仅重复已经成功读取的相同内容，且没有任务状态进展时，立即终止，停止后续模型调用。

- 对成功只读调用记录“工具名 + 规范化参数 + 返回内容”的指纹，忽略调用 ID；包括渲染图片引用和文字 observation。
- 首次读取、新资源、返回内容变化打断连续重复计数。A→B→A→B 等交替重复同样计数；同一批多个读取只计一轮。
- 文件变化、计划内容或步骤状态变化、权限范围变化、新渲染证据/截图索引变化清空旧观察；用户追加输入或回答问题也清空。普通助手文案、时间流逝、图片释放和上下文压缩不算进展。
- 检测在工具响应落入历史后、下次模型调用前执行，不额外请求模型进行判断。保留至多 64 个观察指纹，检查点不保存第二份工具正文或图片字节。
- 失败使用现有任务失败事件和中文原因，保留已经保存的修改与可继续检查点。用户明确继续时重新开始检测额度，并向模型保留停止原因；不自动继续。
- 执行提示词要求记录具体视觉结论，并使用 Run 中已经保留的图片，避免反复读取相同内容。

此规则针对重复成功读取；不同参数不断制造新结果、反复执行有副作用的写操作、不断生成新截图等其他无进展形式仍受已有总轮次/时长限制，不能将这条检测描述成覆盖所有类型的死循环。6 轮为本次默认阈值，可在后续真实案例中调整。
