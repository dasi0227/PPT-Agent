# Kickoff 讨论结论提炼与 Handoff 接续上下文

日期：2026-09-22。依据用户本次确认的设计，替代 `2026-09-04-slash-commands-design.md` 中简报复用 Polish 上下文的临时约定，并更新命令结果协议文档中的正文定位与输出预算。结果工具、HTTP、存储、版本修订及新建会话草稿协议保持现状。

## 产品行为

Kickoff 把当前讨论已经明确的任务整理成可直接发送给新会话的首次用户输入。接手者无需重新经历讨论，但应知道任务及原因、已定方向与边界、必要参考和预期结果。输出以用户下达任务的口吻直接表达，不附来源说明、命令介绍或生成过程。

这些内容不是固定必填章节，可以合并为几段自然语言或短列表。保留标准是：删掉某条信息是否会改变接手者的重要决定。通常中文约 300–600 字，简单任务更短，复杂任务可增加必要约束与引用；不为了凑字数扩写，也不硬截正文。省略讨论流水账、完整实施计划、通用验收清单及无关项目背景。

必须将助手提出的方案与用户反馈一起理解。助手建议、提交过的计划、旧生成摘要均不自动等于用户确认；最新明确决定优先。保留关键选择的原因，只有能避免重走弯路时才保留被否决方案。遵循用户确定的下一阶段：先分析、先原型、先计划或直接实施；生成 kickoff 本身不改变授权阶段。参考文件须来自已有输入，并说明用途，关键结论不能仅由文件引用代替。

Handoff 用于交接实际工作状态：必要背景、已完成事项、未完成事项、重要失败、验证边界及下一步。可以比 kickoff 长，但不复制日志或重写计划。任务已经完成时明确说明，不编造后续任务。写入成功、HTML 已生成、视觉检查和导出成功是不同事实。

## 上下文来源

`AssembleBriefing` 使用独立 `BriefingContext`，不再调用 `AssemblePolish`，因此不影响润色功能。

- 读取当前持久模型 transcript 中的用户和助手文本，不限制为最后四条，也不按 500 字节截断；保留多段文本和段落结构。
- 单独携带已有 `context_summary`，标明其为可能不完整的历史摘要。模型历史已经压缩过时，不宣称可以恢复原始完整讨论。
- 保留 `create_plan`、`update_plan`、`ask_user` 的提案／问题及对应结果，避免丢失通过工具提交的方案和用户选择。源会话计划批准仅作为历史事实；丢弃催促调用终态工具的运行时指令。
- 保留图片引用与说明，不附图片二进制、不宣称视觉识别；DOM 选择保留标识、页面、版本、意图及目标摘要，省略原始 HTML 快照。
- 项目资源包括清单、大纲、设计和页面概要的准确相对路径，用于补充现状与定位资料，不从项目概况自行构造任务。
- Handoff 额外携带模型历史中可用的非读取工具结果及必要定位参数，不复制写入 payload；每项保留所属讨论轮次。页面概要额外读取当前物化状态。工具结果仍是历史证据，物化状态不能证明视觉检查或导出。
- 历史文件损坏等读取错误向上传递，不能静默当作空历史；确实缺少讨论时明确提示模型不得猜测任务。

全部动态输入仍作为不可信参考数据放在 user 层，不能覆盖系统规则。生成结果继续通过单次 `kickoff_thread`／`handoff_thread` 工具调用提交。

## 预算与裁剪

简报基础上下文的默认估算上限为 24,000 token。若所选模型窗口较小，扣除系统提示词、结果工具、完整修订输入、输出预算及 1,024 token 余量后进一步收紧。Kickoff 输出预算 3,000 token，Handoff 保留 6,000 token；正文字符校验上限保持现有 40,000，简洁度主要由生成要求控制，不截断生成后的结果。

Handoff 的执行观察先限制在约 6,000 输入 token 内，超出时优先保留近期观察；单条过长参数或结果使用带省略标记的 Unicode 安全首尾摘录。

基础上下文超预算时按顺序处理：

1. 缩减项目资源正文，保留引用。
2. 移除较早的补充执行观察。
3. 按完整讨论轮次移除较早的中间讨论，保留开场轮次、已有摘要及至少最近两轮，以保留最近确认所指的方案。
4. 必要时对特别长的消息或摘要保留首尾，显式标明省略；最后才缩减页面资源索引。

裁剪均附输入警告，不声称无损提炼，也不能将缺少证据解释成“没有发生”或“已经完成”。如果预算小到无法保留基本讨论，返回错误而不是生成空任务。内容相关性的最终取舍由生成模型根据可用讨论完成；确定性预算裁剪不冒充语义判断。

## 验证交接

按仓库约定，未运行自动化测试或浏览器验证。为容易回归的历史保留、输入裁剪和请求预算补充了行为测试，用户可在 `backend` 目录手动执行：

```sh
go test ./internal/contextengine ./internal/service -run 'Test(Briefing|Kickoff)' -count=1
```

人工检查建议使用同一任务分别生成 kickoff 和 handoff：

- 多轮比较方案后只回复“第二种，先出原型”，kickoff 应保留方案含义和原型阶段，不扩展为实施。
- 最新纠正旧决定、引用文件、附图或圈选后生成，确认关键约束与引用用途被保留，正文自然简洁。
- 已压缩或超长对话不应编造遗漏决定；带反馈修订仍输出完整替代文本。
- 实际完成部分工作、出现失败或未验证结果时，handoff 应区分这些状态，kickoff 不应变成执行日志。
- 新建会话仍只把正文放入输入框，发送后是普通首次用户消息。
