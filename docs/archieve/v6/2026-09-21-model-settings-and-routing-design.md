## 1. 目标与范围

新增全局设置后端，支持在页面管理共享模型配置，为主路和各旁路分配模型。用户点击页面保存后，配置写入 `backend/config.yaml`，后端无需重启即可供新任务使用。运行中的任务保持自身配置快照。

主路和旁路分别具有默认模型与可选备用模型。原模型按既有策略重试仍失败时，才接替到备用模型。主路接替在当前一轮 Run 内持续有效，下一轮重新从用户选择或主路默认模型开始。

本期覆盖模型库增删改、整页配置读写、校验、热更新、六项旁路接入、故障接替、模型选择与事件投影。不增加温度、推理强度、供应商自定义 URL、连通性测试按钮、密钥托管、自动探测模型列表、跨进程配置服务或配置文件监听器。

现有适配器支持 `openai / deepseek / kimi`。前端演示下载 Claude、Gemini 等品牌素材不等于后端支持相应供应商；供应商扩展必须另行落实适配器和能力信息，不因存在图标而接受未知 provider。

本次实现包括生产设置页面、配置管理接口、主旁路快照路由、故障接替与状态投影，并已同步实际开发配置和示例。保留独立卡片演示用于对照；未操作运行中服务。

## 3. 唯一 YAML 结构

```yaml
llm:
  - name: 主力模型
    provider: openai
    model: gpt-5
    key: sk-your-main-key
  - name: 轻量模型
    provider: kimi
    model: kimi-k3
    key: sk-your-side-key
  - name: 备用模型
    provider: deepseek
    model: deepseek-v4-pro
    key: sk-your-backup-key

main-road:
  default: 主力模型
  fallback: 备用模型

side-road:
  default: 轻量模型
  fallback: 备用模型
  rename:
  compact:
  commit:
  polish:
  handoff:
  kickoff:
```

示例模型标识仅演示结构，不意味着可用性承诺。实际值由用户填写。

### 3.1 模型库

- `llm` 是有序列表，至少一个条目；列表顺序供 UI 展示使用。
- 每条只有 `name / provider / model / key`。name 是可编辑的显示名，也是 YAML 内唯一引用标识；不新增永久 ID。
- name 去除首尾空白后长度为 1–80 个 Unicode 字符，禁止控制字符，大小写敏感且全局唯一。
- provider 为现有受支持的固定枚举；model、key 必填，去除首尾空白，禁止内部换行和控制字符。name/model/key 均为短文本单值，前端使用单行输入框，key 默认以密码形式遮蔽。
- 允许不同名称引用同一 provider/model，也允许使用不同 key；不自动合并这些条目。
- Key 保留于本地配置文件，不进入聊天模型列表、日志、事件、运行记录或示例文件。

### 3.2 道路与引用

- `main-road.default`、`side-road.default` 必填，必须精确引用有效 name。
- 两个 fallback 可省略或为空；空值统一表示不配置备用模型。
- 六项用途可省略、为 null 或空字符串；统一表示继承 `side-road.default`，不是关闭该功能。
- 指定了用途模型时直接使用该模型；失败后只尝试 `side-road.fallback`，不插入 side-road.default 作为第二层接替。
- 所有非空引用必须有效。未知字段或用途名称应拒绝，避免拼写错误被忽略。
- fallback 与本次实际首选模型名称相同时跳过接替，不重复执行同一个模型的整套重试。

### 3.3 编辑行为

重命名应同时替换页面草稿中主路、旁路以及用途的全部引用，再整体提交。后端只接受引用闭合的完整结果，不能分两次保存而形成悬空引用。

模型被引用时 UI 要求先改分配或清除可选分配；后端以保存后的完整文档为准：一次请求同时解除引用并删除合法，删除后仍存在引用则失败。最后一个模型不可删除。

按项目规范直接切换结构，同时更新实际开发配置和 `config.example.yaml`；不提供旧结构读取、双写、历史开发数据迁移或环境变量密钥回退。

## 4. 模型解析与生命周期

### 4.1 主路

解析顺序：有效的显式手选 → `main-road.default`。

聊天区提供 `llm` 的全部模型。用户修改全局 default 时，保留有效手选；没有手选时立即反映新 default。被删除的手选在列表刷新后恢复默认；同一设置页内重命名时同步更新该手选。

实现时须区分「用户明确选了某个名称」与「界面为了显示而填入的默认名称」，不能只凭当前名称是否存在判定手选。自动使用默认模型的主路请求省略 model；手选才显式传 name。

服务端收到非空但不存在的显式 model 时返回 `MODEL_PROFILE_NOT_FOUND`，不静默替换。前端刷新配置、恢复 default 后由用户重新发起；这样可避免并发删除后的请求意外使用另一模型。

一轮定义为一个 Run，包括其工具循环和同一 Run 内的暂停/继续。Run 启动时捕获配置快照，解析首选与备用；接替后该 Run 后续主路模型调用持续使用备用模型。下一次新建 Run 重新解析，不修改用户选择或磁盘配置。

### 4.2 旁路

| 用途 | 实际调用范围 | 首选模型 |
| --- | --- | --- |
| rename | 自动命名、显式立即命名 | rename 或旁路 default |
| compact | 自动压缩、手动压缩 | compact 或旁路 default |
| commit | 提交说明生成 | commit 或旁路 default |
| polish | 输入润色 | polish 或旁路 default |
| handoff | 交接内容生成及修订 | handoff 或旁路 default |
| kickoff | 启动内容生成及修订 | kickoff 或旁路 default |

这些请求不再使用聊天区选中模型。实施时删除旁路请求中承担模型选择作用的 model 字段，前后端同步切换，不接受旧字段覆盖旁路设置。

独立旁路操作在实际启动时捕获快照；排队但尚未开始的命名采用开始时的版本。自动压缩属于当前 Run，使用该 Run 已捕获快照中的 compact 路由；因此设置热更新不改变在途 Run 的压缩模型。

每次独立旁路操作都有自己的首选与备用状态；后续新操作重新从用途首选开始。主路切换 fallback 不影响 compact 或其他旁路的选择；旁路失败也不触发主路模型切换。

### 4.3 接替规则

```text
本次首选模型
  ├─ 成功：继续
  ├─ 可恢复失败：先耗尽已有供应商重试
  │    ├─ 可用且不同的 fallback：调用备用模型，沿用其既有重试
  │    │    ├─ 成功：当前操作继续；主路本轮保持备用
  │    │    └─ 失败：报告失败，不再切换
  │    └─ 无 fallback：报告失败
  └─ 不可恢复错误 / 用户取消 / 总时限耗尽：停止
```

- 可恢复范围沿用供应商层 `ErrUnavailable` 分类，包括网络、请求级超时、408、429、5xx 和可归类为临时上游故障的响应解码问题。
- 认证、权限、参数、未支持能力等配置或请求错误直接返回，不将所有错误统一当作可接替故障。
- 业务输出校验失败（例如命名格式不合法）沿用该业务原有有限修复策略，不擅自升级为通用 fallback；已有业务补救不能重置整条接替状态。
- 供应商层负责原有重试，路由层只负责至多一次模型接替，不额外套一层重试放大请求数。
- 备用调用仍处于原操作的取消与总时限内。若原重试已耗尽整个时间预算，直接结束，不能复活已取消 context，也不承诺每次故障都能实际执行 fallback。
- 接替仅重做失败的模型生成步骤，不能重启 Run 或重放已执行工具；commit 只能重做提交说明生成，绝不重做已经完成的 Git 操作。

### 4.4 跨模型切换正确性

不能简单在 Provider.Generate 外层捕获错误后把完全相同的供应商请求转发给另一 Provider：

1. 保留完整的供应商无关消息、工具调用与结果链，但清除原模型私有 continuation、response ID 和私有推理字段。
2. 使用备用模型的能力重新组装请求，重新计算上下文窗口、输入预算和可用输出预算。
3. 主路接替先落检查点，再回到认知循环重新估算，并通过同一快照的 compact 旁路按原有语义压缩；压缩后仍超限则明确失败。独立旁路调用在发送备用请求前校验窗口，无法容纳时直接失败，不递归触发压缩；不能静默丢弃图片或用户材料。
4. 备用模型无法满足当前图像或工具能力时明确失败；配置允许保存，但运行时不伪装成已接替成功。
5. 下一次调用使用备用 Provider 返回的新 continuation。记录实际模型和 token 使用，不能继续套用原模型的窗口上限。

模型选择状态留在每个 Run/旁路操作中，不能写进共享 Registry 或全局 Provider；并发会话之间不得传播 fallback 状态。

## 5. 配置管理器与热更新

`llm.ModelConfigManager` 统一拥有配置文件绝对路径、当前不可变快照和保存互斥锁。注入服务的根 Registry 委托管理器读取当前快照，操作持有的 Registry 快照自身保持不变。

快照至少包含：配置 revision、规范化配置、全部已构造的模型适配器、两条道路和用途的解析结果。所有保存前置工作完成后才发布新快照；运行时不就地修改已发布对象。

配置文件路径在启动时解析为绝对路径，后续 API 不接受任意文件路径。所有相关服务通过根 Registry 访问管理器，不继续长期持有启动时的固定 Provider。任务启动只取得一次完整快照；读写切换使用短临界区，不能把网络调用放入全局锁内。

### 5.1 整体保存流程

1. 加保存锁，核对客户端 revision；同时核对磁盘文件是否被外部改写。
2. 解析请求，以当前配置合并未修改的密钥，规范化并全量校验。
3. 构建新 Registry、路由和不可变快照；此阶段不发起付费模型请求，也不把本地格式合法等同于密钥有效。
4. 将完整 YAML 写入配置文件同目录的临时文件，权限设为 `0600`；完成写入、同步、关闭后原子 rename 替换目标文件。
5. 在同一配置发布临界区切换内存快照，生成新 revision，然后释放锁并返回脱敏结果。文件替换后的发布步骤不得再包含网络调用或可能失败的适配器构建。

校验、构建、写入或 rename 失败时不发布候选快照，保留旧配置和可继续使用的页面草稿，清理本次临时文件。进程在 rename 后异常退出时，重启读取已落盘的新配置。

配置保存不等待旧 Run 完成。旧快照由在途操作持有，引用释放后自然回收；删除模型或更改 key 不会中断已持有旧快照的任务。

### 5.2 文件变更与并发边界

本期不加文件监听。页面保存和设置刷新均为热更新入口：手工编辑 YAML 后，进入设置页、刷新该页面或点击右上角刷新按钮，会重新读取、校验文件并发布新快照，无需重启。普通 GET 设置仍返回当前生效快照。无效文件不替换内存配置，页面刷新失败时保留已有草稿。

两个页面保存同一版本时，只允许首个成功；后者返回版本冲突，保留本地草稿并提示重新读取。若检测到磁盘被外部修改，则拒绝覆盖，提示点击设置页右上角刷新，加载文件后重新编辑保存。内部磁盘指纹不含明文日志输出，API revision 使用不含密钥信息的不透明值。

## 6. 设置接口与密钥契约

### 6.1 GET `/api/v1/settings/models`

返回当前 revision、可选供应商、完整共享模型列表及道路配置。JSON 使用下划线字段，YAML 使用上文的连字符字段，由后端统一转换。

```json
{
  "revision": "opaque-revision",
  "providers": ["openai", "deepseek", "kimi"],
  "llm": [
    {"name": "主力模型", "provider": "openai", "model": "gpt-5", "has_key": true}
  ],
  "main_road": {"default": "主力模型", "fallback": ""},
  "side_road": {
    "default": "主力模型", "fallback": "",
    "rename": "", "compact": "", "commit": "",
    "polish": "", "handoff": "", "kickoff": ""
  }
}
```

读取时可选分配统一返回空字符串；写入时省略、null 与空字符串均表示不设置该可选分配。

不返回原始 key 或可用于重新提交的假掩码。UI 显示「已配置，留空保留」，用户可输入替换值；显示/隐藏按钮只作用于本次新输入，不提供读取旧密钥的额外接口。返回 `Cache-Control: no-store`。

### 6.2 PUT `/api/v1/settings/models`

单一全量提交入口，包含 revision、完整 llm、main_road、side_road。此接口同时支持新增、编辑、重命名、删除和分配，不拆成容易形成短暂无效状态的单字段写接口。

```json
{
  "revision": "opaque-revision",
  "llm": [
    {"previous_name": "主力模型", "name": "主力模型", "provider": "openai", "model": "gpt-5"},
    {"name": "备用模型", "provider": "kimi", "model": "kimi-k3", "key": "sk-replacement-example"}
  ],
  "main_road": {"default": "主力模型", "fallback": "备用模型"},
  "side_road": {
    "default": "备用模型", "fallback": "主力模型",
    "rename": "", "compact": "", "commit": "",
    "polish": "", "handoff": "", "kickoff": ""
  }
}
```

密钥更新规则：

- 新增条目必须提交非空 key。
- 现有条目使用 `previous_name` 指明当前 revision 中的原条目，key 缺省表示保留；名称变更时同样适用。
- 显式空 key 不代表保留，校验失败；UI 将「未修改密钥」序列化为不带 key，而非空字符串或掩码。
- 切换 provider 必须重新提供 key；只改 name/model 可以保留。
- previous_name 必须存在且在本次请求中最多引用一次，避免重命名或复制时错误复用密钥；它仅为 API 编辑身份，不写入 YAML。
- 完整目标列表中被省略的原条目即被删除。服务端基于最终文档校验引用，不推测用户希望自动替换成哪个模型。

成功返回 200 和新的脱敏设置对象。关键失败码为：`SETTINGS_INVALID`（400，包含安全字段路径）、`SETTINGS_REVISION_CONFLICT`（409）、`SETTINGS_FILE_CHANGED`（409）、`SETTINGS_WRITE_FAILED`（500）。沿用项目现有统一错误 envelope；禁止将解析原文、key、请求 body 或供应商原始负载加入错误信息。

### 6.3 POST `/api/v1/settings/models/reload`

在保存互斥锁内读取磁盘 YAML，使用与保存相同的严格校验及适配器构建逻辑，然后发布新快照，返回脱敏设置。不修改磁盘文件，不影响在途任务。配置内容未变化时保留 revision；只有注释或排版变化时更新磁盘指纹，保持配置 revision 不变，避免无意义的编辑冲突。密钥变化也视为配置变化。

读取失败返回 `SETTINGS_READ_FAILED`（500）；文件无效返回 `SETTINGS_INVALID`（400），不返回 YAML 原文。失败时保留原快照、revision 和磁盘指纹。刷新与保存串行化，旧页面不能覆盖已加载的新配置。

设置页初次进入及刷新均调用此接口，成功后同步聊天区模型选择；存在未提交草稿时沿用丢弃确认。刷新按钮位于右上角主页按钮左侧，主页统一使用 Presentation 图标。

### 6.4 GET `/api/v1/llm/profiles`

## 7. 在途任务、恢复与状态展示

### 7.1 在途与恢复

同一进程内暂停/继续的 Run 必须保留其配置快照和当前生效模型，不因为保存设置而重新按当前 default 解析。

初始选择保留在 `Run.Model`；新增 `RuntimeCheckpoint.ModelRoute` 保存 revision、道路用途、初始 profile、active profile、provider、model 和接替状态，并保存仅供后端恢复核对的配置指纹，不保存密钥。Run 查询新增安全的 `model_execution` 投影，从检查点导出实际模型；不把内部配置指纹返回客户端。

跨进程恢复时对比已记录配置身份与启动加载配置。若无法重建原快照或实际模型已变化，返回明确的不可恢复原因，要求新建一轮；不把新配置偷偷套进旧 Run。本期不建设保存历史密钥的快照仓库，也不承诺服务重启后恢复已删除的配置。使用内部配置指纹校验身份，不把可含凭证关联信息的内部指纹投影到客户端。

### 7.2 模型接替事件

主路沿用当前 activity 体系，在首选重试耗尽且决定接替时发送可持久化状态更新，展示「已切换至备用模型 ××」。包含 `model.fallback` 活动及 from/to 的安全名称和用途；该活动只由重试耗尽的 `ErrUnavailable` 触发，每次实际接替只记录一次。

先保存 active 模型变化，再进入备用调用，使 SSE 重连、暂停恢复和后续上下文窗口查询能够获得同一状态。备用模型失败时，终态明确失败，不能让接替提示成为成功结论。

UI 中聊天区手选保持不变，运行状态单独显示实际模型；上下文容量、用量归属和诊断使用实际模型。不要把旁路 token 混入主路容量占用。

旁路复用各自已有返回或任务事件通道携带安全的实际模型/接替信息；命名沿用项目线程事件，commit 沿用其任务事件，polish/briefing 等同步接口在响应元数据中携带，不为此改造成新的流式任务。

设置为全局独立页面，包含「模型配置」「模型分配」，不属于某个项目。按 2026-09-22 最新用户决定，移除页面级「保存全部」，保留已保存配置快照和各卡片独立编辑缓冲。

模型库表现为翻转卡片：正面为品牌 logo 与自定义 name，背面为 provider/name/model/key 和底部保存、取消、删除操作。卡片「保存」校验并立即持久化当前模型，成功后收起，失败保留编辑内容。新建未保存的模型不进入分配列表；取消新卡直接移除，取消已保存模型的编辑则恢复其已保存值。

模型分配每次选择后立即保存，保存中暂时禁用写入入口并显示进度，成功使用返回的最新 revision，失败恢复原分配并反馈错误。删除已保存模型确认后立即持久化，仍禁止删除被引用模型及最后一个模型。卡片保存、分配保存和删除均复用现有全量 PUT，将已保存快照与本次操作组合成完整配置；重命名同时替换全部引用，不夹带其它卡片的未保存输入或未完成的新模型。成功后保持其它卡片的稳定 ID 与编辑缓冲，避免丢失未保存的工作。保存请求使用前端互斥保护，后端继续校验 revision 与磁盘指纹，冲突时提示刷新，不自动覆盖。

点击其他卡片或空白处收起当前卡片，不丢弃尚未保存的编辑输入。离开整个设置页面才对未提交修改统一处理。独立 HTML 演示仅在内存中模拟卡片保存，刷新恢复示例数据，不读取真实配置或密钥。

所有模型选择为下拉。用途下拉提供「使用旁路默认模型」，fallback 提供「不启用备用模型」。provider 使用下拉，name/model 使用单行文本框，key 使用可切换显示/隐藏的单行密码框。Kimi 卡片使用黑色单色 SVG。

根据用户最新澄清，短文本配置使用单行输入框；只有长文本配置才使用固定高度、内部滚动且禁止用户拖拽改高度的多行文本框。当前模型设置没有长文本配置项，不使用多行文本框。此规则取代此前将所有文本输入统一做成多行的理解。
