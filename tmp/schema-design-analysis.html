PPT Agent JSON Schema 设计分析

目标不是重写一套“看起来完整”的协议，而是把仓库现有能力、HTML PPT 业务、前后端架构、Agent 工程实践放到同一张桌子上，明确每个字段到底归谁、解决什么问题，以及后续是保留、增加、减少还是替换。

临时分析页 生成日期：2026-08-08 当前权威 schema：3.0 参考：Codex / ClaudeCode 文件真相实践 参考：html-ppt SKILL.md 原文

已敲定改动点

后续你拍板的 schema 决策都记录在这里，正文分析同步调整。

  1. 001. schema_version 改为 version 适用于 outline.json、design.json、slides/{id}/spec.json 以及后续相关 schema。字段仍由 Runtime 托管，语义不变，只改命名。
  2. 002. 删除 sections[].number 章节编号由 sections[] / subsections[] 的顺序派生，不进入 JSON 真相源。重排、跨组移动后由 UI/API 计算展示编号。
  3. 003. 删除 narrative_arc 不保留 deck 级自由文本叙事路径。后续如果需要叙事控制，应通过更具体的字段表达，例如章节目的、页面角色或结构化 storyline。
  4. 004. core_thesis 替换为 positioning positioning 是可选字符串，表示整份 PPT 的核心主张、立场或判断。它回答“看完这份 PPT，观众应该接受什么判断？”，不是标题、行动目标或章节结构。
  5. 005. 所有 ID 由 Runtime 生成并对 Agent 隐藏 统一短 ID 格式：project=pro_<rand6>、slide_id=sli_<rand6>、section_id=sec_<rand6>、subsection_id=sub_<rand6>。Agent-facing contract 不暴露真实 ID；Agent 通过标题、顺序、选择项或 Runtime handle 表达意图，由 Runtime 映射到持久 ID。
  6. 006. 新增 constraints Deck 级硬约束字段，用来记录“必须写什么”和“不能写什么”。其他字段主要表达正向目标，constraints 专门承载禁区、边界、不可违反项和用户显式要求。
  7. 007. 新增 sections[].purpose 每个 section 都应有清晰定位，说明这一小节在整份 PPT 中承担什么作用，避免 section 只有标题但缺少叙事职责。
  8. 008. 删除 design.canvas 固定 16:9 / 1600x900 是 Runtime/System Prompt/HTML Output Contract，不是设计稿字段。design.json 不再保存 canvas，避免伪可配置和重复 diff。
  9. 009. project_id 重命名为 project 所有 schema 中统一使用 project 字段承载项目 ID 值，值格式仍为 pro_<rand6>，语义和 Runtime 托管属性不变。
  10. 010. design.json 收敛为主题引用 + 设计指挥 最终字段只保留 theme、direction、density、chrome 及 Runtime 托管字段。删除 tone、motion，不再保存 palette、typography、spacing、radius、shadows 等 theme.css 已沉淀内容。
  11. 011. chrome 使用三字段结构 chrome[] 每项只包含 type、placement、style。type 枚举为 page_number / section_marker / key_message / deck_title；placement 枚举为六个角点/中点加 left-edge/right-edge；不设置 visibility。

结论先行

三份 JSON 不应该合并。`outline.json`、`design.json`、`spec.json` 的拆分方向是对的，问题主要在字段粒度：`design.json` 太像“少量视觉摘要”，`spec.json` 太像“大纲卡片”，还没有把布局模板、数据表达、组件约束这些 HTML PPT 真正需要的中间层说清楚。

建议版本策略

短期：发 3.1，只增加可选字段，前端与旧项目不破。

本轮：完成 spec.json 的轻量语义规划结构，并把 HTML 物化关系迁移到 Runtime-owned 的 materialization.json。

当前业务链路

本仓库已经形成了清晰的资源所有权：内容真相在文件系统，运行编排在 DB；Agent 通过 read_ppt/write_ppt/edit_ppt/render_slide 访问资源对象，而不是直接传路径。这一点与 Codex / ClaudeCode 的工程实践一致：文件是可审计、可 diff、可恢复的真相源，工具层负责边界和校验。

1. WorkSpec目标：spec/presentation
范围：deck/slide
意图：talk/ask/plan/execute
2. OutlineDeck 目标、受众、叙事、章节、稳定页序
3. Design全局 16:9 视觉系统，派生 common/tokens.css
4. Slide Spec单页语义、内容层级、视觉意图、讲稿
5. Slide HTML最终页面实现，Chromium 渲染与诊断证据

关键边界

Agent 可写 vs Runtime 托管

当前 schema 使用 x-runtime-managed 标记 version、revision、project、slide_id、source revision、timestamp 等字段；后续还应覆盖嵌套的 sections[].id、subsections[].id 和 spec 里的 section 引用字段。

已敲定：所有真实 ID 都由 Runtime 生成并维护，Agent-facing contract 不暴露真实 ID。模型只表达标题、顺序、归属意图或选择 Runtime 给出的临时 handle，不能伪造持久 ID。

html-ppt 的可借鉴点

该 skill 的核心不是“多主题很多”，而是这几个协议思想：模板优先、token 优先、布局可枚举、键盘 runtime 稳定、speaker notes 隔离、预览用同一 HTML/CSS 且切换不 reload。

映射到本仓库：theme.css 沉淀可复用视觉系统；design.json 只表达本 deck 如何使用主题、往哪个方向走，以及全局共享 chrome 如何出现。

ID 生成策略

字段格式唯一性边界生成者Agent 可见性说明
projectpro_<rand6>全局唯一，DB unique + 冲突重试Runtime不可见替代旧名 project_id 和 UUID；字段值仍是项目 ID，创建时必须查重，冲突重新生成。
slide_idsli_<rand6>项目内唯一Runtime不可见不表达页码或顺序；页面顺序由 slide_order 投影。

Schema 一：outline.json

/outline.json

职责：整份 PPT 的产品目标与叙事结构。它不应该保存每页内容细节，也不应该保存最终排版。

字段 当前类型 / 约束 含义 归属 建议 理由
versionconst "3.0"schema 合约版本。旧名 schema_version 已敲定替换。Runtime替换命名更短，仍用于迁移和兼容判断；模型不可写。
revisioninteger, min 1outline 内容版本。Runtime保留作为当前文件版本，与每页 materialization.source.outline 比较以判断 HTML 是否 stale。
project^pro_[a-z2-9]{6}$所属项目 ID。旧名 project_id 已敲定替换。Runtime替换字段值仍是项目 ID；由 Runtime 生成并对 Agent 隐藏，DB unique + 冲突重试。
titlestring, 1-200整份 PPT 的对外标题。Agent / 用户保留区别于项目管理标题；是演示稿内容的一部分。
goalstring, 1-1200这份 PPT 要达成的结果。Agent / 用户保留对齐生成、审查和后续编辑的最高层约束。
audiencestring, 1-600受众画像。Agent / 用户保留影响深度、术语、证据密度和设计风格；也是 html-ppt 原文要求先确认的三件事之一。
languagestring, 2-32主要语言，例如 zh-CN。Agent / 用户保留影响字体、文案长度、标点和 fallback 字体。
positioningoptional string, 1-600整份 PPT 的核心主张、立场或判断。旧名 core_thesis 已敲定替换。Agent / 用户替换回答“看完这份 PPT，观众应该接受什么判断？”。它不是 title、不是 goal、不是章节结构；可选，不 required。
narrative_arcstring, 1-1600叙事路径。Agent / 用户删除自由文本叙事路径不可执行、不可验证，容易成为空泛描述。后续若需要叙事控制，应改用更具体的章节目的、页面角色或结构化 storyline。
sections[].id^sec_[a-z2-9]{6}$章节稳定 ID。Runtime替换由 Runtime 生成并维护，对 Agent 隐藏。Agent 只写标题、目的和顺序，不创造持久 ID。
sections[].numberstring, required章节展示编号。当前由 Agent 写删除编号是由数组顺序派生的展示值，不应进入 JSON 真相源。重排、跨组移动后由 UI/API 计算展示编号。
sections[].titlestring, 1-160章节标题。Agent / 用户保留目录、分节页、导航都需要。
sections[].subsections[]array, max 64；每项 id=^sub_[a-z2-9]{6}$二级目录。ID 由 Runtime；标题由 Agent/用户替换保留二级目录结构，但 subsection 持久 ID 由 Runtime 生成并对 Agent 隐藏。
slide_orderarray, unique, max 200；items 为 sli_*持久页顺序。Runtime 持久化；Agent 表达排序意图替换文件里仍保存真实 slide_id 顺序，但 Agent 不直接写 ID；Agent-facing contract 应使用位置、标题或临时 handle 表达重排。
created_at / updated_atinteger timestamp创建/更新时间。Runtime保留冲突、审计和 UI 展示用；模型不可写。

Schema 二：design.json

/design.json

职责：选择仓库主题，并给出本 deck 的设计指挥信息。theme.css 是视觉系统真相源；design.json 不重复保存 palette、typography、spacing、radius、shadows 等 token 细节。

字段 目标类型 / 约束 含义 归属 建议 理由
versionconst "3.0"schema 合约版本。旧名 schema_version 已敲定替换。Runtime替换版本迁移入口；字段名统一为 version。
revisioninteger, min 1视觉系统版本。Runtime保留设计变化会让受影响 HTML design_stale。
project^pro_[a-z2-9]{6}$所属项目 ID。旧名 project_id 已敲定替换。Runtime替换字段值仍是项目 ID；由 Runtime 生成并对 Agent 隐藏，用于跨项目隔离。
themestring，仓库主题 ID当前 deck 使用的主题，例如 tokyo-night。seed 主题也是 repo 初始值，不需要 source 字段。Agent / 用户选择，Runtime 校验新增theme.css 承担 palette、typography、spacing、radius、shadows 等可复用视觉系统。
directionstring, 1-600在选定主题之上，本 deck 的视觉方向。例如“偏云原生控制台感，而不是赛博朋克海报感”。Agent / 用户新增替代 visual_positioning 命名；比 style 更不容易和 theme 重叠。
densitysparse | medium | dense页面信息密度。控制页面更像海报、常规汇报页，还是数据/架构密集页。Agent / 用户替换从旧 layout_system.density 提升为顶层字段；删除 tone 和 motion。
chromearray全局共享组件配置，如页码、章节标记、每页 key message 位置、deck 标题。Agent / 用户新增替代旧 signature。它不是泛泛“签名视觉”，而是可执行的跨页共享组件列表。
chrome[].typepage_number | section_marker | key_message | deck_title共享组件类型。Agent / 用户新增必须枚举，便于 Runtime/HTML 生成器稳定消费。
chrome[].placementtop-left | top-center | top-right | bottom-left | bottom-center | bottom-right | left-edge | right-edge共享组件位置。Agent / 用户新增必须枚举，避免自然语言位置导致不可执行。
chrome[].stylestring, 1-160语义化外观描述，例如 tiny muted mono counter。不能写 CSS。Agent / 用户新增给 Agent 创造力，但不允许绕过 theme token 和组件模板。
created_at / updated_atinteger timestamp创建/更新时间。Runtime保留运行时托管。

字段 当前类型 / 约束 含义 归属 建议 理由
versionconst "3.0"schema 合约版本。旧名 schema_version 已敲定替换。Runtime替换版本迁移入口；字段名统一为 version。
revisioninteger, min 1单页 spec 版本。Runtime保留用于判断 HTML 是否 spec_stale。

slide_id^sli_[a-z2-9]{6}$稳定页身份。Runtime替换由 Runtime 生成并对 Agent 隐藏。路径、版本快照、前端跳转、目录移动都依赖它；不能用 page index 代替。

slide HTML 不是 JSON，但必须有硬协议

当前业务规则已经明确：每页 HTML 使用 1600x900 .slide-stage，链接 ../../common/tokens.css 与 ../../common/base.css，使用项目本地/data/blob 资源，渲染后通过 Chromium 做诊断证据。

仍待拍板的问题

最终判断

最佳实践不是把 schema 做得最大，而是让每个字段都有明确所有者、明确消费方、明确校验方式。当前方向是：theme.css 承载可复用视觉系统，design.json 只承载 theme 选择、direction、density 和 chrome；slide spec 再承载单页语义与布局意图。
