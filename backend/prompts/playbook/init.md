id: playbook.init
description: Guides the establishment of a presentation brief, narrative structure, visual direction and initial slide content when those foundations are missing.
---

Use this playbook when the requested work needs presentation foundations that have not yet been established, including missing parts of an existing project. An application-created file or default theme does not establish the user's content or design requirements. Initialize only what the current task needs; ordinary conversation requires no setup.

## Presentation Foundations

- Establish the audience, intended outcome, language, slide count, required content and exclusions from the user's request and supplied material. Store content requirements in MANIFEST and presentation-wide visual requirements in DESIGN. Preserve actionable details from mixed content and design requests; make reversible design choices when the brief supports them.
- Build a narrative that gives each promised slide a distinct role and a supported primary message. Allocate slides to evidence, explanation and decisions rather than equally sized sections. Follow the requested count or range; do not change MANIFEST merely to fit an easier outline.
- Create the initial OUTLINE when it is missing, using the editing tool's initialization contract. For an existing outline, extend its saved structure and preserve existing identities. Use identities returned by the application before dependent Spec or HTML writes, and follow the current slide authorization.

## Initial Slide Content

- In SPEC, express the slide's main takeaway, ordered content elements, actual supporting material and intended reading order in natural language. Explain what each element contributes. Identify missing evidence rather than inventing content to complete the composition.
- Keep canonical titles and order in OUTLINE. Use SPEC for semantic intent and optional local layout direction; classifications describe communication intent rather than a fixed template or CSS program.
- Carry the content into HTML when the user requested a rendered slide. A request for an outline or content brief alone does not require HTML. Complete coherent slides or batches according to their dependencies; there is no mandatory all-Specs-first sequence.
- A representative content-heavy slide can establish visual hierarchy and chart language before extending the deck when that prevents repeated layout mistakes. It is not an automatic approval checkpoint.
