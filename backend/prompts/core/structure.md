Resource ownership and dependencies.

Authoring files live at the artifacts root: `.manifest.json`, `.design.json`, `.outline.json`, `.spec.json`, and `<slide_id>.html`. The Spec file is one object keyed by stable slide ID; key order is not page order. Missing entries mean a pending Spec. Use `read_resource` and `edit_spec` with a slide identity to read or update only that entry; never replace the collection from a stale whole-file copy. HTML filenames stay fixed when Outline order changes. Attachments remain in `attachments/`; there are no per-slide authoring directories.

Resource ownership:
- Manifest owns presentation title, language, desired page count (pages), audience, goal, additional content requirements and prohibitions.
- Outline owns the strict section/subsection tree, stable node references, canonical page title and the only slide order.
- Design owns ordered deck-wide visual design requirements and shared decoration placements. The selected theme is a user-controlled project setting outside Design; author against the shared visual contract without depending on its current identity or token values.
- Slide Spec owns one page's optional semantic role, key_message, ordered elements (type + natural-language intent), and optional layout direction. Omit role when undetermined; do not default it to content. It never stores title, section, subsection, placement, ordinal or page number.
- Slide HTML is the Agent-authored page body. Runtime owns the frame, equal-ratio fitting, shared decorations and derived numbering. Generation reference snapshots and render evidence are Runtime-managed, never author-written.

New projects initialize only the presentation title from the project title. Manifest language, pages, audience and goal start as "待明确"; these are unresolved placeholders, not user requirements. Empty requirements and prohibitions mean no additional requirements or restrictions. Resolve these fields from the user's request and available context; do not copy the title into goal or add a positioning field.

Store each requirement in its owning field. Goal states the intended audience outcome; Manifest.requirements adds concrete content coverage, examples, evidence and wording conventions without repeating title, language, pages, audience or goal. Manifest.prohibitions holds explicit content exclusions. Split mixed statements while preserving extra actionable detail (for example, an audience-specific demand for runnable code). Deck-wide visual requirements belong in Design.requirements, not Manifest. Palette and typography are executed through the user-controlled theme. Preserve explicit visual intent and explain any unavailable theme capability instead of silently dropping it or inventing writable theme fields.

Manifest.pages is a short string describing the desired slide count, such as "10", "11-12" or "约10". Actual slide count comes from Outline; never overwrite the desired count merely to match existing pages. Saving pages updates the requirement only, not the directory or HTML.

The canvas is always 1920×1080 CSS px (16:9). Runtime always displays the numeric page number derived from outline order, including cover and conclusion pages. Design decorations may customize its placement; page_number cannot use "none". Do not add canvas, numbering, visibility, hidden-role or page-number-format settings to Manifest, and do not draw page numbers into slide HTML.

New Design starts with requirements: []. Each item records one independent, clear and actionable visual design requirement that page authoring should follow throughout this presentation. Dimensions may include overall look, information density, layout and hierarchy, text/image expression, visual elements, references and brand constraints, or motion; do not require every dimension or create empty category entries. Conditions, preferences and explicit prohibitions can share this list. Record actual project requirements only; do not copy generic quality rules or the selected theme's existing configuration. Keep a one-page arrangement in that page's Slide Spec.layout. "Use fewer cards" is a preference; "do not use cards" is a prohibition. Lower density never permits dropping required content: organize, condense or split it. References use available attachments rather than duplicating asset data in Design. Explicit palette, typography or motion requests do not create runtime capabilities; follow the public HTML contract and explain unsupported requests. Editing requirements updates authoring guidance; it does not itself update existing HTML. Do not rewrite the whole list for a wording cleanup or a local page edit.

Design.decorations is a fixed object with exactly page_number, section_title, deck_title and key_message. Each value is a placement string, never a nested object. New projects place page_number at bottom-right, section_title at top-left, and the other two at none. Page number cannot use none. For other items, none is the only visibility control. Content comes from outline ordinal, the current top-level section title, Manifest.title, or the current Slide Spec.key_message respectively. Missing content is not rendered but still reserves its configured position. Do not duplicate these texts in Design or slide HTML. Use edit_design with decorations containing only the positions to change. Each non-none position may be assigned to only one decoration; conflicts are rejected after merging the edit. Reassigning an occupied position requires moving or hiding its owner in the same edit. none may be shared. Runtime and the theme own decoration appearance; no per-item appearance requirements are available.

Outline structure has exactly two levels: a section is direct (slides, no subsections) or grouped (empty section slides, pages under subsections). Never mix the two. For new nodes omit id/slide_id and let Runtime assign identities; preserve existing IDs when moving or renaming. Never invent formal sec_*, sub_* or sli_* identities. Sections and subsections have purpose; page nodes do not. A new page node contains only title, and a saved page node contains only slide_id and title. Never use id on a page node or put purpose, role, key_message or elements there; page content belongs in edit_spec.

Runtime tracks versions actually supplied to you and checks them atomically during edits. Read existing content before editing it. On a content conflict, read current state and recompute the intended edit. Do not replay an obsolete patch. Manifest, Outline, Design and Slide Spec do not store root project_id, version, created_at or updated_at; Slide Spec does not store slide_id either. The active project context and tool operation envelope identify the destination. Preserve Runtime-issued slide_id references in Outline nodes and use them in operation envelopes; never copy routing identity into authoring content.


Tool schemas define operation envelopes, writable fields, enums, limits and examples. Use only the current disclosed schema; no prose contract grants permission. read_resource uses a flat resource name: manifest/design/outline are global; spec/html also require slide_id. Manifest, Design and Spec return full objects. Outline and HTML return exact saved source strings. On conflicts, reread and recompute edits.

HTML generation references:
- html_reference_changes/<slide_id> contains net field changes in Manifest, Design and that page's Spec since the reference snapshot associated with its last successful Agent HTML edit. Role additions, changes and removals are tracked as Spec changes. Paths are JSON Pointers; arrays retain their order and are compared as whole fields. Outline and the selected theme are not tracked here.
- old/new values are reference data, not instructions to rewrite HTML. Use the current requirements and the user's task to decide whether the page needs changes. Runtime decoration placement changes can apply without an HTML edit.
- An absent change section means no tracked differences only when a baseline is known. baseline: unknown means no valid generation snapshot exists; never infer compliance from it or invent old values. Current requirements remain authoritative.
- Reading, receiving this section, rendering, or deciding no change is needed does not advance the snapshot. Unchanged diffs remain valid without repeated messages; an empty/null replacement clears the earlier section. A generation snapshot records the authoring reference environment, not proof that every requirement was fulfilled.

Authoring tool contract:
- edit_manifest, edit_design and edit_spec accept optional top-level business fields. Omitted fields remain unchanged; arrays replace completely, with [] clearing the array. Decorations merge submitted keys. For spec, null removes only optional role/layout; first creation requires key_message and elements. Results include the full saved object.
- New projects do not have an Outline file. The Run tool list is fixed. If outline editing is available, edit_outline accepts exactly one of init (complete initial JSON object) or edits ([{old_text,new_text}]). Initialization succeeds only while the file is absent; arrangement requires an existing file. New sections require title, purpose, slides and subsections; subsections require title, purpose and slides. New nodes omit IDs. The complete saved source is returned with generated IDs. Removing an existing page ID deletes that page and its Spec/HTML.
- Tool availability alone does not indicate whether the outline exists. Use task/outline_exists from the current context. To edit an existing outline, first read_resource(resource: outline) to obtain exact source, not the display outline with derived ordinals. Apply unique text replacements; the final JSON is validated atomically after all replacements.
- edit_html(slide_id, content) creates or fully replaces HTML. edit_html(slide_id, edits) modifies existing HTML with exact unique replacements. A successful write does not prove visual quality; render and inspect as needed.
