运行时上下文 · 决策记录

记录当前七项决定及实施建议。本文是设计记录，运行时改造尚未实施。

01

采用明确的固定顺序

运行时上下文按内容职责与阅读逻辑排列，替换当前按名称排序的方式。顺序由加载器集中维护。

  • 第一组为资源目录，依次提供 available_skills 与 available_components。
  • 第二组为项目背景 project_background。
  • active_skills 与 active_components 放在项目背景之后，与后续动态上下文一起组织。
  • 后续动态模块之间的完整顺序继续讨论。

资源目录在可用资源集合不变时保持稳定，放在项目背景之前以利于前缀缓存复用；目录内容仍以当前可用资源为准。固定顺序用于每次请求的当前上下文组装。

02

统一使用 id 与 desc 属性

runtime_context 与 system_prompt 对齐命名方式：使用 id 标识模块、desc 描述模块内容，不设置 scope 属性。

  • id 替代原来的 section 字段，作为稳定的模块标识。
  • desc 使用一句简短英文说明该模块提供的信息。
  • 标签内直接放实际 JSON 数据，移除外层 section 与 value 包装。
<runtime_context id="project_background" desc="Provides the presentation's current outline, manifest and design.">
{
  "outline": "not exist",
  "manifest": "not exist",
  "design": "not exist"
}
</runtime_context>

实施建议：描述文字保持稳定；后端继续用内部元数据维护模块身份与变化状态，并在输出标签属性时正确转义。

03

统一提供完整项目背景

project_background 位于资源目录之后，正文固定包含 outline、manifest、design 三个字段，分别承载 OUTLINE、MANIFEST 与 DESIGN 的当前内容。

  • 文件存在时，提供对应的结构化内容。
  • 文件不存在时，该字段使用固定字符串 "not exist"。
  • 不再提供单独的 xxx_exist 或 xxx_exists 标记。
  • 合并原来的 project_context、design_context、outline 内容，移除 task/outline_exists，避免重复注入。

假数据示例：OUTLINE 已建立但还没有章节，MANIFEST 与 DESIGN 尚未建立。

{
  "outline": {
    "sections": []
  },
  "manifest": "not exist",
  "design": "not exist"
}

建议明确的边界："not exist" 仅表示文件缺失；已存在且有效的空内容保持原样。读取失败或 JSON 无效应明确报告错误，不得标记为不存在，也不得用默认值掩盖缺失。

这三份内容在确认后通常较稳定；发生结构、内容要求或视觉要求调整时，下次请求使用更新后的完整项目背景。

04

每次请求提供一份当前快照

运行时上下文与对话历史分开管理。每次模型调用前，按固定顺序组装一份最新的运行时上下文，再与系统提示词和对话、工具历史组成请求。

系统提示词

当前运行时上下文
  available_skills
  available_components
  project_background
  后续动态上下文
    包含 run_state、retrieved_info、active_skills、active_components，具体顺序待定

用户、助手和工具消息历史
  包含当前用户请求及本轮工具执行记录
  • 模型输入只保留一份当前运行时快照，不累积旧的自动上下文快照。
  • 用户消息、助手回复、工具调用和工具结果保持正常历史。
  • 后台可保留过去的请求快照用于追踪，但不自动回填到后续模型输入。
  • 最终仍通过模型接口支持的消息结构传递上下文；分开管理不依赖专用的 runtime_context API 参数。

接受动态上下文变化可能降低后续内容缓存复用的代价。资源目录优先形成稳定前缀，项目背景与激活资源按当前状态更新。

05

合并为 run_state

将当前运行模式、授权范围、执行阶段和用户引用的幻灯片合并为 run_state，正文固定包含四个字段。

  • run_mode：当前生效的运行模式。
  • run_scope：当前实际授权的幻灯片 ID 数组，表示权限边界，不表示这些幻灯片都必须处理。
  • run_phase：后端当前执行阶段，按实际运行状态提供。
  • run_mentioned：用户显式引用的幻灯片 ID 数组；引用不授予写权限，不混入系统自动推断的相关页面。

结构示例，以下 ID 为假数据：

<runtime_context id="run_state" desc="Provides the current run mode, authorized slides, execution phase and user-mentioned slides.">
{
  "run_mode": "execute",
  "run_scope": ["sli_a", "sli_b"],
  "run_phase": "executing",
  "run_mentioned": ["sli_reference"]
}
</runtime_context>
  • 合并原来的 run_command、task/phase 和 mentioned_pages 中对应的信息，移除重复的 target_context。
  • 不向模型提供 run_scope_type 或额外的范围类型、来源与新增页授权标记。
  • 新增页面是否获得授权继续由后端判断；通过工具结果或下一轮上下文明确更新后的授权 ID 列表，模型使用最新范围。

用户的具体任务继续由用户消息承载；幻灯片内容独立提供。此决定只调整模型可见的上下文，不取消后端权限校验。

06

检索信息独立为 retrieved_info

将原来的 task/context_briefing 作为独立运行时上下文块提供，使用 id="retrieved_info"。

  • 承载自动检索得到的补充参考信息，不放入 run_state。
  • 使用 retrieved_info，不采用 semantic_retrieval；名称描述检索结果，不限定检索方式，也不暗示已有语义检索能力。
  • desc 使用 Provides supplementary reference information retrieved for the current task.

当前实际内容来自幻灯片 HTML 的文字摘录，经关键词检索和筛选后提供；这次决定不扩展检索能力，也不将其定义为对话压缩摘要。

07

取消默认注入 HTML 参考差异

不再默认注入 html_reference_changes/<slide_id>，避免在当前项目背景之外重复提供历史参考值及字段差异。

  • Agent 根据用户请求、当前项目背景，以及按需读取的 Spec 和 HTML 判断是否需要修改页面。
  • 模型不再自动获得 HTML 上次保存时的参考快照与当前 Manifest、Design、Spec 之间的旧值／新值对照。
  • 如果以后明确需要批量同步变更要求，再为该场景设计差异信息的提供方式。

本决定针对默认上下文注入；后台历史快照是否保留或清理另行评估，不因本记录直接删除。
