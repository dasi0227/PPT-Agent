02

使用 runtime_context 标签及 id、desc 属性

运行时信息统一使用 runtime_context 标签，并与 system_prompt 对齐属性命名：使用 id 标识模块、desc 描述模块内容，不设置 scope 属性。

  • id 替代原来的 section 字段，作为稳定的模块标识。
  • desc 使用一句简短英文说明该模块提供的信息。
  • 标签内直接放实际 JSON 数据，移除外层 section 与 value 包装。
  • 资源存在状态统一使用 exists 与 missing；具体内容通过读取工具按需获取。
  • 没有计划时，plan 模块正文为 null；没有检索结果时，retrieved_info 模块正文为 []。两者均不因无数据而省略。
<runtime_context id="project_state" desc="Provides current resource availability, slide render freshness and cumulative changes in this run.">
{
  "outline": "missing",
  "manifest": "missing",
  "design": "missing",
  "slides": {},
  "changes": []
}
</runtime_context>

实施建议：描述文字保持稳定；后端继续用内部元数据维护模块身份与变化状态，并在输出标签属性时正确转义。

03

项目资源与变更统一为 project_state

将原 project_setup、slide_state 与 changes 合并为 project_state，放在 run_state 后面；完整模块顺序统一见第一张决策卡片。该模块提供资源存在状态、截图新鲜度和本次 Run 的累计净变化。

  • outline、manifest、design 仅提供 exists 或 missing，不再默认注入文件完整内容，也不另设 xxx_exists 标记。
  • slides 覆盖当前 OUTLINE 中的全部幻灯片，以稳定的幻灯片 ID 为键；spec 表示 .spec.json 中对应条目的存在状态，html 表示对应 HTML 文件的存在状态，均使用 exists 或 missing。
  • render 使用 fresh、stale 或 missing，分别表示最新截图匹配当前渲染输入、截图已过期或没有截图。
  • changes 按项目文件或整张幻灯片汇总本次 Run 的累计净变化，每项仅含 target 与 type；具体规则见变更决策卡片。
  • 不再独立注入原 project_context、design_context、outline、task/outline_exists、page/<slide_id> 或 task/latest_rendered_images。

结构示例，以下 ID 与状态为假数据；已删除的幻灯片只出现在变更清单中：

<runtime_context id="project_state" desc="Provides current resource availability, slide render freshness and cumulative changes in this run.">
{
  "outline": "exists",
  "manifest": "exists",
  "design": "exists",
  "slides": {
    "sli_a": {
      "spec": "exists",
      "html": "exists",
      "render": "stale"
    }
  },
  "changes": [
    {"target": "outline", "type": "updated"},
    {"target": "sli_a", "type": "updated"},
    {"target": "sli_b", "type": "deleted"}
  ]
}
</runtime_context>

内容统一按需读取：需要理解叙事结构、解析页码或标题时调用 read_resource 读取 OUTLINE；需要内容要求、视觉规范或具体幻灯片内容时，读取相应 MANIFEST、DESIGN、Spec 或 HTML。复用已经获得且仍有效的内容，缺失或过期时重新读取。

读取失败、文件损坏不能记为 missing，也不能用默认值掩盖缺失。存在状态与截图新鲜度不代表内容质量或任务完成；列出幻灯片不授予写权限，实际授权仍由 run_state.run_scope 表达。

04

每次请求提供一份当前快照

运行时上下文、真实会话记录和模型输入投影分开管理。每次模型调用前，按固定顺序组装一份最新的运行时上下文，再提供对话历史，最后放置本次 Run 的 user_request。

系统提示词

当前运行时上下文
  各模块顺序统一见第一张决策卡片

对话历史
  之前 Run 的需求、助手回复及完整的工具调用与结果

user_request
  本次 Run 的原始需求、追加修订及必要澄清问答
  • 模型输入只保留一份当前运行时快照，不累积旧的自动上下文快照。
  • 真实会话仍按发生时间保存；仅在模型输入中将本次 Run 的普通用户输入归入最后的 user_request，不在历史中重复提供。
  • 通过工具获得的澄清回答和计划反馈在历史中保留原工具结果以维持调用配对，同时纳入需求模块。下一次 Run 将此前输入恢复为普通历史。
  • 后台可保留过去的请求快照用于追踪，但不自动回填到后续模型输入。
  • 最终仍通过模型接口支持的消息结构传递上下文；runtime_context 是内容标签，不是模型接口的专用 API 参数。

接受动态上下文变化可能降低后续内容缓存复用的代价。资源目录优先形成稳定前缀；已激活资源使用当前内容，项目状态使用当前快照，项目文件正文按需读取。

05

合并为 run_state

将当前运行模式、授权范围和执行阶段合并为 run_state，正文固定包含三个字段。用户引用的幻灯片 ID 随用户需求文本传入，不在运行时状态中重复提供。

  • run_mode：当前生效的运行模式。
  • run_scope：当前实际授权的幻灯片 ID 数组，表示权限边界，不表示这些幻灯片都必须处理。
  • run_phase：后端当前执行阶段，按实际运行状态提供。

结构示例，以下 ID 为假数据：

<runtime_context id="run_state" desc="Provides the current run mode, authorized slides and execution phase.">
{
  "run_mode": "execute",
  "run_scope": ["sli_a", "sli_b"],
  "run_phase": "executing"
}
</runtime_context>
  • 合并原来的 run_command 与 task/phase 中对应的信息，移除重复的 target_context。
  • 移除 run_mentioned，不再单独注入 mentioned_pages。引用通过用户消息中的显示名称与稳定幻灯片 ID 表达，引用本身不授予写权限。
  • 普通 @ 引用目前由前端提交序列化将 ID 写入需求文本，后端校验引用；实施时确保任务恢复等入口也把引用关系完整放入模型收到的用户消息。
  • 不向模型提供 run_scope_type 或额外的范围类型、来源与新增页授权标记。
  • 新增页面是否获得授权继续由后端判断；通过工具结果或下一轮上下文明确更新后的授权 ID 列表，模型使用最新范围。

用户的具体任务继续由用户消息承载；幻灯片内容按需读取。此决定只调整模型可见的上下文，不取消后端权限校验。

06

检索信息独立为 retrieved_info

将原来的 task/context_briefing 作为独立运行时上下文块提供，使用 id="retrieved_info"。

  • 承载自动检索得到的补充参考信息，不放入 run_state。
  • 正文使用数组，每项仅包含 target、source 与 content：分别表示来源目标、来源类型与实际文字摘录。
  • 当前来源为幻灯片 HTML，target 使用来源幻灯片 ID，source 使用 html；content 来自实际检索到的文字，不编造或补写内容。
  • 不注入检索评分、哈希、内部索引或检索过程信息；没有结果时提供空数组 []，保留模块位置。
  • 使用 retrieved_info，不采用 semantic_retrieval；名称描述检索结果，不限定检索方式，也不暗示已有语义检索能力。
  • desc 使用 Provides supplementary reference information retrieved for the current task.

结构示例，以下 ID 与摘录为占位数据：

<runtime_context id="retrieved_info" desc="Provides supplementary reference information retrieved for the current task.">
[
  {
    "target": "sli_reference",
    "source": "html",
    "content": "从来源幻灯片 HTML 中提取的实际文字。"
  }
]
</runtime_context>

当前实际内容来自幻灯片 HTML 的文字摘录，经关键词检索和筛选后提供；这次决定不扩展检索能力，也不将其定义为对话压缩摘要。

07

取消默认注入 HTML 参考差异

不再默认注入 html_reference_changes/<slide_id>，不额外提供历史参考值及字段差异。

  • Agent 根据用户请求，以及按需读取的当前项目文件和幻灯片内容判断是否需要修改页面。
  • 模型不再自动获得 HTML 上次保存时的参考快照与当前 Manifest、Design、Spec 之间的旧值／新值对照。
  • 如果以后明确需要批量同步变更要求，再为该场景设计差异信息的提供方式。

本决定针对默认上下文注入；后台历史快照是否保留或清理另行评估，不因本记录直接删除。

08

移除 related_context

移除独立的 related_context 上下文块，不再额外注入按相邻位置、同一 subsection 或用户引用规则选出的相关幻灯片 ID 列表。

  • 需要幻灯片顺序与层级时，通过 read_resource 读取 OUTLINE，Agent 根据实际任务判断哪些页面值得参考。
  • 用户显式引用随用户需求文本提供，不再复制为 run_state 字段或另一份相关页列表。
  • 自动检索的补充参考信息由 retrieved_info 独立承载，不混入用户显式引用。
09

计划信息统一放入 plan

使用 <runtime_context id="plan"> 独立承载当前计划及其相关运行时信息。

  • 有计划时，正文仅包含 title、content、status、approved 与 steps，分别提供计划标题、完整正文、当前状态、审批结果与有序步骤。
  • status 沿用现有计划状态：awaiting_approval、active、completed 或 canceled。
  • approved 为布尔值，由后端根据当前计划内容与有效审批记录是否匹配计算；不能仅凭执行模式或计划处于 active 状态推断用户已经批准。
  • steps 中每项包含 id、title 与 status；保留后端分配的步骤 ID 供进度更新工具使用。步骤状态沿用 pending、processing、completed 或 failed。
  • 替代原来的 task/plan，不再单独注入 task/plan_authority；不提供计划 ID、审批 ID、审批哈希或内部时间戳。
  • 没有计划时，模块正文为 null，保留模块位置。
  • desc 使用 Provides the current plan, step progress and approval state.

结构示例，以下计划与步骤 ID 为假数据：

<runtime_context id="plan" desc="Provides the current plan, step progress and approval state.">
{
  "title": "调整演示文稿",
  "content": "先确认内容结构，再修改幻灯片并完成检查。",
  "status": "active",
  "approved": true,
  "steps": [
    {"id": "step_example_1", "title": "确认内容结构", "status": "completed"},
    {"id": "step_example_2", "title": "修改幻灯片并完成检查", "status": "processing"}
  ]
}
</runtime_context>

计划与审批状态以实际运行记录为准；合并上下文不取消后端的审批校验与已批准计划保护。

10

按技能与组件聚合已激活内容

使用 active_skills 和 active_components 作为独立模块 ID；正文分别按 skill/<id> 和 component/<id> 区分各项资源。

  • available_skills 与 available_components 提供可用资源目录；对应的 active 模块提供当前已激活或已加载资源的完整内容。
  • 每个 active 模块使用 JSON 对象，以资源标识为键、当前加载内容为值；同一资源在模块中只出现一次。
  • 不再将 skill/<id>、component/<id> 分别注入为顶层模块，也不再单独提供 task/active_skills ID 清单。

结构示例，以下资源 ID 与内容为占位数据：

<runtime_context id="active_skills" desc="Provides the full content of currently active skills, grouped by skill ID.">
{
  "skill/example": "该技能的完整内容"
}
</runtime_context>

<runtime_context id="active_components" desc="Provides the full content of currently loaded components, grouped by component ID.">
{
  "component/example": "该组件的完整 HTML 内容"
}
</runtime_context>
11

按目标汇总本次 Run 的净变化

project_state.changes 记录相对于本次 Run 开始时的累计净变化；每个目标只出现一次，没有净变化时使用空数组。

  • target 直接使用 outline、manifest、design 或幻灯片 ID；不再嵌套目标对象，也不区分幻灯片的 HTML 与 Spec。
  • type 统一使用 created、updated 或 deleted；不保留 changed: true 或 change 字段。
  • 幻灯片的 created 与 deleted 以其在 OUTLINE 中的新增或移除为准。修改已有幻灯片的标题、Spec 或 HTML，或首次为其生成 Spec、HTML，均汇总为 updated。
  • 新增后继续修改仍记为 created；新增后删除，或相关内容全部恢复到 Run 开始时的状态，则移出清单。
  • 已删除的幻灯片从当前 slides 中移除，累计删除记录保留在 changes 中。

后端继续保留具体资源的变更记录，用于差异计算和完成检查；向模型提供时再按目标聚合。

12

取消默认注入 evidence

不再向模型默认注入 task/evidence；模型通过实际工具结果了解检查结果，通过 project_state.slides[slide_id].render 了解截图是否匹配当前渲染输入。

  • 保留后端证据账本和任务完成检查，继续核对必要检查及其与当前内容的对应关系。
  • 缺少必要检查或检查已经过期时，由 finish_task 返回具体缺项与补救要求，Agent 按结果补齐。
  • 接受部分遗漏检查直到请求完成任务时才被发现，不额外注入一份检查状态清单。

本决定仅取消模型侧默认注入，不降低后端完成条件，也不将截图存在或新鲜等同于任务完成。

13

Execute 模式的静态提示词顺序

core.agent → core.output → core.reference → core.quality
→ mode.execute
→ workflow.execution → workflow.recovery → workflow.completion
→ playbook.init → playbook.improve → playbook.html → playbook.runtime

init 与 improve 同时加载，分别指导缺失基础的建立和现有成果的完善；同一项目可以同时存在这两类工作。playbook.html 承载 HTML 创作规范，playbook.runtime 仅说明第一张卡片中各运行时 ID 的含义、使用时机和边界。

具体工具的参数和调用约定放在工具定义中，不恢复独立的 next-input-suggestions 模块。

14

user_request 始终位于请求末尾

该模块逐项保留当前 Run 的原始需求、追加修订和必要澄清问答，按真实输入顺序组织，不生成推断式需求摘要。后续明确修订覆盖冲突内容，其余先前要求继续有效。

  • 正文、COMMENT、映射后的 ID 和附件顺序沿用现有表达；图片保留原生多模态内容，不转换成编码文本。
  • 同一 Run 的工具循环、恢复和压缩后均重新投影该模块，保留当前需求中的原始引用和图片。
  • 末尾需求保持不变时保留可用的协议连续性；需求、工具或前序内容发生变化时重新核验，不能复用不匹配的协议状态。
  • 该模块是请求投影，不作为新的用户事件写回会话记录；重复出现在请求末尾不表示重新启动任务。
